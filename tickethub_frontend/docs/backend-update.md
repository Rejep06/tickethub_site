# Обновление фронтенда под PortalBilet и пакетный редактор

Дата: 7 октября 2026. Основание: **исходный код** `tickethub_portalbilet_editor_partial(1).zip`, а не предположение о работающем внешнем API.

SHA-256 архива backend: `de82b597ae1bc6478c4c897fefe11137f735ce2a9f36a6d0ac6fabc053629e21`.

Бэкенд не изменён. Фронтенд сохраняет прежние каталог, оформление, сессии/CSRF, кабинет, staff-панель, RU/EN и светлую/тёмную/системную темы. Все дополнительные вызовы идут в реальный `/api/v1/`; тестовые данные не используются в production flow.

## 1. Обложка мероприятия

**Создание:** `/ru/staff/events/new` → выбрать изображение в блоке «Обложка мероприятия» → указать основание использования и подтвердить права → заполнить событие → создать. Фото необязательно: его можно добавить позже.

**Замена:** `/ru/staff/events/{id}` → верхний блок «Обложка мероприятия» → выбрать файл → «Сохранить обложку». Якорь `#event-cover` ведёт непосредственно к этому блоку. Обложка отображается в staff-списке, публичной карточке и странице события через поле `image`. Публикация самого события — отдельное действие.

Форма поддерживает выбор файла и перетаскивание, предварительный просмотр, размер и разрешение, отмену нового выбора, сохранённое изображение и индикацию результата. Проверяется сигнатура PNG/JPEG/WebP, декодирование браузером, лимиты 10 МиБ, 8000 px по стороне и 40 млн пикселей. SVG, просто переименованный в PNG, получает отдельное объяснение. Серверная проверка остаётся окончательной.

Загрузка выполняется **отдельным multipart POST**, не JSON-полем события:

```text
POST /api/v1/staff/events/{id}/image/?lang=ru
image              файл
rights_source      строка, до 500 символов
rights_confirmed   true
expected_version   актуальная версия события
```

`Content-Type` для FormData не выставляется вручную: браузер добавляет boundary. Сохраняются credentials и X-CSRFToken; перед записью запрашивается `/api/v1/auth/csrf/` без lang. Версия берётся с сервера.

При создании выполняются два шага: POST события, затем POST изображения. После известного успеха первого шага его ID удерживается до завершения второго. Ошибка загрузки не запускает повторное создание события. Можно повторить загрузку либо открыть уже созданную карточку. При потере ответа **самого первого POST** сохраняется обычная неопределённость исходного CRUD API: перед повторным созданием нужно проверить список событий, поскольку отдельного серверного ключа идемпотентности для Event здесь нет.

При 409 изображение остаётся выбранным, повторная запись блокируется до обновления версии. Несохранённая основная форма блокирует параллельную загрузку изображения; выполняющаяся загрузка блокирует редактирование основной формы/геометрии. Не выполняется скрытого удаления обложки: отдельного image DELETE в присланном API нет. Кнопка отмены убирает только новый локальный выбор. Загрузка по внешнему URL, автоматическая конвертация SVG и обрезка на сервере не добавлены.

Исходники контракта: `backend/events/views.py` (`StaffEventViewSet.image`, `EventImageSerializer`), `backend/core/serializers.py` (`ImageUploadSerializer`), `backend/core/validation.py`, `backend/events/serializers.py` (`image` read-only).

## 2. Импорт по ссылке PortalBilet

Маршруты фронтенда:

```text
/ru/staff/external-events
/ru/staff/external-events/{source_id}
```

Пункт «Импорт мероприятий» появляется в меню администратора. Доступ проверяется через существующий staff/admin API, а не роль, придуманную из `/me/`. MANAGER и покупатель не получают интерфейс импорта. Сервер повторно проверяет ADMIN и парольную staff-сессию.

Процесс: URL → серверный предпросмотр → подтверждение импорта → отчёт → созданные локальные события. На карточке источника доступны даты, привязка к площадке, диагностика и ручная синхронизация. С каждой даты есть переход к редактированию мероприятия и его обложке. При неизвестном результате сеть/тайм-аут не вызывает автоматического повтора.

| Метод | API после `/api/v1/` | Назначение |
|---|---|---|
| GET | `staff/external-events/` | Источники, серверная пагинация |
| GET | `staff/external-events/{id}/` | Источник, даты, диагностика |
| POST | `staff/external-events/preview/` | Непишущий предпросмотр |
| POST | `staff/external-events/import/` | Создание черновиков/снимков |
| POST | `staff/external-events/{id}/sync/` | Синхронизация; тело `{}` |

Preview/import передают только `provider: "portalbilet"`, `url`, `mode: "IMPORT_ONLY"`. Поле preview необязательно и не требуется при отдельном preview endpoint. Tracking-параметры ссылки убираются; безопасность загрузок обеспечивает backend.

**Ограничение именно присланного backend:** адаптер частичный. Нет подтверждённого полного декодирования схемы и связи внешних билетов с координатами. Он подготавливает непубличные даты и сохраняет диагностику; не создаёт собственные билеты, не переносит автоматически обложку и не резервирует билеты у источника. HTTP 200 может содержать `PARTIAL` или `FAILED`. Фронтенд не подменяет эти состояния успешным полным импортом. При неизвестной дате выводится «Дата и время требуют проверки», а не выдуманная дата. Известное время источника явно помечено UTC; часовой пояс и отображение события проверяются в его карточке.

Отдельного REST endpoint чтения полного содержимого ExternalSnapshot в этой поставке нет: UI показывает доступные `diagnostics/resources`, не выдуманную загрузку снимков. Режимов MIRROR/LIVE_PROVIDER_SALE нет. Реальный Bootstrap-reader, сеть провайдера и синхронизация PostgreSQL здесь не запускались.

Источники: `backend/external_events/{urls,serializers,views,services,models,provider,http}.py`, `docs/portalbilet-and-editor.md` нового backend.

## 3. Редактор схем

Открытие: `/ru/staff/seating-plans/{id}/editor`. Новый редактор использует атомарный `bulk-edit`, а не цепочку независимых POST/PATCH/DELETE старого Seat API.

Сначала загружается `GET staff/plans/{id}/preview/` с обязательными в текущей реализации `plan` и `seats`. Локальные добавления, изменения и удаления вычисляются относительно исходного набора и сохраняются одним запросом:

```json
{
  "expected_version": 7,
  "create": [],
  "update": [],
  "delete": []
}
```

Число 7 здесь — только пример структуры. Код подставляет реальную загруженную версию. Пустое изменение не отправляется. Внутренние `key` и `plan` не попадают в editable payload. Ответ содержит новую version, счётчики и created_ids; после успеха перечитывается канонический серверный набор, включая сброшенные группы соседства.

Доступны нейтральный холст без фона, создание отдельных мест, блоков прямых/изогнутых рядов, начало/шаг нумерации, разделение групп соседства, импорт CSV с предпросмотром, выбор рамкой/Shift, перенос, поворот и отражение выделения, переименование, удаление, фильтры сектор/ряд, список мест, zoom и перемещение холста. Undo/redo хранит до 20 локальных операций; это не история отката уже сохранённых серверных версий.

Блоки строятся **серверным** `block-preview/`, CSV разбирается `csv-preview/`; результат `saved: false` сначала явно добавляется на холст. Только «Сохранить изменения» пишет геометрию в базу. Лимит — 2000 изменяемых мест за запрос, до 50 000 мест в схеме. Блокирующая проверка не разрешает накопить заведомо несохраняемый пакет. Крупные схемы нужно сохранять по блокам; производительность на 50 000 SVG-точках не измерена.

Список поддерживает выбор с клавиатуры и редактирование координат без мыши. Масштабирование колесом — Ctrl/Cmd + колесо, панорамирование — инструмент «Рука», Alt + перетаскивание или средняя кнопка. У панели есть кнопки zoom. Проверки touch/мобильного браузера в реальном Next остаются в ручной приёмке.

При геометрическом изменении/перенумерации очищаются затронутые группы соседства. Новый фон доступен отдельным version-checked upload; он блокируется, пока есть несохранённые места. Опубликованная схема read-only, для изменения есть клонирование. Публикация без фоновой картинки разрешена новым backend, и покупательская схема тоже отображается на нейтральном холсте.

409 сохраняет местный черновик и блокирует перезапись. Доступны экспорт CSV/JSON и явная загрузка актуальной версии. После успешной записи и неудачного последующего GET не выполняется повторная запись старого пакета. При неизвестном исходе POST требуется сверка. Экспорт — выгрузка данных, не уход со страницы: UnsavedGuard больше не перехватывает download-ссылки. CSV включает заголовки `sector,row,number,x,y`, UTF-8 BOM и защиту от формул таблиц; JSON служит резервной копией, автоматический импорт JSON не реализован.

Источники: `backend/venues/{views,editor_api,editor_services,geometry,services}.py`. Старые create-row/Seat endpoints остаются в backend, но новый визуальный редактор не использует их для записи геометрии.

## 4. Ошибки и совместимость

DRF возвращает details как словарь, строку или массив. Раньше массив мог исчезать при нормализации, оставляя только «Проверьте заполненные поля». Теперь сохраняются сообщения полей и вложенные причины, а `request_id` остаётся доступен для поиска в логах. Для 5xx содержимое подробностей не выводится; HTML-ответ 413 распознаётся как слишком большой запрос.

В площадках разрешены неполные импортированные черновики: пустые страна/город/адрес не блокируются локальным required, когда новый сериализатор их допускает. Часовой пояс остаётся отдельным полем.

Старые URL и CSRF не изменены: `/api/v1/me/?lang=ru`, `/api/v1/public/config/?lang=ru`, `/api/v1/auth/csrf/`. Медиа продолжают идти через same-origin `/media/` без принудительного завершающего `/` у имён файлов.

Для импорта и загрузки картинки применяется 90-секундное ограничение ожидания клиента; прочие запросы сохраняют прежний тайм-аут. Это не отменяет тайм-аутов reverse proxy и gunicorn. В поставляемом frontend Nginx-шаблоне read timeout — 65 секунд, как в новом backend-шаблоне. При собственной конфигурации проверьте её отдельно.
