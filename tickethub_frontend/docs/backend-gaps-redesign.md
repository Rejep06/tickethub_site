# Backend gaps и расхождения требований

Основание: чтение исходников приложенного `tickethub_backend_complete(1).zip`, `docs/frontend-api.md`, OpenAPI и serializers/services/views. **Это статический анализ, не результат запуска Django.** Backend-код не изменялся. Ранний `02_FRONTEND(1).md` описывает более широкий продукт; основной текущий запрос предписывает следовать фактическому бэкенду.

## Resolved — неоднозначности контракта, учтённые во фронтенде

| Вопрос | Фактическое поведение и реализация |
| --- | --- |
| Session или JWT | Django session. Все мутации получают CSRF, отправляют credentials. Отдельный staff password login. |
| Можно ли оформлять заказ без онлайн-оплаты | Да. Ориентир — `order_intake_enabled`, не `online_payments_enabled`. Никакой формы банковской карты. |
| Slug или UUID | `events/{slug}/` читает карточку; offers/seat-map/availability используют UUID события. |
| Что резервируется | `checkout/holds/` создаёт Hold на основе реального stock; reload читает Hold по ID. |
| Оформление Order | Идемпотентный POST по `hold_id`; таймер не продолжает управлять уже созданным Order. |
| Quote на непубличное событие | Сведения берутся из авторизованной заявки/Quote, а не попытки открыть приватный Event через публичный каталог. |
| Версия отправки Quote | `expected_version` равна `request_version`, а не коммерческому номеру версии Quote. |
| Возврат | Решение использует версию обращения; settle — `order_version`. `APPROVED` не означает перечисленные деньги. |
| Себестоимость | NULL остаётся неизвестным. `profit_complete=false` не превращается в точную прибыль. |
| Нет выбранных позиций обращения | `item_ids` опускается; пустой массив не отправляется. UI объясняет, что это обращение по всем позициям. |
| Смена email | Подтверждаются оба кода. Сохраняется текущая обновлённая сессия, не изображается logout без запроса к серверу. |
| Роли в `/me/` | Поля роли нет. Доступ staff проверяется настоящим staff endpoint; admin — admin endpoint. UI guard не заменяет серверные permissions. |
| Схема и категории | Используется модель бэкенда: точные места при привязанной схеме, категории без неё. Не изобретается смешанная корзина. |

Эти пункты означают исправление понимания/клиентского кода, **не исправление или проверку работы самого Django**.

## Blocking

### B1. Нет защиты от устаревшей версии для изменения геометрии отдельного Seat

Существуют POST/PATCH/DELETE `staff/seats/` и `staff/plans/{id}/create-row/`, однако сериализаторы этих операций не принимают `expected_version` родительского плана. Изменения плана увеличивают версию; публикация и загрузка изображения проверяют её, но запись геометрии не использует клиентскую версию.

**Следствие:** требование раннего ТЗ «конфликт параллельного редактирования не перезаписывает изменения» не может быть гарантировано клиентом. Редактор поддерживает explicit save, черновики, проверки дубликатов, published read-only, но не выдаёт это за серверный optimistic locking.

**Предлагаемое изменение Django:** `expected_version` для всех операций над геометрией, проверка под транзакционной блокировкой плана, 409 при конфликте. Должны проверяться реальной PostgreSQL два параллельных изменения. До доработки: один редактор на схему; не считать такой организационный порядок технической гарантией.

### B2. Полная приёмка старого frontend-ТЗ невозможна на текущем API

Это не блокирует нынешний MVP с менеджером, но блокирует объявление соответствия старому ТЗ целиком:

- Нет TicketFile API: загрузки, проверки, публикации, отзыва и защищённого скачивания билетов.
- Нет платёжного провайдера, payment attempts, confirmation_url, webhook/return и live-payment readiness.
- Нет интерфейса создания ручного Order для произвольного внешнего канала; фактические origins — SITE_DIRECT и SITE_REQUEST.
- Нет обязательного TOTP/MFA flow.

**Expected** — добавить эти самостоятельные подсистемы на бэкенде, а не эмулировать их клиентом. **Current** — ручные платежи и фактические отметки отправки по email. Они честно отображаются в UI. Настоящий финансовый перевод эта панель не выполняет.

## Non-blocking — ограничения и предусмотренные обходы

| Недостающая возможность | Что сделано вместо выдуманного endpoint |
| --- | --- |
| Public price, availability, country filters; category kind/hierarchy expansion | Отправляются только реальные q/category/venue/participant/city/date/status/ordering. Категорийные ссылки используют реальные ID; нет ложного параметра `kind=sport`. |
| Staff orders filters payment/delivery/overdue | Отдельные состояния показываются в строках; фильтруются только поддерживаемые поля. Счётчик просрочек честно ведёт на общий список, не на фиктивно отфильтрованный. |
| Staff order email-search | Поиск списка заказов — номер; email ищется в поддерживаемом customer endpoint, далее переход к заказам по user ID. |
| Customer detail/aggregated spend/history of requests | Список контактов и переход к заказам. Не высчитывается «всего потрачено» из одной страницы. |
| Bulk-create TicketUnit | Создание единицы через реальный endpoint. Массовое добавление ряда Seat есть и использует create-row. Это разные операции. |
| Featured/popularity management | Главная показывает ближайшие настоящие события, спорт раньше других; не подписывает случайную подборку «популярное». |
| Writable runtime settings API | Только read-only страница для администратора. Изменения через env и deployment Django. |
| Серверный список допустимых действий | UX-подсказки по status/составу; окончательный результат определяет services/permissions с version/409. Кнопка не гарантирует, что за время между загрузкой и запросом состояние не изменилось. |
| Детальные чужие статусы мест | Публичное API возвращает продаваемые места. Остальные — «Нет доступного предложения», без заявления «организатор продал» и без данных чужих клиентов. |
| Ссылка Hold → созданный Order | При `CONVERTED` предлагается история заказов. Угаданный ID заказа не подставляется. |
| Отдельное API profit на карточке заказа | Отображаются продажи/получено/возвраты/стоимости. Агрегированный результат — только из analytics. |

## Отдельно: ограничения проверки и самого фронтенда

Не являются backend gaps: недоступный npm registry, отсутствующие локальные Django/PostgreSQL/Docker, отсутствие package-lock, отсутствие выполненного build/E2E. Они перечислены в `verification.md`.

Текущие frontend-ограничения: справочники категорий/площадок публичных фильтров загружаются первой страницей до 100; reference picker сотрудника ищет внутри текущей страницы и позволяет переходить по страницам; нет полного browser QA, Lighthouse/WCAG-аудита, lossless восстановления незавершённых финансовых форм с ПД после закрытия вкладки. Неоднозначный идемпотентный результат блокирует новую отличающуюся операцию до сверки, а не автоматически сбрасывает ключ.
