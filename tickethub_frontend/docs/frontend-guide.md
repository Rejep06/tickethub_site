# Руководство по фронтенду Tickethub

## 1. Как ориентироваться в проекте

```text
src/app/                  страницы и layout Next.js
src/app/[locale]/         RU/EN и вложенная русская staff-панель
src/components/           общий layout, providers и UI
src/features/catalog/     главная, каталог, событие, аналитика просмотра
src/features/auth/        вход и guards
src/features/seat-map/    выбор точных мест и список
src/features/checkout/    preview, Hold, contacts, Order
src/features/requests/    клиентская заявка
src/features/account/     заказы, заявки, Quote, профиль
src/features/staff/       управление проектом
src/lib/api/              HTTP-клиент, DTO, группировка вызовов
src/lib/                  деньги, время, черновики, геометрия
src/i18n/                 локализация
src/messages/             ru.json и en.json
src/styles/globals.css    общий визуальный язык и responsive правила
```

Файл `app/.../page.tsx` обычно небольшой: получает параметры URL, выбирает feature-компонент и задаёт metadata. Не размещайте там десятки fetch и всю финансовую логику. Бизнес-правила остаются в Django.

## 2. Маршруты

Публичные: `/{locale}`, `/events`, `/events/{slug}`, `/sports`, `/concerts`, `/other`, `/request`, `/login`, информационные `/about`, `/how-it-works`, `/contacts`, `/faq`, `/legal/{slug}`. Префикс `locale` всегда ru или en.

Покупатель: `/checkout`, `/account`, `/account/orders`, `/account/orders/{id}`, `/account/requests`, `/account/requests/{id}`, `/account/profile`. Checkout восстанавливается через query `hold`, `event` либо `request`. `event` — slug для публичной карточки, `request` нужен для Quote на непубличное событие.

Рабочая панель: `/ru/staff/login`, `/dashboard`, `/orders`, `/orders/{id}`, `/requests`, `/requests/{id}`, `/refunds`, `/refunds/{id}`, `/analytics`, `/customers`, `/notifications`. Повторяющиеся сущности обслуживает `resources.ts`: events, venues, seating-plans, offers, tickets, suppliers, categories, participants, team, content. Редактор схемы: `/ru/staff/seating-plans/{id}/editor`. Администратору доступны также settings и privacy.

Параметр ID — реальный UUID. Не заменяйте его slug «для красоты», если backend endpoint принимает UUID.

## 3. Публичный рендеринг и картинки

Server Components получают каталог/событие через `publicApi` из `api/server.ts` и передают initial data клиентской части. Нет клиентской fake database. Неперсональные GET используют внутренний адрес Django; cookies клиентов туда не копируются, потому что это публичные запросы.

`mediaPath` допускает только настоящие пути `/media/`, а абсолютный URL этого media приводит к same-origin. Так development proxy и production Nginx одинаково обслуживают изображения. Тексты API не вставляются через `dangerouslySetInnerHTML`; произвольный SVG из загрузки не исполняется. Изображения событий используют Next Image в unoptimized-режиме: не утверждается наличие настроенного image CDN.

Если API недоступно, страница показывает ошибку/retry, а не «нет мероприятий». Отсутствующая афиша — placeholder, не другой матч под видом нужного.

## 4. Локализация

`useT()` возвращает next-intl translator, `useLang()` — ru/en. В `ru.json` и `en.json` совпадают ключи. Добавляя строку, сразу заполните обе локали и запустите `npm run check:translations`. Форматы сумм используют одну валюту RUB. Backend-тексты берутся из соответствующего `_ru`/`_en`; fallback названия на RU не означает автоматический перевод юридических условий.

Динамические business error/status keys перечислены в словарях; неизвестный ответ не должен раскрывать stack trace. Staff-тексты в этой версии русские.

## 5. Общие UI-компоненты

`components/ui/index.tsx`: кнопки, inputs, select/textarea, checkbox, field/error, card, badge/status, skeleton, empty/error, native modal/confirm, pagination и tabs. `Field` связывает label с input и aria-describedby с подсказкой/ошибкой. Для составного reference picker применяется fieldset/legend.

Кнопки финансов блокируются во время запроса. `useTask` дополнительно использует синхронную ref-блокировку: два клика до очередного React render не запускают две локальные операции. Реальную защиту от повторения обеспечивает Django idempotency, а не disabled-кнопка.

`UnsavedGuard` предупреждает при закрытии страницы и обычном переходе по ссылке с грязной формой. Полноценный перехват браузерного Back этим компонентом не гарантируется. Native dialog даёт основу keyboard/focus поведения; проверка Safari/screen reader остаётся частью релизной приёмки.

## 6. API, session и CSRF

```ts
import {api} from '@/lib/api/client';
import type {Order} from '@/lib/api/generated';
const order = await api<Order>(`orders/${id}/`);
```

`api` добавляет `/api/v1/`, credentials, язык, request ID, timeout, no-store. Перед изменяющим запросом получает `auth/csrf/` и передаёт `X-CSRFToken`. Это важно после login: Django может сменить CSRF, поэтому устаревший токен не считается постоянным.

Ошибка имеет `ApiError.status`, `code`, `details`, `requestId`, `retryAfter`. Используйте ErrorState для общего сообщения и FieldErrors для поля. 409 не означает «повторять бесконечно»: свежие данные требуют решения пользователя. 500/HTML ответа не показываются клиенту как traceback.

`authApi` объединяет OTP, staff login, `/me/`, профиль и logout. Доступность staff проверяется backend permission probe, поскольку `/me/` не выдаёт role. ADMIN-интерфейс не открывается по значениям localStorage/query. Backend остаётся единственным средством защиты данных.

При успешном входе/выходе QueryClient очищается. Если logout не дошёл до Django, UI не делает вид, что серверная сессия уничтожена.

## 7. Каталог и выбор

Каталог хранит поддерживаемые фильтры в URL. Поиск имеет задержку 300 мс; предыдущий fetch получает AbortSignal. Справочники публичного UI ограничены 100 первыми записями — это сознательно обозначенное ограничение реализации, не ограничение размера основного каталога. Основная выдача постраничная.

Event читает offers, seat-map, availability. Availability обновляется каждые 10 секунд при видимой секции, при фокусе вкладки и после конфликта. Карта содержит фон и кнопки с координатами 0..1. Отдельный список позволяет выбирать без мыши; сектор/ряд фильтруются. Серые места не названы «продано организатором»: сервер знает только предложения Tickethub.

Выбор — локальный черновик, не Hold. `drafts.ts` сохраняет только eventId, slug, selection, createdAt. После возврата из login данные перечитываются. Изменение цены требует явного подтверждения; исчезнувшее место не заменяется автоматически. Соседство подтверждается только явной adjacency_group/position, не близостью точек на картинке.

## 8. Checkout и неопределённый результат запроса

Последовательность: проверить профиль → `checkout/preview/` → показать состав/цену → `checkout/holds/` → сохранить ID в URL → `orders/` с hold_id и согласиями. Нет самостоятельного выставления PAID.

`HoldClock` рассчитывает остаток от server_now/expires_at и монотонного `performance.now()`. Изменение часов устройства не продлевает резерв. При reload загружается серверный Hold; истечение блокирует submit даже после закрытия окна уведомления.

`api/attempts.ts` сохраняет ключ попытки и хэш канонического тела. При одинаковом повторе используется прежний ключ. При network/5xx ключ сохраняется; при изменении тела операция блокируется до выяснения результата. После подтверждённого успеха ключ очищается. Исчезновение модального окна не отменяет уже принятый сервером запрос.

`pending-hold.ts` сохраняет неперсональный payload незавершённого reserve: иначе после потери ответа новый preview мог бы увидеть собственные места как уже занятые. Восстановление повторяет **тот же** idempotent запрос. Для завершённого Hold сервер отвечает CONVERTED; UI ведёт к истории заказов.

Согласия хранят точный номер версии документа; прежняя галочка не принимается автоматически за согласие с новой редакцией.

## 9. Заявки, Quote и кабинет

`request-form.tsx` принимает существующее либо отсутствующее событие, контакты, количество, бюджет и пожелания. Бюджет переводится из рублей в копейки. Запрос на подбор не означает наличие/резерв. Состояние заявки и публичный ответ читаются с backend.

Quote показывает состав, цену и срок. Принятие вызывает `quotes/{id}/start-checkout/`, а результатом является Hold. Для непубличного события используются данные Quote, доступные владельцу заявки, без обхода публичных permissions.

Order detail показывает обработку, оплату и отправку отдельно. Timeline строится из настоящей history, не из предполагаемых пройденных этапов. Частичная отправка считается по OrderItems, не по числу файлов. Файлового API нет — UI сообщает о ручной email-доставке, не создаёт fake download.

Обращение по возврату не обещает автоматический возврат. Пустой выбор позиций явно означает все позиции, а не пустой запрещённый список. Email change использует коды старого и нового адреса; текущий серверный сеанс обновляется, остальные завершаются согласно Django.

## 10. Staff: CRUD и специальные действия

`resources.ts` описывает обычные поля и endpoint. `resource-page.tsx` делает список/форму, а `fields.tsx` — выбор связанных UUID с пагинацией. Reference picker фильтрует текущую страницу: подпись не обещает глобальный поиск, которого endpoint не поддерживает.

Версия записи фиксируется при открытии формы. Новый refetch не заменяет её молча поверх несохранённых полей. `expected_version` отправляется только для сущностей/операций, где это поддерживается. Публикация, блокировка и другие статусные действия отдельны от обычного PATCH.

`order-detail.tsx` хранит снимок Order при открытии модалки. Действия сначала показывают подтверждение, затем ждут ответа Django. Для денег: сумма в копейках, метод, обязательная reference, фактическая дата, заметка. Это учёт уже произошедшей операции, а не команда банку. Для отправки: только выбранные действительно отправленные позиции, разрешённый email, фактическое время, ID письма по желанию.

`refunds.tsx`: decision по версии Case; settle по версии Order. Одобрение и выплата разные действия. Сторно исправляет учёт; оно не заменяет возврат денег клиенту.

## 11. Редактор схем

Площадка → черновик схемы → разрешённое изображение → точки/ряд → явное сохранение → публикация. При drag координаты определяются по фактическому размеру отображённого изображения. Ряд задаётся концами/номерами, предпросматривается и отправляется через create-row. Adjacency задаётся явно.

Published-схема read-only, изменения делаются в копии. Добавить точку не означает создать TicketUnit или продать билет. Единицы привязываются отдельно к опубликованному Seat. Backend gap защиты от параллельного изменения геометрии описан отдельно: клиент его не скрывает.

## 12. Аналитика

Dashboard, sales, cashflow, funnel и export используют реальный API. Даты периода явно UTC, верхняя граница исключается. Когорты продаж и движение денег различаются. UI не считает итоговую прибыль по текущей странице заказов. При неизвестных закупках нет ложного нуля и ложной точной прибыли.

Client analytics отправляет только EVENT_VIEW, TICKETS_VIEW, TICKET_SELECTED, CHECKOUT_STARTED при разрешённой конфигурации и согласии. PAYMENT_RECEIVED и прочие бизнес-события формирует Django. Контакты, свободные комментарии и содержимое финансовых форм туда не передаются.

## 13. Добавление страницы или API

1. Сначала найдите endpoint и serializer в Django. Проверьте права, money units, nullability, pagination, версию и idempotency.
2. Обновите `docs/backend-openapi.json` из настоящей схемы; выполните `npm run generate:api`. Не редактируйте generated.ts руками.
3. Добавьте небольшой вызов в `api/endpoints.ts` или отдельный domain-модуль; используйте общий api client.
4. Сделайте feature-компонент с loading/error/empty, сохранением input и явным подтверждением опасного действия.
5. Подключите его через page.tsx, задайте metadata/noindex и добавьте переводы.
6. Добавьте unit/компонентный тест; проверьте запрос на отдельном настоящем backend. После этого build/lint/typecheck и браузерные сценарии.

Для финансов сначала разберите возможные состояния «запрос не дошёл / сервер выполнил, но ответ потерян». Не добавляйте retry с новым UUID как универсальное исправление сетевой ошибки.
