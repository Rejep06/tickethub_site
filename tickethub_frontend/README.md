# Tickethub — frontend для backend с PortalBilet и пакетным редактором

Обновление от 7 октября 2026 под `tickethub_portalbilet_editor_partial(1).zip`: административный импорт по ссылке, version-checked редактор схем, явная загрузка обложки при создании/редактировании мероприятия и конкретные ошибки полей. **Установка поверх редизайна:** [UPDATE.md](UPDATE.md). Сохраняйте `.env.local`, `package-lock.json`, `node_modules` и свои исходные изменения. Новые зависимости не добавлены. Подробные возможности, ограничения и источники контрактов — [docs/backend-update.md](docs/backend-update.md).

**Фактически выполнено:** 182 автономных теста (0 ошибок), строгая компиляция 20 самостоятельных модулей, 30 сверок исходного API-контракта, 458 совпадающих ключей переводов, проверка синтаксиса/локальных импортов 126 TS/TSX-файлов. **Не подтверждены:** production build, полный typecheck/lint, 38 компонентных и 10 E2E-тестов, работа Next с Django/PostgreSQL и реальным PortalBilet. ## 1. Что именно реализует этот MVP

Каталог и карточки событий читаются на сервере Next.js. Интерактивные части: места и категории, актуальность наличия, OTP, серверный резерв, оформление заказа, заявки и персональные предложения. Кабинет показывает отдельные состояния обработки, оплаты и отправки, историю, обращения и профиль.

Staff: заказы и допустимые действия, ручной журнал денег и сторно, частичная отправка, возвраты с раздельными одобрением/фактической выплатой, заявки/Quote, события, площадки, категории, участники, предложения, единицы билетов, поставщики, клиенты, изображения/обложки, пакетный редактор мест/блоков/CSV, публикация/копирование схем, аналитика/CSV/воронки. Администратор дополнительно импортирует черновики мероприятий PortalBilet, управляет сотрудниками и версиями контента, просматривает настройки и обращения по данным.

**Оформление заказа не означает онлайн-оплату.** Приложенный бэкенд использует ручную работу менеджера. В нём нет платёжного провайдера, загрузки/хранения TicketFile и выдачи файлов через кабинет. Поэтому отсутствуют формы банковской карты, фиктивная кнопка оплаты и неработающая кнопка скачивания билетов.

После успешного создания Order checkout-резерв заканчивается, а единицы остаются `ORDER_HELD` до действий менеджера. Таймер не должен продолжать отменять уже созданный Order.

## 2. Требования и структура папок

Рекомендуемая локальная версия Node — **24** (`.nvmrc`), npm 10+. В `package.json` указаны Next.js 16.3.8, React/React DOM 19.3.0, TypeScript 5.9.3 и совместимые диапазоны остальных библиотек. Доступная здесь Node 22.16 использовалась только для автономных проверок.

Расположите проекты рядом:

```text
workspace/
  tickethub/                 # распакованный backend
    backend/manage.py
    compose.yaml
  tickethub_frontend/        # этот проект
    package.json
    src/
```

Не создавайте папку `backend` внутри фронтенда. Не переносите файлы из исходного ZIP бэкенда поверх Next.js.

## 3. Запуск Django

В корне **бэкенда** `tickethub/`:

```bash
python3 scripts/create_local_env.py
```

В созданном `.env` сохраните случайные секреты и установите:

```dotenv
SITE_URL=http://localhost:3000
DJANGO_CSRF_TRUSTED_ORIGINS=http://localhost:8000,http://127.0.0.1:8000,http://localhost:3000
```

Локально `EMAIL_BACKEND=django.core.mail.backends.console.EmailBackend` выводит OTP в консоль Django. На production нужен настроенный SMTP. Не используйте console email для реальных клиентов.

```bash
docker compose config --quiet
docker compose build api
docker compose up -d --wait db
docker compose run --rm api python manage.py makemigrations --check --dry-run
docker compose run --rm api python manage.py migrate
docker compose run --rm api python manage.py check
docker compose run --rm api python manage.py createsuperuser
docker compose run --rm api python manage.py seed_demo
docker compose up -d api
```

При ошибке миграций остановитесь и исправьте её на отдельной тестовой базе. Не используйте `--fake` как способ пропустить проблему. Детали запуска, cron, писем и резервов находятся в README и `docs/production.md` **приложенного бэкенда**.

`seed_demo` добавляет `demo-seats` и `demo-category`; не создаёт известный пароль. Повторный seed не восстанавливает проданные билеты и не переносит прошедшие даты. Для повторного E2E используйте отдельную одноразовую базу, а не рабочие заказы.

Проверка API:

```text
http://localhost:8000/health/ready/
http://localhost:8000/api/v1/events/
```

## 4. Запуск фронтенда

В другом терминале, из `tickethub_frontend/`:

```bash
# Linux / macOS / WSL с установленным nvm
nvm install
nvm use
cp .env.example .env.local
npm install
npm run dev
```

PowerShell, когда Node уже установлен:

```powershell
Copy-Item .env.example .env.local
npm install
npm run dev
```

Содержимое `.env.local` для этого расположения:

```dotenv
NEXT_PUBLIC_APP_URL=http://localhost:3000
BACKEND_ORIGIN=http://127.0.0.1:8000
API_INTERNAL_URL=http://127.0.0.1:8000/api/v1/
```

Браузер обращается **к `localhost:3000/api/v1/`**, а Next проксирует запросы в Django. Не меняйте browser API на `localhost:8000`: это меняет origin и усложняет cookies/CSRF. Не смешивайте `localhost` и `127.0.0.1` в адресной строке браузера. Backend origin может оставаться `127.0.0.1`.

Откройте:

```text
http://localhost:3000/ru/
http://localhost:3000/en/
http://localhost:3000/ru/events/demo-seats
http://localhost:3000/ru/events/demo-category
http://localhost:3000/ru/account
http://localhost:3000/ru/staff/login
```

Корень `/` использует сохранённый RU/EN, иначе RU. Рабочая панель канонически находится в `/ru/staff`; `/staff` перенаправляется туда. `/en/staff/...` тоже переходит в русскую панель. Django Admin остаётся отдельно на `localhost:8000/ops/`.

### Вход покупателя

Откройте `/ru/login`, введите свой email, запросите код. В отдельном терминале бэкенда:

```bash
docker compose logs -f api
```

Найдите письмо для введённого email и введите свежие шесть цифр. Коды не сохраняются во фронтенд-хранилище. Не отправляйте логи с действующими кодами другим людям.

### Вход сотрудника

Откройте `/ru/staff/login` и используйте email/пароль из `createsuperuser`. Создание менеджера — раздел «Команда» у администратора или технический Django Admin. Email-код покупателя не заменяет парольный staff-вход. Для параллельного тестирования покупателя и сотрудника используйте разные браузерные профили.

## 5. Быстрый ручной сценарий

На чистой локальной базе откройте `demo-category`, выберите предложение и количество, продолжите оформление. Войдите, заполните имя и международный телефон, прочитайте документы, проверьте предварительную сумму. Подтвердите резерв; таймер берётся из `expires_at` и `server_now`. Обновление страницы загружает существующий Hold, а не создаёт новый.

Оформите заказ. В кабинете он должен оставаться неоплаченным, пока сотрудник не зафиксирует реальное поступление. В отдельном staff-профиле откройте заказ, возьмите в работу и подтвердите. Запишите **только тестовую операцию в одноразовой базе**, затем отметьте отправку выбранных позиций. При четырёх билетах и двух отмеченных отправках должны различаться `PARTIALLY_SENT` и полный `SENT`.

Для схем: «Площадки» → создать площадку → «Схемы мест» → создать черновик → загрузить разрешённое изображение → редактор → точки/ряды → публикация → привязка к событию → предложения и единицы билетов.

## 6. Команды проверки

```bash
npm run generate:api
npm run check:translations
npm run check:source
npm run typecheck
npm run lint
npm test
npm run test:components
npm run build
npm start
```

`npm test` — автономные domain/API-client тесты, а не браузер и не Django. `npm run check:source` — только синтаксис/локальные импорты. Эти команды **не заменяют** `typecheck`, `lint` и `build` с настоящими зависимостями.

Для браузерных тестов:

```bash
npx playwright install chromium
npm run test:e2e
```

Должны уже работать Next.js и отдельный Django с demo-данными. Два E2E-теста чтения не меняют базу. Два сценария с записью требуют явного `E2E_ALLOW_WRITES=1` и настроек из [testing.md](docs/testing.md). Они не должны запускаться на production.

### Lock-файл

`package-lock.json` намеренно не выдуман: registry не был доступен. На машине с интернетом выполните `npm install`, сохраните полученный lock в Git, затем повторите установку через `npm ci` и все проверки. До этого воспроизводимая сборка не подтверждена. Dockerfile и CI специально требуют реальный lock-файл.
