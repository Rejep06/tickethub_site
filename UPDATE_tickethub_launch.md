# Обновление Tickethub: каталог, категории и запуск

20.10.2026. Основа patch — **ваш последний `tickethub.zip` из этого сообщения**, а не один из старых архивов ассистента. Обновляются **frontend и backend**. Новый deployment лежит в корне рядом с обеими папками.

## Перед заменой файлов

Сохраните копию текущих исходников, `.env`, `.env.local`, базы и папки media. Не удаляйте Docker-volumes, не используйте `docker compose down -v`. Ваши `package-lock.json`, `node_modules`, база, загруженные изображения и реальные env-файлы в patch не заменяются. Новых JavaScript-зависимостей нет.

Если после отправки архива вы меняли эти же исходники, сначала сравните их с patch. `LAUNCH_MANIFEST.json` содержит исходную SHA-256 архива, список изменений и их хеши. Это не автоматический merge.

**Обязательно прочитайте про миграцию ниже:** часть импортированных мероприятий будет снята с публикации, но не удалена.

## Установка локально: Windows + уже работающий Docker backend

1. Остановите frontend через Ctrl+C. Временно прекратите действия менеджеров и покупателей.
2. В папке `tickethub_backend` сохраните дамп базы. Для существующего локального compose с сервисом `db`:

```powershell
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc --no-owner --no-acl -f /tmp/before-launch-update.dump'
docker compose cp db:/tmp/before-launch-update.dump .\before-launch-update.dump
```

Скопируйте также `tickethub_backend\backend\media` и текущие env-файлы в приватное резервное место. Дамп не нужно отправлять в чат. Если ваши сервисы названы иначе, сначала посмотрите `docker compose ps` и используйте их настоящие имена.

3. Остановите локальный API, но не базу:

```powershell
docker compose stop api
```

4. Распакуйте patch в каталог, где находятся **обе** папки `tickethub_backend` и `tickethub_frontend`. Согласитесь на замену перечисленных исходников. Не создавайте лишний уровень `tickethub_frontend\tickethub_frontend`.
5. Из папки `tickethub_backend` примените миграции одноразовым контейнером:

```powershell
docker compose run --rm api python manage.py migrate
docker compose run --rm api python manage.py seed_categories
docker compose up -d api
```

Существующий backend использует bind mount `./backend:/app`, поэтому новый код доступен контейнеру без пересборки Python-зависимостей. Для другой вашей конфигурации с кодом внутри образа потребуется `docker compose build api` перед миграциями.

6. Из папки `tickethub_frontend`:

```powershell
Remove-Item -Recurse -Force .next -ErrorAction SilentlyContinue
npm run dev
```

Повторный `npm install` не нужен для уже установленного проекта с тем же `package-lock.json`. Для новой папки сначала выполните `npm ci` на компьютере с доступом к npm и 64-битным Node.

7. Откройте сайт, обновите страницу Ctrl+F5. Проверьте каталог, главную, категории, загрузку обложки категории, вход и сохранение мероприятия.

Если backend запускается без Docker: активируйте своё окружение, из `tickethub_backend/backend` выполните `python manage.py migrate`, `python manage.py seed_categories` и перезапустите сервер.

## Что именно делает миграция

`events.0004_category_images_publication`:

- добавляет категории фото, поля прав использования, `is_placeholder` и `version`;
- помечает служебную `external-review` неактивной и служебной;
- снимает с публикации уже опубликованные события с этой категорией, шаблонами `{name}`, `{city-in}`, `{phone}` или остатками инструкции покупки на Portalbilet;
- увеличивает версию снятого с публикации события;
- не удаляет мероприятия, схемы, билеты, заказы, фотографии и историю;
- при откате миграции **не публикует их автоматически обратно**.

Сначала резервная копия. После обновления менеджер должен выбрать настоящую категорию, проверить текст и остальные условия и опубликовать событие заново. Если после этого шага главная пока пуста, проверьте не только код, но и список опубликованных записей: миграция могла правильно убрать единственное непроверенное событие.

## Категории и фотографии

`/ru/staff/categories` → создать или открыть категорию → сохранить основные поля → «Фото категории».

Тип: SPORT / CONCERT / OTHER; родитель — необязательное поле для подкатегории. Можно загрузить файл или прямую HTTPS-ссылку, подтвердив источник и права. Фото сохраняется локально тем же безопасным обработчиком, что обложка события. Endpoint:

```text
POST /api/v1/staff/categories/{id}/image/
```

Ссылка передаётся JSON (`image_url`, `rights_source`, `rights_confirmed`, `expected_version`), файл — multipart (`image`, остальные поля). Лимиты сохранены: PNG/JPEG/WebP до 100 МиБ, SVG до 10 МиБ, стороны до 20 000 px, площадь до 300 МП. Проверяет сервер. Для быстрой страницы категории лучше использовать отдельное веб-фото, а не оригинал схемы на 300 МП.

На `/sports`, `/concerts`, `/other` теперь есть карточки категорий с фотографиями и подборка настоящих событий раздела. Если фото не добавлено, показывается нейтральная иконка, а не случайная фотография. Для дерева категорий преимущественно показываются конкретные конечные подкатегории; родитель остаётся в фильтре каталога.

`seed_categories` добавляет недостающие реальные категории, но не переименовывает ваши существующие категории, не назначает категории импортированным событиям наугад и не создаёт demo-события.

## Что исправлено

- Главная запрашивает до шести событий из того же публичного каталога, что афиша. Убран скрытый отсев по текущей дате. Вкладки запрашивают SPORT/CONCERT/OTHER у backend, а не фильтруют случайную загруженную страницу.
- Служебные/выключенные категории скрываются вместе с их дочерними категориями из публичного API. Сервер отклоняет публикацию с такой категорией, шаблонным описанием или инструкцией покупки на Portalbilet. Интерфейс показывает список проблем до публикации.
- Исходные тексты не «чистятся» незаметно: менеджер редактирует их, чтобы не потерять смысл и реальные сведения.
- Галочка аналитики убрана со страницы события. Без явного согласия необязательные клиентские события не отправляются. При включённой функции настройки открываются в подвале. Production по умолчанию `CLIENT_ANALYTICS_ENABLED=false`.
- Наклонённые LIVE/YOUR MOMENT, декоративный штрихкод и `th.` заменены спокойным блоком с настоящим логотипом; поправлены мобильная компоновка, фотографии категорий и отступы описания.
- Явный UTC задан в next-intl request config и клиентском provider. Время мероприятия по-прежнему форматируется в timezone площадки, не заменяется временем UTC на экране.
- В `<html>` добавлен `data-scroll-behavior="smooth"`; создан реальный favicon и Apple touch icon из исходного знака.
- Предыдущие исправления Canvas-карты, обработки импортированных мест и загрузки изображений сохранены. Код viewport/editor не переписывался в этом обновлении.

## Проверки перед запуском

```powershell
# В frontend
npm run typecheck
npm run lint
npm test
npm run test:components
npm run build

# В backend
docker compose exec api python manage.py check
docker compose exec api python manage.py makemigrations --check --dry-run
docker compose exec api python manage.py catalog_audit --strict
```

Backend API-тесты лучше запускать на отдельной тестовой базе. В корне подготовлен `compose.check.yml`, не подключённый к рабочему volume. Не запускайте тесты с настройками production-базы.

`catalog_audit --strict` ничего не исправляет сам: он перечисляет проблемы опубликованных событий, demo-записи, пропущенные обложки и просроченные даты. При отсутствии готового каталога или блокирующих проблемах возвращает ненулевой код.

**Развёртывание на VPS:** откройте `DEPLOY_tickethub.md` в корне — там DNS, Docker, env, SMTP, база/media, HTTPS, продление сертификатов, резервные копии, обновление и восстановление. Используйте новый корневой `compose.production.yml`, а не прежний backend-only compose.

**Статус проверки:** прочитайте `VERIFICATION_tickethub_launch.md`. Полная сборка и новая интеграция с Django в среде подготовки не подтверждены. Исторические отчёты внутри frontend описывают предыдущие версии, не текущий релиз.
