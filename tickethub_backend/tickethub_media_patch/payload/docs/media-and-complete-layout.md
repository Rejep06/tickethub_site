# Tickethub: большие изображения, SVG, ссылка вместо файла и все места схемы

## Состав изменения

Патч устанавливается поверх PortalBilet verified patch v2 и исправлений из переписки. Никаких новых Django apps, Celery, Redis или Python-зависимостей. Используются установленный Pillow, Django и стандартная библиотека Python.

Изображения мероприятий и фоны схем используют один обработчик `core/image_processing.py`. Скачивание по ссылке вынесено в небольшой `core/image_urls.py`; существующий `core/validation.py` связывает их с Django. `ImageField` в моделях сохраняется, поэтому миграция для изображений не нужна. В формах/DRF используется `FileField` + общая проверка: стандартная предварительная проверка `ImageField` иначе отвергла бы SVG до нашего обработчика.

## Лимиты

| Что | Лимит |
|---|---|
| Каждая сторона растра | 20 000 px включительно |
| Площадь растра | 300 000 000 пикселей включительно |
| Размер входного и обработанного PNG/JPEG/WebP | 100 МиБ |
| Статический SVG | 10 МиБ, до 100 000 XML-элементов |
| Размер холста SVG | До 20 000 px по стороне, площадь до 300 МП |
| Схема | До 50 000 точек |

Оба геометрических ограничения применяются одновременно: 20 000 × 15 000 проходит, 20 000 × 20 000 — нет, поскольку это 400 МП. Размер файла в байтах и количество пикселей — разные ограничения. SVG — вектор; для него проверяется объявленный размер холста, а не декодируются 300 миллионов пикселей.

Растры не уменьшаются. RGB сохраняется в JPEG, прозрачные изображения — в PNG с сохранением прозрачности. Метаданные EXIF и прочие необязательные данные не переносятся; ориентация EXIF применяется к пикселям. Это не побайтовое сохранение исходного файла. Анимация не поддерживается.

Pillow сохраняет конечную защиту `MAX_IMAGE_PIXELS=300_000_000`; она не отключается. Загрузка больших изображений требует памяти. Реальная проверка RGB JPEG 20 000 × 15 000 в среде разработки потребовала около 1 237 МиБ максимального RSS. Это результат одного прогона, не гарантия для PNG/альфа-канала или нескольких параллельных запросов. Не загружайте несколько гигантских изображений одновременно на малом сервере; держите Pillow и системные декодеры обновлёнными.

## В Admin

Откройте мероприятие либо карточку схемы. Появятся:

- «Изображение»: выбрать PNG, JPEG, WebP или SVG;
- «Или ссылка на изображение»: вставить прямую HTTPS-ссылку.

Передаётся одно из двух. Указание и файла, и ссылки одновременно отклоняется. Ссылка на HTML-страницу вместо файла также отклоняется. Для замены изображения достаточно вставить новую ссылку, существующая картинка не считается новым файловым вводом. Ссылка скачивается сервером, проверяется тем же обработчиком и сохраняется как локальный файл с UUID-именем. Постоянного hotlink на произвольный сайт нет, URL входного запроса не добавляется в публичную модель.

Поля подтверждения основания использования изображения остаются. Это не автоматическое предоставление прав на чужую картинку. Локальная картинка схемы имеет приоритет над `external_background_url`, а последующая синхронизация PortalBilet не переписывает поле `image`.

Опубликованная схема по-прежнему защищена. Для смены её фона сначала создайте копию. Фото мероприятия изменяется через обычную версионную операцию.

## REST API

Существующие адреса не меняются, завершающий `/` сохраняется:

```text
POST /api/v1/staff/events/{id}/image/
POST /api/v1/staff/plans/{id}/image/
```

Файл: `multipart/form-data` с `image`, `expected_version`, `rights_source`, `rights_confirmed`.

Ссылка: `application/json`:

```json
{
  "image_url": "https://cdn.pbilet.com/origin/your-image.svg",
  "expected_version": 3,
  "rights_source": "Основание использования изображения",
  "rights_confirmed": true
}
```

URL выше показывает формат запроса, это не существующий демонстрационный файл. Необходимо подставить реальную прямую ссылку и актуальную версию объекта. Ответ — прежняя карточка мероприятия/схемы, `image` указывает на локальный файл. Авторизация — существующая staff session + CSRF. Клиент не может вызвать скачивание.

Ссылки допускаются только по HTTPS на публичные адреса, порт 443. Запрещены localhost, приватные/служебные адреса, данные авторизации в URL и опасные схемы. Проверяется каждый редирект и DNS-ответ; TLS-соединение открывается именно на проверенный IP с проверкой исходного имени сертификата. Прокси из окружения, cookies и заголовки авторизации не используются. Нужна сетевая доступность источника из контейнера; для production дополнительно полезно ограничить исходящий доступ сетевыми правилами.

## SVG

Принимается статическое подмножество SVG: фигуры, группы, пути, текст, градиенты, простые CSS-классы/id и clipPath. SVG разбирается и собирается заново. Скрипты, обработчики `on*`, `foreignObject`, внешние ссылки, DTD/ENTITY, анимация, встроенные/внешние `<image>`, `<use>` и сложные CSS-конструкции запрещены. Такой файл возвращает понятную ошибку, а не хранится непроверенным.

Это не полный редактор всех вариантов SVG. Для неподдерживаемого документа экспортируйте статический SVG с текстом/символами в путях либо PNG. SVG не вставляется в HTML как доверенная разметка. В клиенте используйте `<img src="...">`, а не `innerHTML`, `<object>` или `<iframe>`.

## Все места PortalBilet

В приложенном capture:

- `coordinates`: 12 075 физических точек;
- `tickets` даты 402328: 2 109 подписанных доступных билетов;
- 9 966 точек в этом capture не имеют подписей с сектором/рядом/номером.

Отсутствие билета в `tickets` не доказывает, что кресло продано: это может быть бронь, закрытый сектор, квота или отсутствие предложения. Код не присваивает фиктивный статус SOLD.

Теперь `apply_layout()` создаёт запись `Seat` для КАЖДОЙ точки `coordinates`, не дожидаясь `tickets`. Цена и наличие по-прежнему не являются частью геометрии.

У неизвестного места:

```json
{
  "sector": "",
  "row": "",
  "number": "",
  "labels_known": false,
  "external_point_key": "стабильный локальный ключ точки",
  "x": "0.057207",
  "y": "0.676316"
}
```

Это пример формата, не выдуманная подпись конкретного кресла. Ключ строится из нормализованных координат внутри конкретной схемы: источник не предоставил официальный ID этих физических точек. При конфликте подписи или координат код сохраняет существующую связь и пишет предупреждение; не переносит билет на другое кресло по догадке.

Когда для точки появился билет, обновляются подписи ТОГО ЖЕ `Seat`; UUID не меняется. Повторный импорт не создаёт копии. Если билет исчез из текущего наличия, `Seat` и ранее полученные подписи сохраняются, внешнее наличие становится `False`. `enabled_for_sale` не сбрасывается. `TicketUnit` из внешнего наличия автоматически не создаётся.

Новые ограничения PostgreSQL:

- уникальна подписанная комбинация «схема + сектор + ряд + место»;
- уникальна «схема + external_point_key»;
- подписи либо заполнены все три, либо все три пустые и есть внешний ключ точки;
- ручное создание без подписей и создание продаваемого `TicketUnit` на неизвестную точку запрещены.

Старый JSON `external_geometry` сохраняется для совместимости. Теперь список `seats` тоже содержит все точки — frontend не обязан самостоятельно превращать geometry_points в кресла.

### Редактор и public frontend

Django-редактор отрисовывает все `Seat`. Серый цвет означает отсутствие подписи, НЕ подтверждённую продажу. Синий означает известную подпись, НЕ наличие собственного билета. Всплывающая подсказка объясняет неизвестные поля. Одинаковые точки не рисуются второй раз поверх слоя геометрии.

Импортированные координаты защищены от случайного ручного сдвига: изменение координат разрушило бы связь с источником. Для ручной правки подписанных мест создайте копию. Копия сохраняет всю геометрию, но отключена от PortalBilet sync. Неизвестным местам номера не придумываются. CSV экспортирует подписанные места; неизвестная геометрия остаётся в API/БД.

В отдельном Next.js отображайте ВСЕ `seat-map.seats`, а не только список `availability.available_seats`:

```javascript
const availableIds = new Set(availability.available_seats.map(item => item.seat_id));
const visibleSeats = seatMap.seats.map(seat => ({
  ...seat,
  selectable: availability.orderable && seat.labels_known && availableIds.has(seat.id),
}));
```

В этом патче изменён Django-редактор и backend-контракт. Отдельного репозитория Next.js среди исходников патча нет; его фильтрацию при необходимости нужно изменить на стороне frontend.

## Установка без потери локальных изменений

Распакуйте папку `tickethub_media_patch` рядом с `backend` и `compose.yaml`.

```powershell
python .\tickethub_media_patch\apply_patch.py --project . --check
```

Проверка ничего не меняет. Установщик сохраняет предыдущие файлы в `backups/media-layout-...`. `.env`, `compose.yaml`, `events/models.py` и существующая `events/0003` не заменяются. В нескольких файлах меняются только именованные функции/класс `Seat`; остальной локальный код сохраняется. Два старых теста адаптируются к новой семантике полного набора мест и детерминированному выбору проверяемого билета. При неизвестных изменениях рабочих функций установка останавливается, а не затирает их.

Production-конфигурация изменяется точечно: `client_max_body_size 101m` и безопасные заголовки для `/media/` в Nginx; `/tmp` увеличивается с 64m до 512m в `compose.prod.yaml`, иначе временный файл 100 МиБ туда не поместится. Порты, имена проектов, секреты и том PostgreSQL не меняются. Если эти конкретные блоки уже изменены локально, установщик потребует сверку. При других прокси их лимит тела запроса также должен пропускать файл 100 МиБ с multipart-обвязкой.

После успешного `--check`:

```powershell
docker compose stop api
python .\tickethub_media_patch\apply_patch.py --project .
docker compose run --rm api python manage.py makemigrations --check --dry-run
docker compose run --rm api python manage.py migrate --plan
```

Новая миграция только одна:

```text
venues.0005_all_geometry_seats
```

Если проверка миграций обнаружила расхождения, не продолжайте автоматически. Не используйте `--fake` и не удаляйте базу. Перед применением на сервере сделайте обычную резервную копию PostgreSQL и media. После создания неизвестных мест откат старого уникального ограничения на три пустые подписи уже не является безопасным обратным шагом; для отката релиза нужна проверенная резервная копия.

После успешной проверки:

```powershell
docker compose run --rm api python manage.py migrate
docker compose run --rm api python manage.py check
docker compose run --rm api python manage.py test venues external_events core.tests.test_media_inputs --verbosity=2
```

Когда тесты пройдут, восстановите все места для УЖЕ импортированных схем:

```powershell
docker compose run --rm api python manage.py backfill_layout_seats
```

Команда использует сохранённый `external_geometry`, не требует обращения к PortalBilet, не удаляет существующие места/заказы и безопасна при повторном запуске. Совпадающие существующие места получают внешний ключ без смены UUID. На неоднозначной геометрии операция конкретной схемы откатывается с сообщением, а не угадывает связь. Для одной схемы есть `--plan UUID`.

```powershell
docker compose up -d api
```

В development с `./backend:/app` пересборка Python-образа для этих файлов не нужна. Если backend скопирован в образ без bind mount, пересоберите его. Для production также выполните `collectstatic` и обновите Nginx-конфигурацию; Compose с другим именем сервисов использует свои команды. Новые импорты уже создают всю геометрию автоматически.

## Проверки и границы результата

Фактически выполнено в среде автора:

- 27 автономных тестов обработчика изображений и URL: успешно;
- реальная обработка JPEG 20 000 × 15 000, 300 МП: успешно, без уменьшения размеров;
- разбор полного предоставленного capture: 12 075 точек, 2 109 точных совпадений билетов;
- 8 сценариев старого редактора в Chromium с тестовыми ответами API: успешно;
- 4 проверки всей схемы в Chromium: 12 075 нарисованных точек, 9 966 неизвестных подписей, нет повторного слоя и JS-ошибок;
- 7 проверок установщика на временных копиях проекта: успешно, включая сохранение локальных исправлений, резервную копию, повторный запуск и остановку на конфликте;
- синтаксическая компиляция Python и проверка JavaScript.

Добавлено 23 Django/DRF/PostgreSQL-теста: сохранение всей геометрии, повторная синхронизация, сохранение UUID/подписей/локальных флагов, защита неизвестных мест от продажи, public API, файлы и ссылки в Admin/API. В этой среде они НЕ выполнены: Django, DRF и PostgreSQL отсутствуют, две попытки установки зависимостей не завершились. `manage.py check` действительно запускался и остановился на `ModuleNotFoundError: No module named 'django'`.

Проверка Chromium использует подменённый HTTP API; это не проверка работы Django Admin с PostgreSQL. Не выдаём ни миграцию, ни весь backend за полностью проверенные. Журналы находятся в `docs/verification/media-layout/`.
