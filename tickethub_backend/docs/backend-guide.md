# Как устроен backend Tickethub

Эта инструкция объясняет **написанный код**, не подтверждает его запуск. Результаты проверки отдельно в development-report.md; точный HTTP-контракт — frontend-api.md.

## 1. Куда смотреть при изменении функции

`models.py` описывает, какие данные хранятся и какие ограничения видит БД. `serializers.py` определяет входные поля и видимый ответ. `views.py` принимает HTTP-запрос, проверяет доступ и вызывает функцию. `services.py` нужен там, где операция состоит из нескольких согласованных изменений. `admin.py` описывает формы сотрудников. `urls.py` связывает URL с view. `tests/` проверяет поведение приложения.

Пример: пользователь отправил заказ. View проверяет формат и сессию, затем вызывает `orders/services.py → create_order_from_hold`. Эта функция проверяет резерв, создаёт Order/OrderItem, переводит TicketUnit в ORDER_HELD и пишет историю в одной транзакции. Отдельных Repository, command bus или workflow engine нет. Критические операции не скрываются в signals.

Девять apps — части **одного** процесса приложения и одной PostgreSQL. Они импортируют обычные модели/функции друг друга. `core` содержит небольшие общие вещи, но не бизнес-правила продажи.

У моделей, наследующих Record, общие UUID, created_at, updated_at. User отдельно наследует стандартный AbstractUser. Record абстрактный и не создаёт таблицу. В проекте 29 прикладных моделей; стандартные таблицы Django auth/session/admin добавляются самим Django.

Простая цепочка связей:

```text
Venue → SeatingPlan → Seat
Category → Event ← Participants
Event → TicketOffer → TicketUnit ← Supplier
User → CheckoutHold → CheckoutHoldItem → TicketUnit
User → Order → OrderItem → TicketUnit
Order → FinancialEntry / DeliveryRecord / CustomerCase / OrderHistory
User → TicketRequest → Quote → QuoteItem → TicketUnit
Quote → CheckoutHold → Order
```

Order имеет максимум один исходный Hold, Quote принимается максимум одним Order. Исторически один TicketUnit может встречаться в нескольких отменённых заказах, но **одновременно активная OrderItem только одна**. История не удаляется ради повторной продажи.

## 3. Доступность — не отдельный счётчик

В категории с десятью билетами создаются десять TicketUnit. Наличие считается по этим строкам, состояниям, активным заказам и сроку поставщика. Нельзя вручную увеличить available_count, не добавив реальные единицы.

OWNED означает принадлежащий проекту билет; EXCLUSIVE_ALLOCATION — подтверждённое эксклюзивное закрепление до даты. На checkout остаток должен оставаться подтверждённым до конца резерва. Продление поставщика выполняется явной операцией `renew_supplier_allocation`, с подтверждением и причиной. Она **не разблокирует** ранее возвращённый билет.

SEAT требует место схемы этого Event; категория — seat=NULL. Ограничения БД не позволяют создать две единицы на одну пару Event+Seat, два активных Hold одного пользователя/события или две активные OrderItem одного Unit. Межтабличное соответствие схемы и события проверяет сервис под блокировкой.

## 4. Как работает резерв

`tickets/services.py` содержит preview/create_hold/release_hold и проверку доступности. Preview ничего не удерживает. CreateHold рассчитывает состав на сервере, проверяет цену клиента, блокирует выбранные единицы и сохраняет expires_at = серверное время + 600 секунд.

```text
AVAILABLE → CHECKOUT_HELD → ORDER_HELD → SOLD
                    │
                    └ истечение/отказ → AVAILABLE или BLOCKED
```

Повтор просмотра Hold не продлевает срок. Замена выбора сохраняет первоначальный expiry. Когда замена не удалась, транзакция откатывается и старый выбор остаётся у клиента.

Условие истечения всегда проверяется по времени сервера: запись с expires_at в прошлом уже недействительна даже со старым status=ACTIVE в БД. API доступности учитывает это само; следующая операция под блокировкой освобождает старые привязки. Команда cleanup лишь приводит хранимое состояние в порядок.

При создании Order единицы становятся ORDER_HELD, current_hold очищается, а Hold становится CONVERTED. Очистка обрабатывает **только ACTIVE**, поэтому отправленный заказ не теряет билеты через десять минут.

## 5. atomic и select_for_update простыми словами

`transaction.atomic()` означает: «сохранить все изменения вместе либо ни одного». Без него могла бы сохраниться половина заказа: Order существует, но билет остался доступным.

`select_for_update()` означает: «пока меняю эту строку в транзакции, другой процесс не может получить такую же блокировку». Для MVP основной короткий замок — строка Event. Поэтому все изменения его запаса выполняются последовательно. При двух запросах на последнее место первый закрепляет билет, второй после ожидания заново проверяет данные и должен получить 409.

Порядок: клиентские изменения сначала блокируют User, затем Event, затем связанные Hold/Quote/Order и TicketUnit в постоянном порядке. Сотрудники начинают с Event и не берут User после него. Это уменьшает риск циклического ожидания. Точный порядок каждой операции виден в функции, не спрятан в декораторе, кроме atomic.

**Ни база, ни соединение не держат блокировку все десять минут.** Блокировка существует только во время короткого HTTP-сервиса. Десятиминутное состояние хранится в таблице. SMTP вызывается после транзакции, не удерживает замок.

Цена простоты: операции запаса одного популярного Event сериализованы. Производительность здесь не измерена. Позже при необходимости можно сузить блокировки, но сначала нужны измерения и повтор конкурентных тестов.

Важный предел: все приложения/сотрудники должны пользоваться сервисами. Владелец БД с прямым SQL технически может обходить прикладные проверки. Частичные UniqueConstraint остаются дополнительной защитой, но не заменяют услуги сервиса.

## 6. Почему три состояния заказа

Order хранит только order_state: NEW → IN_PROGRESS → CONFIRMED → COMPLETED; отдельно REJECTED/CANCELLED. Клиентский PATCH состояния запрещён. Staff тоже не меняет его произвольно — вызывает start/confirm/cancel/complete.

payment_state вычисляется из FinancialEntry: UNPAID, PARTIAL, PAID, PARTIALLY_REFUNDED, REFUNDED. delivery_state вычисляется по множеству действующих отправленных активных OrderItem: NOT_SENT, PARTIALLY_SENT, SENT.

CONFIRMED + PAID + NOT_SENT нормально: договорились, деньги получили, письма с билетами ещё нет. COMPLETED требует подтверждённого непустого заказа, денег для активных позиций, выдачи всех активных позиций и отсутствия открытой проблемы. Сервис не позволяет просто отметить пустой заказ выполненным.

Версия Order увеличивается после рабочих изменений. `expected_version` предотвращает незаметное сохранение сотрудником устаревшей формы. Это не замена блокировке: версия защищает намерение пользователя, замок — одновременные изменения БД.

## 7. Идемпотентность и повторы

Сервер мог создать Order, но ответ потерялся. Повтор с тем же Idempotency-Key и телом возвращает прежний результат. При том же ключе и другом содержимом — 409. У Order/заявок/денег/выдачи хранятся ключи и хеш запроса; для Hold есть небольшая IdempotencyRecord. Отдельного универсального движка нет.

Функция проверяет повтор **до expected_version**: первый успешный запрос уже увеличил версию, но потерянный ответ всё равно должен повторяться безопасно. Нельзя присылать новый UUID на каждую сетевую попытку.

## 8. Деньги, сторно и неизвестная закупка

`payments/services.py` принимает фактическое поступление, расход, возврат поставщика; клиентский возврат привязан к одобренному Case. Метод BANK_CARD/SBP описывает способ реального внешнего расчёта, а не вызывает банк.

Заказ на 10 000 ₽ и получение 3 000 ₽ дают PARTIAL. Это учёт факта, не продукт «предоплата 30%». При полной сумме и согласованном заказе билеты становятся SOLD.

FinancialEntry нельзя редактировать/удалить через API, модельный save или Admin. Ошибка исправляется новой REVERSAL того же типа и суммы со ссылкой на оригинал и обязательной причиной. После этого можно создать правильную запись. Сторно не может нарушить уже исполненные/одобренные возвраты.

`purchase_price_minor=NULL` сохраняется как неизвестная себестоимость. Отчёт показывает известную часть и profit_minor=null. Уточнение после заказа — `orders/services.py → update_item_cost`, только сотрудник, с версией и причиной. Продажная цена и клиентский снимок при этом не меняются. Внутреннее изменение не отображается клиенту.

## 9. Выдача и возврат

DeliveryRecord фиксирует письмо, **уже отправленное вручную**. Четыре купленных билета, две отмеченные позиции дают 2/4. Ещё одна запись с теми же двумя ID остаётся 2/4. Считается объединение множеств, не количество строк. Ошибочная отметка аннулируется с причиной, не удаляется. Обычная выдача доступна только после полной оплаты.

CustomerCase одновременно хранит запрос и решение; отдельная RefundDecision не требуется. APPROVED означает разрешение, не перевод денег. `record_refund` создаёт настоящий CUSTOMER_REFUND. Исполнение можно отметить частями до одобренной суммы. После полного исполнения выбранные позиции становятся неактивными; ранее отправленный или возвращённый Unit остаётся BLOCKED.

Возвращать BLOCKED в продажу может сотрудник только после проверки действительности билета через unblock с confirmed_valid. Сторно возврата не делает билет активным автоматически. Для безопасной отмены без денег и отправки нужно явное подтверждение отсутствия незавершённых расчётов.

## 10. Подбор и Quote

Request допускает event=NULL, но требует понятное описание/название. Менеджер создаёт Event позже, при необходимости UNLISTED. Доступ к такому событию клиент получает через собственный Quote, а не общий каталог.

Quote содержит реальные проверенные TicketUnit и персональные цены. Отправленная версия не редактируется. Новое предложение отзывает предыдущее и связанные незавершённые резервы. Сама отправка не расходует остаток. На start-checkout наличие проверяется снова; затем работает обычный Hold→Order, не второй тип заказа.

Для пожелания «рядом» используются разметка групп соседства либо явное подтверждение менеджера с понятным условием. Номера 10 и 11 сами по себе не гарантируют отсутствие прохода. Заявка становится CONVERTED, Quote — ACCEPTED только после успешного Order.

## 11. Авторизация, CSRF и права

Customer получает шесть цифр по email. База хранит HMAC кода с случайным nonce, адресом и назначением, а не код. Challenge действует 10 минут, имеет максимум пять ошибок, используется один раз. Общие лимиты отправок/проверок лежат в PostgreSQL и не сбрасываются новым challenge. Ошибки фиксируются до выдачи ошибки HTTP, иначе откат транзакции обнулил бы защиту.

После проверки устанавливается стандартная Django session. Сотрудник входит отдельно по паролю. Даже если у email роль ADMIN, вход через OTP даёт только клиентские возможности. На рабочую панель нужны роль **и парольная сессия**. Staff-сессии ограничены по общему сроку и простою. MFA не обязательна и не реализована в MVP.

CSRF — проверка, что запрос изменения сделан вашим интерфейсом, а не чужой страницей, воспользовавшейся cookie. Frontend получает csrftoken, отправляет X-CSRFToken; после login получает новый. Вход и аналитика проверяют CSRF даже для анонимов. В production session cookie Secure/HttpOnly, один origin через Nginx. JWT не нужен.

Permissions отвечают «кто может вызвать операцию». Queryset по user отвечает «какие объекты ему доступны»: чужой приватный UUID даёт 404. Отдельные публичные и staff-сериализаторы отвечают «какие поля увидит вызывающий». Входные strict-сериализаторы отклоняют неизвестные и read-only поля, включая попытки передать purchase_price или passport_number.

Fan ID хранит только требование, инструкцию и ответ о помощи. Форм документов нет. Произвольный комментарий всё же может содержать лишние сведения: интерфейс должен явно запрещать их отправку, сотрудники — удалять случайно полученное по процедуре инцидента. Код не обещает распознавать любые документы в произвольном тексте.

Смена email требует два кода — на старый и новый адрес. После неё другие сессии отзываются, текущая обновляется. Снимки уже созданных заказов остаются прежними. Email нельзя тихо менять через профиль/Admin действующего пользователя.

## 12. Analytics

Продажи рассчитываются только по SITE_DIRECT/SITE_REQUEST. Создать «внешнюю продажу из Telegram» через этот backend нельзя. Отчёты используют ORM и небольшую понятную агрегацию Python; для MVP это проще, чем отдельная аналитическая БД. Пока нет измеренного предела объёма.

Успешные продажи исключают отменённые заказы. Историческая оплаченная когорта сохраняет оборот и возврат отменённых, cashflow считает фактические даты денег. Средний чек/прибыль объяснены в frontend-api.md. Не смешивайте эти представления.

Frontend может прислать только EVENT_VIEW/TICKETS_VIEW/TICKET_SELECTED/CHECKOUT_STARTED после согласия на аналитику. Заказ/оплату/выдачу создаёт только сервер. В web-воронке важен порядок и уникальный путь; у рабочих milestones должны существовать все предыдущие шаги. Сессия аналитики — отдельный случайный идентификатор, не раскрытая auth-cookie. Корректировки денег не удаляют исторический факт прохождения этапа.

## 13. Email и периодические команды

OTP синхронно отправляется через стандартный email backend, без сохранения открытого кода. Бизнес-письмо сначала получает EmailLog внутри основной транзакции. `transaction.on_commit` отправляет его после успешного commit. Сбой SMTP не отменяет уже принятый заказ. Сотрудник видит FAILED/PENDING и может явно повторить отправку.

Нет автоматического брокера, сложной очереди, бесконечного worker или гарантии exactly once для SMTP. При неоднозначном ответе сервера повтор письма возможен. Восстановление и ответственность за ручной retry описаны в production.md.

Cron может вызывать cleanup_expired_holds, cleanup_expired_quotes, remind_staff и cleanup_auth. Если cron выключен, checkout всё равно проверяет expiry; только напоминания/физическая очистка запаздывают. Deadline обработки заказа сам по себе **не освобождает** билеты.

## 14. Admin не обходной путь

Поля состояния заказов, денег, выдачи и занятого запаса read-only. Действия/формы вызывают те же service functions. MANAGER работает с каталогом/клиентами/заказами; ADMIN дополнительно управляет сотрудниками и контентом. Обычный клиент не входит в Admin. Опубликованный контент/схема имеют ограничения на редактирование.

Не добавляйте admin action с `queryset.update(order_state='COMPLETED')`: он обходит все проверки. Правильно перебрать выбранные ID и вызвать complete_order с текущей версией, показав ошибки формы.

## 15. Как добавить новую функцию

Например, новый срок обработки. Сначала сформулируйте допустимые значения/переходы. Добавьте поле модели только если его нельзя вычислить. Создайте Django migration в работающем окружении и проверьте её на чистой PostgreSQL. Внесите поле во staff input/output, но не автоматически в клиентский ответ. Изменение связанных объектов делайте в сервисе с прежним порядком блокировок. Добавьте позитивный тест, отказ доступа, неправильную версию и граничный случай. Обновите frontend-api и вручную пройдите сценарий.

При последующих изменениях фиксируйте путь файла, причину и точный участок. Небольшой файл удобно показать целиком. Сначала запускайте тесты изменённого app, затем общий verify. Не меняйте уже применённые миграции — добавляйте следующие.

TicketFile позже можно связать с OrderItem. Онлайн-провайдер сможет записывать FinancialEntry через небольшой сервис; created_by уже допускает NULL, но сейчас никакого фальшивого gateway нет. Новые блокировки или очереди добавляются по доказанной необходимости, не ради архитектуры.

## 16. Что именно проверено

Автономные проверки действительно исполняют чистые функции расчётов и проверяют исходники. Они **не** запускают Django ORM. TransactionTestCase для двух соединений написан, но его успех пока не измерен. Handwritten migrations и authored OpenAPI остаются непроверенными runtime-артефактами до запуска verification script.
