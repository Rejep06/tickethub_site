# Часть 1. Бэкенд

**Tickethub — техническое задание, версия 2.0 от 30 сентября 2026 года.** Целевой запуск первой версии: не позднее 31 октября 2026 года, до 1 ноября. Разработка с нуля. Документ описывает требуемый продукт, а не уже реализованные функции.

Это полная актуальная редакция, заменяющая ТЗ версии 1.0. Приоритет имеют последние ответы заказчика: в первой версии принимаются заказы без онлайн-оплаты, их обрабатывают менеджеры; учитываются только продажи сайта. Часть 1 определяет данные, бизнес-правила, права и API; часть 2 — интерфейсы на этом же контракте. При обнаружении противоречия исполнитель фиксирует его в `docs/decisions.md`, а не выбирает молча удобное поведение.

## 1.1. Цель продукта и объём первой версии

Tickethub — сайт заказа билетов преимущественно на спортивные мероприятия, а также на концерты и другие события. Покупатель выбирает имеющееся предложение либо просит менеджера подобрать билеты, включая мероприятие, которого нет в каталоге. Сайт должен быть удобен с телефона и компьютера. Публичный интерфейс и кабинет покупателя — русский и английский; валюта — только RUB. Рабочая панель команды — русский язык.

**Модель MVP:** каталог → выбор места или категории → вход → временный резерв → отправка заказа → работа менеджера → ручной учёт фактической оплаты → ручная отправка файлов по email → история и статусы в кабинете. Сайт не принимает банковские реквизиты покупателя и не списывает деньги. Будущие способы онлайн-оплаты — банковская карта и СБП.

### 1.1.2. Границы MVP и последующих этапов

**Обязательно к приёмке:** каталог RU/EN; поиск и фильтры; площадки и простой редактор схем; учёт подтверждённого наличия; email-вход; личный кабинет; 10-минутный резерв; заказы и заявки; рабочая панель; ручные поступления и возвраты; контроль отправки билетов; Fan ID-инструкции; поставщики, закупочные цены, расходы, дашборд и воронки; уведомления; безопасность, резервные копии, развёртывание и тесты.

**Следующий этап, не условие сдачи MVP:** реальный или тестовый платёжный провайдер, карты/СБП, автоматические платёжные ссылки и фискализация; автоматическая отправка билетов; загрузка билетов в закрытое хранилище и скачивание в кабинете; интеграции с организаторами; импорт/экспорт разметки; расширенная аналитика рекламы.

**Не входит:** приложения iOS/Android, кабинеты поставщиков, продажа билетов пользователями, внешний учёт Авито/Telegram, чат, SMS-вход, программа лояльности, промокоды, несколько валют, 3D-схемы, автоматический сбор чужих сайтов, генерация/подделка билетов или QR-кодов. Сам сайт не проверяет подлинность чужого билета и не гарантирует пропуск на мероприятие программным способом.

Скачивание в кабинете было в ранней версии требований. В настоящем MVP приоритет отдан последнему согласованному процессу ручной отправки по email; интерфейс скачивания и хранение файлов вынесены в следующий этап. Сохраняется отдельный модуль выдачи и связь «заказ — билет — отправка», чтобы не менять модель заказов при расширении.

### 1.1.3. Принятые инженерные значения

Решения ниже выбраны для устранения неоднозначностей, а не выданы за отдельные пожелания заказчика: один заказ — одно событие; до 10 билетов в прямом заказе и до 100 в заявке; вход покупателя по коду на email; отдельный MFA-вход сотрудников; резерв начинается после подтверждения email; срок первичного разбора заказа — 24 часа с контролем просрочки; обычный срок выдачи — за 24 часа до начала. Лимиты и сроки, кроме подтверждённых 10 минут, настраиваются администратором и журналируются. Их изменение не переписывает уже согласованные условия заказа.

## 1.2. Архитектура, стек и репозиторий

Использовать модульный монолит. Единственный источник истины для заказов, цен, наличия и денег — Python-бэкенд и PostgreSQL. Фронтенд не создаёт собственную коммерческую базу и не подтверждает оплату самостоятельно. Для MVP не вводить микросервисы, Kafka, Kubernetes или Elasticsearch.

| Компонент | Решение |
| --- | --- |
| Бэкенд | Python 3.13, Django 5.2 LTS, совместимая стабильная Django REST Framework |
| База данных | PostgreSQL 17, `pg_trgm` для поиска |
| Фоновые задачи | Celery + Redis; Redis не хранит единственный экземпляр резервов |
| API | REST JSON, `/api/v1/`, OpenAPI через drf-spectacular |
| Сервер приложения | Gunicorn за Nginx; не использовать development server в production |
| Фронтенд | Next.js App Router + React + TypeScript + Tailwind CSS |
| Окружения | Docker Compose; отдельные local, staging, production |
| Почта | Адаптер транзакционного SMTP; local — почтовый перехватчик |
| Тесты | pytest/pytest-django, PostgreSQL для транзакций, Playwright для E2E |

Django 5.2 официально обозначен LTS-релизом и поддерживает выбранную ветку Python [S01]. Конкретные исправленные версии зависимостей закрепить в lock-файлах в начале разработки, проверить совместимость и актуальные предупреждения безопасности перед релизом. Не фиксировать заведомо устаревшую patch-версию из примера и не использовать `latest` в релизных Docker-образах. Использование Next.js с TypeScript, Tailwind и App Router соответствует его официальной документации [S02].

Модули Django: `accounts`, `catalog`, `venues`, `inventory`, `ticket_requests`, `orders`, `finance`, `delivery`, `notifications`, `analytics`, `audit`, `content`, `payments`. Не называть локальный модуль `requests`, чтобы не конфликтовать с одноимённой библиотекой. Коммерческие изменения — явные сервисные функции, не скрытая цепочка сигналов моделей.

```text
tickethub/
  backend/                 # код Django, миграции, тесты
  frontend/                # Next.js, переводы, компоненты, E2E
  infra/                   # Docker, Nginx, backup/restore
  docs/
    01_BACKEND.md
    02_FRONTEND.md
    openapi.yaml           # сгенерированная из реализации схема
    decisions.md
    runbook.md
  compose.yaml
  compose.prod.yaml
  .env.example
  README.md
```

Один origin: Nginx направляет `/api/v1/` в Django, `/ops/` — в защищённый технический Django Admin, публичные страницы и `/ru/staff/` — в Next.js. Админка `/ops/` не должна обходить сервисные проверки: коммерческие модели там read-only либо используют те же операции. Не включать wildcard CORS с cookie; локальные origin разрешать явно.

## 1.4. Общие правила данных

Наружные идентификаторы — UUID. Номер заказа для человека — `TH-2026-000123`, заявки — `TR-2026-000123`; номера не секреты доступа. Все datetime — timezone-aware UTC, API использует ISO 8601. У площадки хранится IANA timezone; время мероприятия показывается как местное время площадки. Часовой пояс отчётов по умолчанию `Europe/Moscow` с видимой подписью.

Деньги — целые копейки (`*_minor`, bigint), `currency=RUB`, без float. Пример: 5 500 ₽ = `550000`. Суммы цен и расходов неотрицательны; коррекции имеют отдельное направление и ссылку на исходную запись. Неизвестная закупочная стоимость — NULL, а не ноль. Подтверждённая нулевая себестоимость требует явного действия сотрудника.

Снимки в заказе: событие, дата на момент оформления, площадка, место/категория, цена, условия выдачи и редакции документов. Текущие сведения о переносе события доступны отдельно. Изменение карточки не меняет исторический заказ. Заказы, деньги, выдачи и связанные справочники архивируются, не удаляются кнопкой Delete.

Для изменяемых рабочих объектов — `version` с оптимистической блокировкой. Изменение с устаревшим `expected_version` возвращает 409 `VERSION_CONFLICT`. Все действия, влияющие на деньги, выдачу и наличие, дополнительно защищены транзакциями. Клиентские поля неизвестного назначения отвергать, а не передавать в модель через массовое присваивание.

## 1.6. Вход, регистрация и сессии

Покупатель смотрит каталог без аккаунта. При оформлении открывается единый экран «Войти или зарегистрироваться»: email → шестизначный одноразовый код. Новый аккаунт создаётся после успешной проверки и необходимых подтверждений документов. Отдельный пароль для покупателя не нужен. Выбор сохраняется, но до серверного резерва место не закреплено.

При отключённом PUBLIC_FORMS_ENABLED существующий покупатель всё равно может войти для доступа к истории/обращениям; создание нового аккаунта запрещено. Ответ OTP-запроса остаётся одинаковым для существующего и неизвестного адреса, чтобы не раскрывать наличие аккаунта.

Код действует 10 минут, одноразовый, криптографически случайный. Хранить HMAC, а не открытый код; потребление и счётчик попыток атомарны. Не более 5 ошибочных попыток на challenge; повторная отправка не чаще 60 секунд, до 5 за час на email, до 30 за час на IP. Общий лимит ошибок на email/IP не обнуляется выдачей нового challenge. Новый код делает старый недействительным. Числа — стартовые эксплуатационные настройки; мониторить ложные блокировки общих сетей.

Ответ запроса кода не раскрывает, существует ли аккаунт. Не логировать код и содержимое авторизационных запросов. Использовать отдельную очередь для OTP. Рекомендации по ограничению попыток, MFA и безопасным ответам см. [S03].

Сессии Django: HttpOnly, Secure, SameSite=Lax; CSRF для всех изменяющих браузерных запросов, включая вход/выход. До первого POST фронтенд получает CSRF-cookie. Сессия покупателя до 30 дней; выход/блокировка отзывает серверную сессию. Не хранить токены в localStorage. Redirect `next` — только разрешённый относительный путь того же сайта.

Сотрудники входят отдельно с паролем и TOTP, резервные коды хешируются. Staff-сессия до 8 часов, бездействие до 30 минут. Вход через покупательский email-код не выдаёт MFA-признак и не открывает `/staff` или `/ops`. Сброс MFA — администратором после проверки личности; начальный администратор создаётся консольной командой, без дефолтного пароля.

Имя — 1–100 символов, телефон — международный формат E.164, не только российская маска; допустимость проверяется библиотекой, но факт владения телефоном не подтверждается SMS. Email заказа в MVP совпадает с подтверждённым email аккаунта. Смена email требует подтверждения старого/нового адреса и отзывает другие сессии; email уже созданного заказа не меняется молча. Изменение адреса доставки для действующего заказа подтверждается клиентом, проходит через менеджера и записывается в аудит.

## 1.7. Каталог, публикация и Fan ID

Событие имеет независимые признаки публикации и жизненного цикла. `Event.status`: SCHEDULED, POSTPONED, CANCELLED, FINISHED. Перенос с неизвестной датой — `date_tba=true`, `starts_at=NULL`; не подставлять фиктивную дату.

Для публикации нужны RU/EN названия и описание, категория, площадка и её timezone, дата либо явное «Уточняется», условия выдачи, статус требования Fan ID и разрешённая обложка либо нейтральная заглушка. Прямой заказ доступен только у SCHEDULED с точным временем и подтверждённым запасом до `sales_cutoff_at`. По умолчанию прекращение заказов за 2 часа до начала; изменяется с проверкой выполнимости выдачи.

Карточки отменённых/прошедших событий остаются по прямой ссылке и в истории, но не дают создать новый заказ. При переносе/отмене остановить новые резервы, освободить незавершённые checkout-резервы; существующие заказы, деньги и закреплённые билеты не отменять автоматически — создать задачи менеджеру. Изменение даты порождает уведомление и новый срок выдачи с историей.

Поиск 2–100 символов по RU/EN названию, команде/исполнителю, площадке. Фильтры: категория, вид спорта, город/страна, даты, диапазон доступных цен, наличие/подбор. Сортировки: ближайшая дата, цена вверх/вниз. Стабильная пагинация: 24, максимум 100; NULL-цены в конце. Минимальная цена вычисляется только по доступным предложениям, не по проданному самому дешёвому билету. «По запросу» не равно нулю.

**Fan ID задаётся на уровне события**, а не для всех спортивных мероприятий разом: `REQUIRED`, `NOT_REQUIRED`, `TO_BE_CONFIRMED`. Менеджер указывает проверенный источник условия и дату проверки. При REQUIRED показать предупреждение на событии, checkout и в заказе; спросить «Карта уже есть / Нужна помощь / Не уверен». При нескольких билетах вопрос относится ко всей группе: «Карты есть у всех / Нужна помощь хотя бы одному / Не уверен». Это самооценка клиента, не проверка подлинности. При TO_BE_CONFIRMED разрешать только запрос менеджеру, без прямого заказа на неизвестных условиях прохода.

Tickethub сопровождает и инструктирует. Не запрашивать паспорт, номер карты, фото, логин, пароль и коды Госуслуг. В формах нет соответствующих полей и вложений. Свободный комментарий предупреждает не присылать документы; случайно полученные лишние данные удаляются по процедуре обработки инцидента.

Важно отличать PDF билета от права прохода: для мероприятий с картой болельщика может требоваться назначение билета зрителю и QR-код в официальном кабинете. Официальная инструкция РФС описывает этот процесс [S05]. Менеджер должен проверить допустимый способ передачи конкретного предложения; файл из письма нельзя универсально объявлять достаточным для входа. Сайт не интегрируется с Госуслугами и не выполняет назначение автоматически. Если передача невозможна без отсутствующей интеграции или сбора запрещённых для MVP данных, предложение публикуется только как подбор до решения процесса.

## 1.8. Схемы площадок и подтверждённое наличие

Схема: PNG/JPEG/WebP-фон плюс слой собственных точек. Ручной редактор позволяет добавить место, указать сектор/ряд/номер, передвинуть/удалить в черновике, создать ряд по двум точкам с явной нумерацией и проверить дубликаты. Координаты нормализованы относительно исходного изображения, не viewport. Публикация фиксирует версию. Футбол и концерт на той же арене могут иметь разные планы.

Опубликованный план не редактируется на месте: изменения — новая версия. План события можно заменить только до возникновения любого checkout-резерва или заказа; после — через отдельную согласованную миграцию и проверку менеджером, не через простую кнопку. Исправление проданного места требует согласия покупателя и аудита.

Изображения загружаются командой, не скачиваются сервером по произвольному URL. Сохраняется источник и подтверждение основания использования. Наличие изображения на другом сайте само по себе не заменяет это подтверждение; не использовать hotlink, обход защиты и удаление водяных знаков. При отсутствии подходящей схемы событие остаётся в категорийном режиме. Технические ограничения загрузки см. 1.20.

Для первой версии поддержать до 5 000 размеченных мест на одном плане; допустимо размечать только продаваемые места. Не отмечать все прочие места как проданные: это «Нет предложения Tickethub». Публичная схема не выдаёт внутренние unit IDs для чужих заказов, клиентов или поставщиков.

`stock_basis`: OWNED либо EXCLUSIVE_ALLOCATION с действующим `allocation_until`. Только такие единицы могут стать AVAILABLE. Неэксклюзивное сообщение поставщика «есть билеты» — REQUEST, не доступный остаток. При просрочке закрепления незанятый unit блокируется, действующий заказ получает инцидент и проверку, но не исчезает.

Сайт не синхронизирует остатки внешних каналов. Чтобы избежать двойной продажи, запас, выставленный AVAILABLE на сайте, должен быть реально выделен для него. Изъятие из запаса — «Снять с продажи» с причиной, не создание внешней продажи в аналитике. Занятый unit нельзя снять/переиспользовать без урегулирования заказа.

Перед созданием Hold проверить, что срок эксклюзивного закрепления поставщиком покрывает все 10 минут оформления. Недостаточный срок означает подбор/проверку менеджером. Перед подтверждением заказа менеджер проверяет достаточность закрепления для исполнения.

Состояния `stock_state`: AVAILABLE, CHECKOUT_HELD, ORDER_HELD, SOLD, BLOCKED. Одно активное Allocation на unit. AVAILABLE не имеет активного Allocation; CHECKOUT_HELD связан с активным CheckoutHold; ORDER_HELD/SOLD — с OrderItem. Возврат денег не переводит автоматически SOLD в AVAILABLE: сначала BLOCKED и отдельная проверка возможности повторной продажи.

## 1.9. Цены, временный резерв и отправка заказа

### 1.9.1. Цена

В MVP дополнительные сборы не вводятся: `total_minor = Σ(price_minor выбранных единиц)`. Отображается полная цена для клиента. Наценка входит в цену; закупочная стоимость внутренняя. Нет платных дополнений, скрытых комиссий и клиентского выбора предоплаты.

Расчёт делает сервер. `POST /checkout/preview` проверяет состав и возвращает версии и расчёт без резерва. При создании резерва передаются эти версии; изменение цены даёт 409 `PRICE_CHANGED` и требует повторного согласия. После резерва его цена фиксирована до истечения. При отправке заказа фиксируется снимок. Менеджер не переписывает цену принятого заказа молча; коммерческие изменения проходят через согласованную отмену неоплаченного заказа и новое оформление клиентом по правилам 1.11.

### 1.9.2. Семантика 10 минут в MVP без оплаты

10 минут — срок завершить форму и отправить заказ. Таймер создаётся на сервере только после входа и нажатия «Перейти к оформлению». Просмотр схемы и локальный выбор не резервируют билет. Код входа также действует 10 минут, но это независимый таймер.

После успешного `POST /checkout/holds` возвращаются `server_now`, `expires_at`, итог и выбранные единицы. Если клиент не отправил заказ вовремя, Hold истекает; при отсутствии иных связей единицы снова AVAILABLE. Сервер проверяет время независимо от фонового worker. Обновление страницы и повторный запрос не продлевают резерв. Один активный Hold на пользователя и событие; смена выбора заменяет его атомарно без скрытого продления исходного срока.

**Отправка заказа до истечения Hold атомарно превращает временный резерв в закрепление за заказом:** Hold → CONVERTED, units → ORDER_HELD, создаются Order/OrderItems. 10-минутный таймер больше не применяется к отправленному заказу. Клиент видит «Заказ получен, менеджер свяжется с вами», а не «Оплачено» или «Билет отправлен».

По умолчанию устанавливается `review_due_at = min(created_at + 24 часа, sales_cutoff_at)`. Это внутренний срок разбора, а не публичная гарантия ответа. При просрочке заказ подсвечивается, администратор получает задачу; закрепление не снимается автоматически, потому что менеджер уже мог договориться об оплате вне сайта. После связи менеджер задаёт `settlement_due_at` и следующее действие. Просрочка этого срока тоже требует проверки, а не автоматического освобождения. Освободить запас можно после подтверждения отсутствия незавершённых расчётов и отмены/отклонения заказа с причиной.

Нельзя оставлять заказы бесконтрольно заблокированными: отдельная очередь «Просрочен разбор/расчёт», ежедневный контроль и напоминания обязательны. Не более одного активного необработанного заказа покупателя на событие; дубликат возвращает ссылку на существующий заказ. Изменения состава проходят через менеджера.

### 1.9.3. Атомарность и конкуренция

Использовать PostgreSQL-транзакции и блокировку строк. Для масштаба MVP допустима короткая сериализация изменений наличия на Event. Единый порядок: Event → Hold/Order/Quote → TicketUnits по UUID → Allocation/проводки. Внешние SMTP/API-вызовы внутри блокировки запрещены. Поведение `select_for_update` и конкурентные тесты проверять на PostgreSQL, а не SQLite [S04].

```text
submit_order(user, hold_id, contact, legal_versions, idempotency_key):
  verify request hash for idempotency_key
  transaction:
    lock event, hold and selected units
    ensure hold belongs to user and is ACTIVE
    ensure server_now < hold.expires_at
    verify event accepts orders, stock and conditions are still valid
    verify contacts and current mandatory legal versions
    create order, item snapshots and operational deadlines
    change each allocation: checkout hold -> order item
    mark units ORDER_HELD and hold CONVERTED
    write history, business event, notification into durable outbox
  return the same order for repeated successful requests
```

Идемпотентность обязательна для создания Hold/заказа/заявки, принятия Quote, финансов и выдачи. Ключ scoped к пользователю и операции; повтор с тем же телом возвращает тот же результат, с другим телом — 409 `IDEMPOTENCY_CONFLICT`. Коммерческий результат с ключом хранится вместе с объектом, не только кратковременно в Redis.

Категория резервирует конкретные N единиц внутри сервера. Недостаток хотя бы одной — отказ всей операции, без неожиданного частичного заказа. Одновременные запросы одного последнего места приводят ровно к одному успеху. Нельзя подменять выбранное место другим без согласия.

Соседство не выводится только из последовательных номеров. Для обещания «места рядом» нужны проверенные adjacency_group/position без прохода между местами. При неизвестной геометрии — «Соседство уточнит менеджер». `together_required` в подборе — обязательное условие; менеджер не снимает его автоматически.

## 1.10. Заявки на подбор и предложения

Заявку создаёт зарегистрированный покупатель. Контакты обязательны. Для события из каталога сохраняются event, желаемая категория, количество, условие мест рядом, бюджет на все билеты и комментарий. Для отсутствующего события обязательны описание желаемого события и количество; город/дата могут уточняться. Лимит текста 2 000 символов; никаких вложений документов.

Состояния Request: NEW → IN_PROGRESS → OFFERED → CONVERTED; закрытие CANCELLED либо REJECTED. Менеджер назначает себя, фиксирует первый контакт, следующее действие и причину закрытия. Заявка не резервирует запас и не является продажей. Заказы из таких заявок имеют origin SITE_REQUEST; исходная заявка сохраняется для воронки.

Quote содержит конкретное событие, состав, цену в RUB, условия прохода/выдачи, проверенное наличие и срок действия. По умолчанию 24 часа, но не дольше доступности поставщика и закрытия заказов. DRAFT редактируется; SENT неизменяем, новая редакция отзывает старую. Само предложение не резервирует запас: это явно написано клиенту.

Принятие Quote в кабинете проверяет версию, наличие и условия; создаёт 10-минутный Hold по цене Quote и ведёт к обычной форме заказа. Quote остаётся SENT до отправки заказа, чтобы незавершённый Hold не считался продажей. Отправка атомарно переводит Quote в ACCEPTED и Request в CONVERTED; повтор даёт тот же заказ. Истёкший Quote → EXPIRED, заявка возвращается IN_PROGRESS. Если клиент отказался от варианта, менеджер продолжает подбор либо закрывает заявку с причиной.

Отсутствующее событие сначала создаётся менеджером с `visibility=UNLISTED` как непубличная карточка с полными условиями и разрешёнными данными. Доступ к такому событию и предложению — только владельцу заявки и сотрудникам; оно не попадает в каталог, sitemap и общий поиск. Публикация в каталог — отдельное действие. Для UNLISTED заказ разрешён только владельцу действующего Quote и при выполнении всех остальных проверок; обычный прямой вызов с event_id без Quote не открывает доступ.

## 1.11. Жизненный цикл заказа

Состояния обработки, денег и выдачи независимы. API возвращает все три, а также `display_status`, `attention_reasons` и `allowed_actions`. Фронтенд не решает переходы только по красивому тексту.

| Ось | Состояния и смысл |
| --- | --- |
| `order_state` | NEW, IN_PROGRESS, CONFIRMED, COMPLETED, REJECTED, CANCELLED |
| `payment_state` | UNPAID, PARTIAL, PAID, PARTIALLY_REFUNDED, REFUNDED; вычисляется из подтверждённых проводок |
| `delivery_state` | NOT_SENT, PARTIALLY_SENT, SENT; вычисляется по активным DeliveryRecord и активным позициям |
| `attention_reasons` | Набор причин: просрочка связи/оплаты/выдачи, проблема Fan ID, возврат, перенос, потеря наличия, финансовое расхождение |

NEW — заказ поступил; IN_PROGRESS — взят сотрудником. CONFIRMED — клиент и менеджер согласовали исполнение, это не означает оплату. COMPLETED — всё согласованное исполнено, все активные билеты отправлены, денежное обязательство урегулировано, незакрытых обращений нет. Посещение события само по себе не отслеживается.

REJECTED допустим до начала исполнения и при отсутствии поступлений. CANCELLED — после согласованной отмены; возврат денег может ещё находиться в обработке, что отдельно видно в payment/refund состояниях. Нельзя установить REJECTED при полученных деньгах, чтобы скрыть обязательство возврата.

Сотрудник выполняет отдельные команды: взять в работу, назначить, отметить контакт, подтвердить, записать поступление, отметить отправку, предложить изменение, рассмотреть обращение, отменить, завершить. Общий PATCH произвольного `status=PAID` запрещён. Каждое действие фиксирует actor/time/reason и выполняет валидацию.

При нуле активных позиций не считать заказ автоматически SENT или COMPLETED: показывать отмену и денежные обязательства.

Поступление полной согласованной суммы закрепляет units как SOLD; деньги до подтверждения условий создают инцидент, а не автоматическое признание продажи. При частичном фактическом поступлении units остаются закреплены, но сайт не предлагает предоплату и не допускает обычную отправку билетов до полной оплаты. Особые коммерческие договорённости не автоматизируются и не выдаются за правило сайта.

В MVP состав и согласованная цена созданного заказа неизменяемы. Изменение до оплаты: менеджер согласует отмену, фиксирует подтверждение клиента и причину; старый неоплаченный заказ отменяется, клиент оформляет новый через обычный checkout. Старый и новый заказы связываются `replacement_of`; факт согласия сохраняется в публичной истории. Для подбора выпускается новая версия Quote той же исходной заявки. До отмены менеджер предупреждает, что прежнее место не гарантируется после освобождения; обещание атомарной замены не даётся. Сложный редактор OrderRevision не реализуется. После любого поступления существенная замена требует урегулирования денег/возврата и нового оформления; оплаченный снимок не правится. В аналитике замена выделяется причиной, не выдаётся за двух новых клиентов; продажи считаются по реально оплаченным заказам.

## 1.12. Ручной учёт оплаты и будущая интеграция

### 1.12.1. Что реализуется сейчас

Менеджер фиксирует только реально состоявшийся приход: сумма, дата/время фактического получения, способ BANK_CARD/SBP/BANK_TRANSFER/OTHER, подтверждающий reference и внутренний комментарий. Не хранить PAN, CVV, банковские пароли или изображения карты. Изменение статуса по словам клиента «Я оплатил» запрещено: это задача проверить поступление, не проводка.

Финансовая запись отделена от заказа и имеет аудит. Повтор запроса не дублирует приход. Опубликованные записи не редактируются/удаляются; ошибка исправляется обратной записью с причиной и корректной новой записью. Нельзя сторнировать приход так, чтобы возникли необеспеченные уже исполненные возвраты без отдельного урегулирования.

В стандартном процессе сумма записи не превышает непогашенную сумму заказа; переплата, платёж по отменённому заказу или неидентифицированный перевод — отдельный инцидент администратору, не автоматическая дополнительная выручка. До сверки статус «Требуется проверка», подтверждение полной оплаты не выдумывается. Нет кошелька, баланса клиента и сценария автоматических частичных платежей.

Проводки агрегируются с учётом направления: NORMAL прибавляет, REVERSAL вычитает соответствующий тип. Исходная запись остаётся в расчёте вместе с её обратной записью; не исключать её дополнительно, иначе возникнет двойное сторно. Повторное сторно одной суммы ограничено ещё не сторнированным остатком.

При отсутствии инцидента payment_state рассчитывается в таком приоритете: refunded > 0 и net_received = 0 → REFUNDED; refunded > 0 и net_received > 0 → PARTIALLY_REFUNDED; refunded = 0 и received = total → PAID; 0 < received < total → PARTIAL; received = 0 → UNPAID. Несогласованные отрицательные/избыточные значения не принимаются в обычном процессе и создают задачу сверки. Исправление ошибочной проводки отличается от настоящего возврата: ошибочный факт оплаты исключается из отчёта с аудитом коррекции, а реальная оплата с последующим возвратом сохраняет исторический first_paid_at.

Суммы `received_minor`, `refunded_minor`, `net_received_minor` возвращаются клиенту без внутренних расходов. У заказа с возвратом отображаются исходная сумма, подтверждённые поступления/возвраты и оставшаяся к возврату согласованная сумма. Размер обязательства после частичной отмены определяется утверждённым решением, не механическим сравнением с первоначальным total.

### 1.12.2. Что предусмотреть, но не подключать в MVP

Интерфейс `PaymentGateway`: create_payment, get_payment, cancel_payment, create_refund, get_refund, parse_notification. В MVP выбран `DisabledGateway`: создающие операции возвращают 409 `ONLINE_PAYMENT_DISABLED`. Секретов реального магазина и фиктивной sandbox-кнопки в production нет.

В следующем этапе добавляются PaymentAttempt и ProviderRefund с уникальным external ID, идемпотентными ключами и проверкой суммы/валюты/заказа по серверным данным. Успешный возврат браузера не доказывает оплату. Вебхук проходит проверку по правилам провайдера, при необходимости — серверный запрос актуального состояния. Формат взаимодействия и ключи идемпотентности, например, описаны в документации ЮKassa [S08]; конкретный провайдер пока не выбран.

В режиме онлайн-оплаты 10 минут могут использоваться как срок начала/завершения платёжного checkout. Нельзя освобождать билет по таймеру при UNKNOWN/PENDING платеже, который ещё способен списать деньги: сначала сверка и подтверждённое завершение. Это требование следующего этапа, а не обязанность реализовать эквайринг до 1 ноября.

Оформление продавца, договорная модель, реальный приём денег, чеки и правомерность распространения билетов — внешний допуск. Техническая кнопка «Отметить поступление» не заменяет юридическое оформление деятельности и не является рекомендацией принимать деньги на личную карту.

## 1.13. Отмены, возвраты и обращения

Клиент подаёт запрос из своего заказа либо обращается по опубликованным контактам. Сайт регистрирует CustomerCase, номер и дату; повторное открытое обращение того же типа по тем же позициям не дублируется. Самостоятельного мгновенного денежного возврата в MVP нет. Менеджер видит причину, связывается с клиентом, фиксирует решение и публичный ответ.

Состояния обращения: NEW, IN_PROGRESS, NEED_INFO, APPROVED, REJECTED, CLOSED. Отдельно состояние возврата APPROVED/SETTLED. APPROVED не увеличивает `refunded_minor`; деньги считаются возвращёнными только после записи фактически выполненного возврата. Частичный возврат допускается с конкретной суммой и позициями. Повторные/одновременные операции не превышают доступные подтверждённые поступления за вычетом исполненных и уже согласованных незавершённых возвратов.

Спортивные мероприятия: организационный маршрут «обращение к менеджеру». Это не формула «возврат исключительно по желанию менеджера» и не исключение обязательных прав клиента. Концерты/другие события: `return_policy_state=PENDING_REVIEW` до согласования; форма обращения остаётся доступна. Нельзя подставлять «Билеты невозвратные» вместо отсутствующих правил. Официальные разъяснения Роспотребнадзора указывают специальные правила для культурно-зрелищных мероприятий [S06]; применимость к конкретному договору проверяет заказчик с профильным специалистом.

Для публичной карточки можно показать, что условия уточняются, и принимать запрос на подбор. Отправку прямого коммерческого заказа по событию с неутверждёнными существенными условиями блокировать с понятным предложением связаться с менеджером. Возвратная политика сохраняется версией в заказе; смена политики не применяется задним числом.

При отмене мероприятия создать задачи по всем незакрытым заказам; не отмечать автоматом возврат, выдачу или завершение. Возвращённый/ранее высланный билет блокируется для повторной продажи до явного подтверждения его валидности и возможности передачи новым клиентам. Отправленный файл нельзя «отозвать» из почтового ящика одной сменой статуса.

## 1.14. Ручная отправка билетов и контроль срока

Файлы в MVP отправляет человек из рабочего почтового ящика. Приложение ведёт задания и записи отправок, но не получает доступ к личной почте и не прикрепляет билет автоматически. Обязательный рабочий email принадлежит проекту; клиентские письма не отправляются из технического `no-reply`, если нужен ответ менеджеру.

По умолчанию `delivery_due_at = starts_at - 24 часа`. На странице до заказа показывается точный срок на языке клиента. Если заказ оформляется менее чем за сутки до события, стандартное обещание уже невыполнимо. По умолчанию такой прямой заказ отключён; доступна срочная заявка. Менеджер может разрешить поздние заказы только с новым конкретным будущим сроком выдачи до начала и явным уведомлением клиента.

У заказа могут быть несколько отправок. Для каждой менеджер выбирает конкретные OrderItem, подтверждённый email, время и необязательный ID письма. Система не позволяет дважды увеличить счётчик выданных позиций одной отправкой. «Повторно отправлено» создаёт дополнительную запись/событие, но не ещё один проданный или выданный билет.

Кнопка «Отметить отправку» означает уже состоявшуюся отправку, не «планирую отправить». Не ставить SENT при постановке задачи или при автоматическом письме «Ваш заказ получен». Ошибочную отметку аннулируют с причиной; история сохраняется. Зафиксированный факт ручной отправки не доказывает доставку/прочтение: при возврате письма создаётся DELIVERY_ISSUE, клиенту доступно обращение «Не получил билет».

Кабинет показывает «Отправлено 2 из 4 билетов», email назначения, дату и инструкцию проверить входящие/спам. Кнопки «Скачать» нет, пока сервер не поддерживает реальный закрытый файл. Для Fan ID выводится отдельная инструкция о проходе и необходимых действиях; отправка файла не означает, что все действия в официальном кабинете выполнены.

Задачи: предупреждение сотруднику за 24 часа до срока выдачи, очередь «Сегодня к отправке», тревога сразу после просрочки и эскалация администратору. Для отменённых позиций задачи закрываются; перенос даты обновляет план с историей. Автоматическое уведомление клиенту о проблеме не должно раскрывать поставщика или внутренний спор.

## 1.15. Уведомления и фоновые задания

Обязательные клиентские email: код входа, заказ принят, заявка принята, предложение готово, существенное изменение заказа/события, решение по обращению. Письмо о факте оплаты допустимо только после проводки. Основной файл билета по-прежнему отправляется вручную. Избыточное автоматическое письмо «Билет отправлен» после ручного письма по умолчанию выключено; запись видна в кабинете.

Команда видит новые заказы, заявки, обращения и просрочки в staff-панели; email-уведомления обязательны. Ранее запрошенные уведомления в приватный Telegram-чат поддержать как дополнительный канал с выключателем. Отказ Telegram не останавливает заказ. Передавать туда только номер, тип события и ссылку в staff — без телефона, email, билета, денег и паспортных сведений. Публичный канал бренда не является чатом рабочих уведомлений. Клиентский бот и SMS не входят в MVP.

Outbox сохраняется в той же транзакции, что бизнес-событие. Worker отправляет уведомления вне транзакции; повторы с задержками 1, 5, 15, 60 минут, затем видимый FAILED и ручной повтор. Если SMTP мог принять письмо, но ответ потерян, нельзя обещать строго единственную доставку; использовать стабильный message ID и не дублировать бизнес-операцию. Ошибка письма не удаляет уже созданный заказ.

Фоновые задачи: проверка истечения Hold каждые 30 секунд; контроль сроков заказов и выдачи каждую минуту; обработка outbox; суточная агрегация аналитики; очистка краткоживущих данных; резервные копии. Истечение Hold также проверяется синхронно при резервировании, чтобы остановившийся Celery не продавал устаревшие резервы. Коммерческие действия идемпотентны при повторном запуске задач.

## 1.16. Финансовый дашборд

Дашборд включает только origin SITE_DIRECT/SITE_REQUEST. Заказ, найденный через рекламу/Telegram и оформленный клиентом на сайте, относится к сайту. Продажа, целиком проведённая в переписке и не начавшаяся на сайте, не добавляется вручную. Источник трафика не равен каналу внешней продажи.

Фильтры: период, событие, категория/вид спорта, менеджер, origin и UTM-источник при наличии согласованных данных. Часовой пояс и тип периода явно видны. Суммы возвращает сервер, фронтенд только форматирует.

| Показатель | Определение |
| --- | --- |
| Созданные заказы | Количество новых Order по created_at; не количество нажатий кнопки |
| Оплаченные заказы | Уникальные заказы, впервые полностью оплаченные; first_paid_at фиксируется один раз |
| Проданные билеты | Позиции впервые полностью оплаченных заказов; отменённые/возвращённые позиции отдельным показателем |
| Оборот продаж | Сумма согласованных итогов впервые полностью оплаченных заказов выбранной когорты |
| Поступления | Реальные подтверждённые RECEIPT по effective_at; отдельный денежный отчёт |
| Возвраты | Реальные CUSTOMER_REFUND; в денежном отчёте по effective_at, в когорте — по связанным заказам на дату отчёта |
| Средний чек | Оборот / число впервые полностью оплаченных заказов, при нуле — «Нет данных» |
| Себестоимость | Сумма подтверждённых закупочных стоимостей проданных позиций минус подтверждённые возвраты поставщиков |
| Прямые расходы | Расходы, явно отнесённые к заказам; нельзя дважды включать стоимость закупки |
| Прибыль по заказам | Маржинальный результат: оборот − клиентские возвраты − себестоимость − прямые расходы |
| Конверсия | По отдельной формуле воронки из 1.17, не оплаченные заказы / все случайные клики |

«Прибыль по заказам» подписывается как управленческий маржинальный результат, не чистая бухгалтерская прибыль и не налоговая база. Общие затраты проекта, зарплаты и налоги здесь не вычитаются, если не введены отдельно как подтверждённые расходы. Отображать процент маржи только при положительной базе и полноте данных.

Если себестоимость хотя бы одной позиции неизвестна, итоговая прибыль по выбранной совокупности — «Не полностью рассчитана»; рядом результат по заказам с полными данными, их число и количество неполных заказов. Не подставлять 0 за NULL. Возврат клиенту сам по себе не обнуляет закупочный убыток; возврат от поставщика отражается отдельно. Кредит поставщика не превышает относимую стоимость без выделенной корректировки.

Когортный отчёт выбирает заказы по first_paid_at, затем учитывает их возвраты/затраты до `as_of`. Денежный отчёт выбирает операции по effective_at. Пример: заказ на 10 000 ₽ оплачен в сентябре, возврат 2 000 ₽ проведён в октябре. В октябрьском денежном отчёте отражается −2 000 ₽; в сентябрьской когорте на конец октября чистый результат продаж уменьшается на 2 000 ₽. Не смешивать эти режимы на одном графике без подписи.

Графики: заказы и билеты по дням, оборот/возвраты, маржинальный результат, события-лидеры по фактическим продажам, причины отказов, время первого контакта и просрочки отправки. Выгрузка CSV с теми же фильтрами доступна сотрудникам, содержит дату формирования и безопасное экранирование формул; чувствительные колонки не включаются в общедоступные ссылки.

## 1.17. Воронки и сбор аналитики

### 1.17.1. Две отдельные воронки

**Прямая:** просмотр события → просмотр предложений → выбор → начало оформления → заказ создан → первый контакт → заказ подтверждён → полная оплата зафиксирована → все активные билеты отправлены → завершён.

**Подбор:** открыта форма подбора → заявка отправлена → взята в работу → предложение отправлено → заказ из предложения создан → полная оплата → выдача. У свободной заявки нет обязательного просмотра существующего события, поэтому её нельзя насильно включать в первую воронку.

Операционные этапы оплачено/отправлено берутся только из базы и BusinessEvent, а не из JavaScript клиента. Просмотр/выбор/начало формы — наблюдаемые клиентские события, которые могут отсутствовать из-за отказа от аналитики или блокировщика. Отсутствие событий нельзя считать отсутствием покупателей.

### 1.17.2. Словарь событий

| Событие | Источник и условие |
| --- | --- |
| event_viewed | Клиент: реально показана страница события, не prefetch |
| offers_viewed | Клиент: виден блок предложений/списка мест |
| selection_started | Клиент: первый выбор в journey |
| checkout_started | Клиент: пользователь открыл процесс оформления, до входа допустимо |
| hold_created | Сервер: успешно создан Hold |
| order_created | Сервер: транзакция создания Order завершена |
| request_form_viewed / request_created | Клиент/сервер соответственно |
| request_in_progress / quote_sent | Серверные переходы заявки |
| first_contact_recorded | Сервер: менеджер явно отметил состоявшийся контакт |
| order_confirmed / order_paid | Серверные факты согласования и первой полной оплаты |
| tickets_sent / order_completed | Сервер: полный набор активных позиций отправлен / заказ завершён |
| order_rejected / order_cancelled / refund_settled | Серверные диагностические события; не новые продажи |

### 1.17.3. Подсчёт и ограничения

Для веб-воронки единица — `journey_id`, а не количество событий. Новый journey относится к одному событию либо свободной заявке; повторный просмотр в текущем процессе не создаёт повторный этап. Одна ступень считается максимум один раз на journey. Для order/request сохраняется исходный journey при наличии согласия; повтор webhook/worker/HTTP не увеличивает счётчики.

Когорта веб-воронки выбирается по времени первого этапа. Окно конверсии — 30 дней, `as_of` не позже текущего момента; незавершённые 30-дневные когорты помечаются как предварительные. Ступень учитывается, только если нужные предыдущие этапы этого пути наблюдались в порядке; другие серверные заказы видны отдельно как «Без связанной веб-истории». Операционная воронка по всем заказам сайта начинается с `order_created` и не зависит от рекламного согласия.

Пошаговая конверсия = число уникальных journey следующего этапа / число предыдущего; общая = финальный этап / первый. При нулевом знаменателе — NULL и «Нет данных», не 0% и не NaN. Отдельно показывать когорты заказов по created_at и исходы до as_of; не делить оплаты старых заказов на новые заказы другого периода. Отказы и возвраты — отдельные ветви, а исторический факт состоявшейся оплаты не исчезает.

Базовая реализация — собственный endpoint сбора с allowlist и серверными отчётами. Внешние системы аналитики не обязательны. Поля: event_uuid, journey_id, event_name, event_id при наличии, client_at, locale, device_class, ограниченные UTM. Не передавать email, телефон, имя, комментарии, номер документа, полный URL с query или raw referrer. UTM очищать и ограничивать 100 символами, referrer сохранять только домен, без идентификаторов.

Клиентская аналитика включается только после отдельного разрешения пользователя в принятой для проекта модели; отказ не блокирует заказ. До согласия не создавать постоянные аналитические идентификаторы и не отправлять события задним числом. Бизнес-события для исполнения заказов хранятся независимо, без попытки восстановить отказавшегося посетителя по fingerprint. Показывать долю заказов с атрибуцией и ограничение полноты. Сотрудники, тесты и известные боты исключаются.

## 1.18. Контракт API

### 1.18.1. Общий формат

Базовый путь `/api/v1/`. JSON, snake_case. Списки: `{count, next, previous, results}`; ошибки: `{error: {code, message, field_errors, details}, request_id}`. Числа денег — копейки. Для RU/EN использовать `?locale=ru|en`; код ошибки стабилен, сообщение локализуется. У каждой пользовательской операции есть схема запроса/ответа, права, побочные эффекты и примеры в сгенерированном OpenAPI.

Коды HTTP: 400 валидация, 401 нет входа, 403 нет права/MFA, 404 недоступный объект, 409 конфликт состояния/версии/наличия, 429 лимит, 503 временно недоступна обязательная зависимость. Для чужого приватного UUID — 404 без раскрытия существования. Изменяющие POST используют CSRF, а коммерческие операции также `Idempotency-Key`.

## 1.19. Админ-панель и операционные правила

Рабочая панель — не просто список таблиц Django. Нужны очередь новых заказов, поиск по номеру/контактам, фильтры сроков и менеджера, карточка с понятными действиями, очередь заявок и возвратов, редактор событий/мест, поставщики, финансы, дашборд. Два сотрудника не должны незаметно перезаписывать друг друга: назначение/изменение с version и конфликтом.

В заказе разделены публичная история и внутренние заметки. Текст клиента экранируется. Нельзя отправить клиенту внутреннюю заметку случайным переключателем без подтверждения. Отметка «Связался» фиксирует реальное время/канал контакта; открытие карточки не считается контактом для воронки. Причины отклонения: нет наличия, не согласована цена, клиент отказался, нет связи, условия прохода, дубль, другое с пояснением.

Публикация события валидирует обязательные поля и права на изображения; публикация Offer валидирует наличие, цену, возвратную политику и способ передачи. Массовое создание units имеет preview и атомарную проверку дубликатов. Цена отдельного sold/held билета не меняется редактированием оффера.

Администратор видит журнал критических действий, состояние очередей, последнюю резервную копию и ошибки уведомлений. Настройки домена, почты и рабочих контактов не заполнены фиктивными значениями: до запуска их предоставляет команда. Рабочие часы задаются настройкой; без неё клиенту не обещается конкретное число минут ответа.

## 1.20. Безопасность, файлы и персональные данные

HTTPS обязателен; DEBUG=false; секреты в окружении/секрет-хранилище, не в Git или `NEXT_PUBLIC_*`. PostgreSQL/Redis не публикуются наружу. Доверенные proxy-заголовки принимаются только от Nginx. Ограничить тело запросов, таймауты, частоту OTP/резервов/обращений/аналитики. Потеря Redis не отменяет DB-брони; при невозможности проверить антиабуз новые ограничиваемые операции временно блокируются.

Обложки/схемы загружают только сотрудники. Принимать JPEG/PNG/WebP, проверять размер и фактический формат, декодировать с лимитом пикселей и пересохранять, удаляя метаданные. Лимит файла 10 МБ, лимит 40 мегапикселей, фон схемы до 8 000 пикселей по стороне. SVG, HTML, исполняемые файлы и архивы отвергать. Имена генерирует сервер; пользовательское имя не путь. Рекомендации по ограничениям, типам и хранению — [S07].

Билетные файлы в MVP на сервер не загружаются. Будущая загрузка — отдельное закрытое хранилище, allowlist PDF/JPEG/PNG, антивирус/карантин, лимиты, проверка владельца каждой выдачи, отсутствие публичных URL и запрет произвольного HTML/SVG. Нельзя включить кнопку скачивания, разместив PDF в публичном каталоге Next.js.

В логах не должно быть OTP, паролей, полных контактов, тел комментариев, документов, платёжных секретов. Audit хранит коммерческие изменения, но чувствительные поля маскируются. CSP, `X-Content-Type-Options`, защита от встраивания, безопасные redirect и очистка HTML контента обязательны. Markdown/rich text допускает ограниченный набор элементов без script/iframe/style.

Требования к персональным данным — организационный и технический допуск, а не автоматически выданное юридическое заключение. До сбора реальных контактов заказчик утверждает оператора, цели/основания, сроки хранения, сведения о хостинге, почте/обработчиках, необходимость уведомлений регулятору, локализацию и трансграничные передачи. Применимость законодательства определяется для фактической модели работы, не по языку интерфейса и не по геолокации разработчика.

Технические настройки: OTP удалять после истечения и короткого окна диагностики до 24 часов; необработанные веб-события — до 90 дней, обезличенные агрегаты — до 12 месяцев; security logs по умолчанию 30 дней. Это стартовые лимиты, не утверждение о законодательных сроках. Сроки заказов/финансов/согласий задаются после согласования retention policy; production-приём форм до этого закрыт. Предусмотреть запрос удаления, проверку личности, выборочную анонимизацию и legal hold. Нельзя уничтожать необходимые коммерческие записи автоматической кнопкой без проверки обязательств.

## 1.21. Производительность, развёртывание и эксплуатация

Три изолированные среды, отдельные БД/секреты/email-получатели. Staging закрыт паролем и noindex; из него нельзя отправлять реальные клиентские письма случайно. Демоданные только там. Health `/health/live` проверяет процесс, `/health/ready` — готовность БД/необходимых зависимостей; внутренние подробности не выдаются публично.

Нагрузочный профиль для приёмочного теста, не прогноз спроса: до 100 параллельных сессий, 20 запросов/сек в смешанном каталожном сценарии в течение 10 минут, 2 000 опубликованных событий, 50 000 TicketUnit суммарно. На согласованной тестовой машине ориентир API p95: каталог ≤700 мс, заказ/резерв ≤1 500 мс без доставки письма. Конкурентность одного места проверяется отдельно 20 одновременными запросами. Исполнитель сохраняет конфигурацию машины, сценарий, результаты и ограничения; не обещает производительность без измерения.

Публичный каталог допускает короткий cache до 60 секунд с инвалидированием при публикации/цене. Наличие и private API не кешируются общим CDN; `Cache-Control: private, no-store` для кабинета/сотрудников/контактов. Использовать select_related/prefetch, индексы, пагинацию. Индексы: event publication/date/category/city; unit event/state; order user/date/state/manager; request state/manager; deadlines; financial effective_at; outbox due; analytics journey/event/name/time.

Стартовый измерительный профиль — 4 vCPU, 8 ГБ RAM и SSD; окончательный хостинг выбирается после оценки процессов и нагрузки. Это не обязательная покупка конкретного тарифа. Развёртывание включает домен, HTTPS с автопродлением, SMTP-домен с SPF/DKIM/DMARC, firewall, Docker volumes и миграции. Домен/сервер пока отсутствуют и передаются настройками.

Целевой RPO ≤1 часа для базы заказов, RTO ≤4 часов. Предусмотреть согласованный механизм почасовой копии/архивации и ежедневных полных копий, шифрование и отдельное место хранения не на том же диске. Медиа — ежедневная копия и после массовых изменений. Срок копий 7 почасовых/14 ежедневных/4 недельных либо эквивалент с доказанным RPO; retention согласуется с политикой данных. Минимум один тест восстановления в пустую среду до сдачи. Наличие файла backup без восстановления не считается проверкой.

Релиз: CI lint/typecheck/tests → сборка фиксированных образов → backup → миграции → deploy → smoke → наблюдение. Миграции по возможности обратно совместимы; возврат образа не равен откату схемы, план rollback документируется отдельно. Мониторить 5xx, ошибки OTP, очереди, возраст outbox, просрочки заказов/выдачи, диск, backup, сертификат. Отказ почты показывает понятную ошибку входа, не фиктивный успешный login.

| 25–28 октября | Приёмка заказчиком, конкурентные/нагрузочные тесты, восстановление backup, исправления |
| 29–31 октября | Производственный smoke, обучение двух ролей, публикация после допуска, резерв на критические дефекты |

**Внешние материалы до публичного приёма заказов:** домен и доступы на стороне заказчика; рабочая почта и SMTP; контакты/график команды; легальные изображения/схемы и контент RU/EN; утверждённые условия заказа/возврата/политика данных; ответственные сотрудники; подтверждённый способ передачи билетов. Нужны реальные реквизиты оператора/продавца в применимой модели, а не заглушки.

Флаги: `PUBLIC_FORMS_ENABLED=false` до готовности документов, контактов, почты и правил данных; `ORDER_INTAKE_ENABLED=false` до готовности запасов/исполнения; `PAYMENT_MODE=disabled` на всём MVP; `TICKET_DOWNLOAD_ENABLED=false`; `CLIENT_ANALYTICS_ENABLED` только после настройки согласия. Администратор включает формы после отметки go-live checklist; отдельные server-side проверки блокируют прямой API. Отключение новых форм не лишает существующих клиентов доступа к заказам и каналам обращения.

Если юридические/почтовые/контентные зависимости не готовы к дате, допустим публичный каталог без сбора контактов; это не следует называть полным запуском MVP с заказами. Эквайринг не блокирует сдачу согласованной первой версии, поскольку исключён из её объёма.

## 1.23. Приёмка бэкенда

Все сценарии ниже должны иметь воспроизводимый тест либо документированный ручной шаг. Критичные деньги/права/наличие — автоматические тесты. Изолированные unit-тесты не заменяют интеграционные тесты PostgreSQL.

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| B01 | Гость смотрит каталог и схему | Доступ есть; контактов/поставщиков/чужих заказов нет |
| B02 | OTP неверный, истёкший, повторно использованный | Отказ; лимиты не обходятся новым challenge |
| B03 | Два одновременных verify одного OTP | Только одна успешная активация challenge |
| B04 | Покупательский вход staff-email | Не открывает staff/ops без пароля и MFA |
| B05 | Покупатель запрашивает UUID чужого заказа/заявки | 404, данные и история не раскрыты |
| B06 | Публикация без цены/условий/права на изображение | Прямое предложение не публикуется |
| B07 | Повторное добавление одного места событию | Дубликат отклонён на уровне БД/сервиса |
| B08 | 20 покупателей резервируют последнее место | Ровно один успех, остальные 409 |
| B09 | Категория содержит 2 units, запрос на 3 | Полный отказ без частичного заказа |
| B10 | Цена изменилась до Hold | 409 и новый расчёт, нужно согласие |
| B11 | Обновление страницы во время Hold | Исходные expires_at и цена сохранены |
| B12 | Hold истёк при остановленном Celery | Новый запрос не использует просроченный Hold; запас корректно перепроверен |
| B13 | Отправка в последнюю секунду и параллельное истечение | Один непротиворечивый исход: заказ или отказ, не двойное освобождение |
| B14 | Повтор POST /orders с тем же ключом | Тот же Order, одна история, одна бизнес-операция |
| B15 | Заказ отправлен, затем истекли 10 минут | Место ORDER_HELD, не возвращено в продажу |
| B16 | Просрочен review/settlement deadline | Видимая задача/эскалация, не бесконтрольный автоматический release |
| B17 | Отмена без денег и неизвестных расчётов | Освобождение через сервис, причина и аудит |
| B18 | Поставщик потерял закрепление действующего заказа | Инцидент, не исчезновение заказа/автовыдача |
| B19 | Заявка на отсутствующее событие | Создан Request, запас/выручка не изменены |
| B20 | Quote изменён/истёк/одновременно принят | Старый не принимается; успешная конверсия одна |
| B21 | Внешний заказ вручную через staff | Запрещён; допускается только исходная заявка сайта |
| B22 | Клиент пытается передать paid/price/supplier | Запрос отвергнут или поле не разрешено контрактом; состояние не меняется |
| B23 | Реальное поступление записано дважды с одним ключом | Одна проводка; PAID только по подтверждённой сумме |
| B24 | Частичная сумма записана при полной цене | PARTIAL, сайт не сообщает полную оплату/готовность выдачи |
| B25 | Возврат одобрен, но ещё не исполнен | Не увеличивает фактически refunded; есть обязательство |
| B26 | Два конкурентных возврата превышают доступную сумму | Лишний отклонён; история согласована |
| B27 | Полный возврат высланного билета | Билет не становится автоматически AVAILABLE |
| B28 | Отмечены 2 из 4 отправок и повтор письма | PARTIALLY_SENT 2/4; повтор не увеличивает число билетов |
| B29 | Отправка отмечается до полной оплаты | Обычный сценарий блокируется, требуется урегулирование |
| B30 | Поздний заказ после стандартного срока выдачи | Срочная заявка либо явно согласованный будущий срок |
| B31 | REQUIRED / NOT_REQUIRED / неизвестный Fan ID | Корректные формы; никаких паспортных полей; неизвестное → подбор |
| B32 | Отмена/перенос события | Новые заказы остановлены, существующие сохранены, задачи/уведомления есть |
| B33 | SMTP упал после создания заказа | Заказ сохранён, outbox повторяется без дубликата Order |
| B34 | Неизвестная себестоимость | Не подставляется 0, прибыль помечена неполной |
| B35 | Возврат в следующем месяце | Денежный и когортный отчёты показывают разные периоды корректно |
| B36 | Повтор бизнес-события/возврат после оплаты | Воронка не удваивается; историческая оплата не исчезает |
| B37 | Отказ от аналитики/попытка fake order_paid с клиента | Заказ работает; веб-трекинга нет; серверное событие не подделывается |
| B38 | Загрузка HTML/SVG/слишком большого изображения | Отказ, файлы не исполняются и не публикуются |
| B39 | Два менеджера меняют одну версию заказа | Второй получает VERSION_CONFLICT, не тихую перезапись |
| B40 | Все флаги форм выключены, прямой API вызван | Новое создание блокируется, история существующих заказов доступна |
| B41 | Экспорт CSV с опасным текстом | Формулы не исполняются, доступ только staff |
| B42 | Восстановление и конкурентный тест после deploy | Данные восстановлены; сценарий заказа проходит в чистой среде |
