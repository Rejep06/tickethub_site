# Часть 2. Фронтенд

**Tickethub — техническое задание, версия 2.0 от 30 сентября 2026 года.** Использовать только совместно с частью 1 той же версии. Целевой запуск MVP — не позднее 31 октября 2026 года. Макеты, компоненты и тексты должны соответствовать режиму заказов с ручной обработкой, а не изображать работающий интернет-эквайринг.

## 2.1. Концепция и визуальная система

Сайт яркий и событийный, с приоритетом спорта. Брендовая основа — приложенный логотип Tickethub: чёрное название и чёрно-жёлтый знак на белом фоне. Сохранить пропорции и написание; не перерисовывать похожим шрифтом. Исходный JPEG приложен в `assets/tickethub_logo_original.jpg`; для интерфейса можно подготовить аккуратный web-asset из исходника, не объявляя автоматически трассированное изображение официальным векторным логотипом.

Дизайн: крупные афиши, сильная типографика, белое пространство, чёрный текст, жёлтые основные действия. Это не тёмный букмекерский интерфейс и не банковский кабинет. Не использовать неон, тяжёлые градиенты, бесконечные карусели и вымышленные счётчики дефицита. Страницы заказа и кабинета спокойнее главной: акцент на понятном следующем действии.

| Токен | Значение/правило |
| --- | --- |
| Основной фон | `#FFFFFF` |
| Основной текст | `#111111` |
| Брендовый жёлтый | `#FFF000`, рабочее приближение по исходному растровому логотипу |
| Hover основного действия | `#E6D800`; текст чёрный |
| Вторичный фон | `#F5F5F5` |
| Вторичный текст | `#525252` |
| Границы | `#D4D4D4`; усиление контраста для интерактивных контролов |
| Статусы | Семантические success/warning/error; всегда текст/иконка, не один цвет |
| Шрифт | Inter с кириллицей, локально размещённый разрешённый шрифт; fallback system-ui |
| Базовый текст | 16 px, line-height 1.5; мелкие подписи не меньше 12–14 px |
| Заголовки | H1 desktop 44–56 px, mobile 28–36 px; длинные названия не обрезать по смыслу |
| Сетка | Max-width 1280 px, desktop отступы 24–32 px, mobile 16 px |
| Скругления | Кнопки 10–12 px, карточки 16 px; единая система |
| Ритм отступов | 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 px |
| Интерактивная область | Основные мобильные элементы около 44×44 px и больше |

Жёлтый текст на белом фоне не использовать. Проверить контраст каждой реальной комбинации, focus и disabled-состояний. Доступность ориентировать на WCAG 2.2 AA для основных сценариев; сами требования контраста, клавиатуры и взаимодействия проверяются по [S09] части 1, а не выводятся из цвета бренда.

## 2.2. Стек и устройство приложения

Next.js App Router, React, TypeScript strict, Tailwind CSS. Клиентские формы — React Hook Form и Zod; библиотеку компонентов использовать только как основу доступных примитивов, не как готовую чужую тему. Данные клиента — TanStack Query либо единый эквивалентный слой без дублирующих fetch-реализаций. Иконки — единый набор с доступными подписями.

Фиксировать точные совместимые версии при создании репозитория, не оставлять плавающие зависимости. Документация Next.js подтверждает используемые TypeScript/App Router-подходы [S02 части 1]. Сборка self-hosted на Node; статический export не заменяет серверный рендеринг приватных/динамических сценариев.

```text
frontend/src/
  app/[locale]/             # публичные страницы и кабинет RU/EN
  app/[locale]/staff/       # рабочая панель; разрешён только RU
  components/ui/            # кнопки, поля, диалоги, таблицы
  features/catalog/
  features/seat-map/
  features/auth/
  features/checkout/
  features/requests/
  features/account/
  features/staff/
  lib/api/                  # типизированный клиент, CSRF, ошибки
  lib/i18n/                 # словари интерфейса RU/EN
  lib/analytics/            # consent-aware события
  types/api/                # типы из OpenAPI
```

Публичные страницы каталога/события — серверный начальный рендеринг. Схема, счётчики, фильтры, формы и кабинет — клиентские компоненты там, где нужна интерактивность. Загружать редактор схем и графики лениво. Django остаётся единственным источником авторитетной цены, роли, статуса и срока брони.

OpenAPI из бэкенда порождает TypeScript-типы. Mock API допустим только в local/тестах с явным флагом, не в production-сборке. Все основные экраны должны работать на реальных endpoint. При несовпадении enum не подменять неизвестный статус на «Оплачено», а показывать безопасное состояние и фиксировать ошибку.

Один origin и cookie-сессия; клиент отправляет CSRF на изменяющих запросах. Private SSR-fetch не кешируется между пользователями и передаёт только нужные cookies. Пользовательские данные не попадают в общие cache, sitemap, public analytics или исходный HTML другой сессии. JWT/localStorage не добавлять параллельно с предусмотренными Django sessions.

## 2.3. Карта сайта

`/{locale}` — `/ru` или `/en`. Корень `/` направляет на сохранённый язык, иначе `/ru`. Slug события общий и стабильный. Смена языка сохраняет объект, выбор, форму и допустимые query-параметры; не создаёт новый заказ или таймер. Staff всегда на русском.

| Маршрут после /{locale} | Содержимое |
| --- | --- |
| `/` | Главная афиша, спортивные события, подбор |
| `/events` | Каталог с поиском/фильтрами/пагинацией |
| `/sports`, `/concerts`, `/other` | Категории на общей логике каталога |
| `/events/{slug}` | Событие, условия, Fan ID, схема/категории |
| `/request` | Запрос на событие, которого нет в каталоге |
| `/login` | Единый вход/регистрация по email-коду |
| `/checkout` | Выбор, вход при необходимости, получение server preview и Hold |
| `/checkout/{hold_id}` | Форма заказа с 10-минутным таймером |
| `/account` | Обзор активных заказов/заявок |
| `/account/orders` | История заказов |
| `/account/orders/{id}` | Детали, статусы, сроки, отправки, обращения |
| `/account/requests`, `/account/requests/{id}` | Подбор и актуальное предложение |
| `/account/profile` | Имя, телефон, email, язык, настройки аналитики/данных |
| `/about`, `/how-it-works`, `/contacts`, `/faq` | Информация из CMS |
| `/fan-id` | Инструкция и помощь по карте болельщика |
| `/legal/{type}` | Утверждённые версии документов |
| `/staff/login`, `/staff/...` | Рабочая панель команды; реально только /ru |

В первой версии нет рабочей страницы `/payment/return`, формы карты/СБП и публичного скачивания билета. Несуществующие функции не показываются как «готовые, но временно недоступные». Внутренние/непубличные предложения доступны только по правам владельца заявки, не только за счёт секретности ссылки.

## 2.4. Главная страница

Шапка desktop: логотип, «Спорт», «Концерты», «Другие события», поиск, RU/EN, вход/кабинет, заметная ссылка «Подобрать билеты». На телефоне: логотип, переключатель языка, аккаунт и меню; поиск отдельной строкой. Навигация управляется клавиатурой, мобильное меню закрывается Escape/кнопкой и удерживает focus внутри.

Первый экран: заголовок «Билеты на события, которые нельзя пропустить», пояснение «Выберите места или оставьте заявку — менеджер поможет оформить заказ». Основное действие «Смотреть события», вторичное «Подобрать билеты». Крупная реальная афиша/фото из CMS; при отсутствии — фирменная нейтральная композиция, не выдуманное мероприятие.

Дальше: быстрые фильтры по городу/дате/типу → ближайший спорт → концерты и другие события → «Как заказать» → помощь с Fan ID → форма/ссылка подбора → FAQ → footer. Блок без опубликованных событий не должен содержать пустую сетку из демо-карточек. Рекомендуемые события выбирает менеджер; «Популярное» не писать без фактического критерия.

«Как заказать» для MVP: выбрать событие и места → отправить заказ → согласовать детали с менеджером → получить билет по email. Не обещать мгновенную онлайн-оплату/автовыдачу. В блоке Fan ID: «Подскажем, как оформить карту болельщика, если она нужна для вашего мероприятия». Без обещания гарантированного оформления и без предложения передать документы.

Footer: реальные контакты, часы работы, информационные страницы, документы, язык, настройка аналитики. Ссылку Telegram брать из CMS; неподтверждённые контакты скрывать, не генерировать. Не публиковать фальшивые отзывы, логотипы партнёров, цифры продаж и подписи «официальный партнёр» без подтверждения.

## 2.5. Каталог и карточки событий

Карточка содержит изображение с фиксированным соотношением сторон, категорию, название, дату и местное время, город/площадку, цену от либо «По запросу», доступное действие и при необходимости Fan ID-бейдж. У переноса — новая дата или «Дата уточняется», у отмены/завершения — статус без покупки. Изображение имеет alt и размеры, не сдвигает страницу при загрузке.

| Ситуация | Текст и действие |
| --- | --- |
| Есть AVAILABLE и разрешены заказы | «От 5 500 ₽», «Выбрать билеты» → событие; далее «Оформить заказ» |
| Только подбор | «По запросу», «Оставить заявку» |
| Запас временно занят | «Доступность уточняется», подбор; не «Весь стадион распродан» |
| Fan ID/возвратные условия ещё проверяются | Пояснение и обращение менеджеру, без неподтверждённого прямого заказа |
| Заказы отключены по конфигурации | Каталог доступен, понятное уведомление; нельзя обойти через прямую ссылку |

Поиск с задержкой около 300 мс, Enter — сразу, устаревшие запросы отменяются. Фильтры: категория/вид спорта, город, страна, даты, цена, «Есть билеты / Подбор». Состояние в URL и корректное восстановление Back/Forward. Геолокация не запрашивается, стартовый город — «Все города».

Desktop: боковые фильтры и 3 карточки в ряд; планшет — 2, телефон — 1 либо 2 только при читаемых названии/дате/цене. Мобильные фильтры в панели с «Показать события» и числом выбранных фильтров. Пагинация адресуемая, не только бесконечный scroll.

Пустой каталог/поиск: объяснение, «Сбросить фильтры», «Подобрать билеты». Ошибка сервера — отдельное сообщение и повтор, не пустая выдача. Пока идёт загрузка, skeleton сохраняет размер карточек; уже введённые фильтры не сбрасываются.

## 2.6. Страница события

Порядок: навигационная цепочка → название/вид события → дата и местное время площадки → город/арена → обложка → выбор билетов → описание → условия прохода и Fan ID → срок получения → возвраты → подбор. Для важного ограничения не требовать открыть незаметный аккордеон: предупреждение о Fan ID и сроке выдачи видно до выбора.

Desktop: схема/категории слева, итог справа. Mobile: сведения, выбор, фиксированная снизу компактная сумма/кнопка с раскрытием деталей; учесть safe-area и padding, чтобы панель не закрывала контент. Смена выбранного события не переносит прежние места в новый заказ.

Точное время показывать с подписью «Местное время площадки». За рубежом не переводить его незаметно во время телефона. TBA не превращать в Invalid Date. При переносе — заметный блок «Мероприятие перенесено», новая/старая дата, связь с менеджером.

Политика возврата — текст утверждённой версии, не самостоятельная юридическая интерпретация фронтенда. Когда правила не готовы — «Условия уточнит менеджер до подтверждения», режим подбора согласно API. Не скрывать возможность отправить обращение в уже существующем заказе.

## 2.7. Интерактивная схема и выбор категории

### 2.7.1. Схема

Отрисовка: безопасный image-фон и SVG-слой, сформированный приложением из проверенных координат. Не вставлять произвольный SVG/HTML из загрузок. Есть pan/zoom, +/−, «Показать целиком», переключатель «Схема / Список мест». Масштабирование работает мышью и касанием, но не блокирует обычную прокрутку страницы мимо схемы.

Выбор доступного места показывает сектор, ряд, номер, цену, категорию. Повторный клик снимает локальный выбор. Выбранные места видны в отдельном списке с удалением и суммой. Несколько мест — отдельные позиции, а не строка «3 билета» без нумерации.

| Состояние | Отображение |
| --- | --- |
| AVAILABLE | Доступное место с контуром и текстовой ценой/категорией |
| Локально выбрано | Жёлтое выделение, чёрная рамка/галочка; «Ещё не забронировано» |
| Собственный Hold | Отдельная отметка, серверный таймер и ссылка вернуться в оформление |
| Чужой Hold/заказ/продажа | Нейтральное недоступное место без данных чужого заказа |
| Нет предложения Tickethub | Фон/нейтральный статус; не ложное «Продано организатором» |

Список мест полностью заменяет карту для оформления с клавиатуры и на слабом устройстве. Фильтры сектор/ряд/цена, поиск номера, тот же выбранный состав. Для 5 000 точек не рисовать все номера мелким текстом; детали при zoom или выборе. Состояния не зависят только от цвета.

Свежую доступность получать при открытии, возврате вкладки и каждые 10 секунд, пока блок видим. После 409 обновить немедленно. Polling прекращается на скрытой/покинутой странице. Успешный GET не гарантирует резерв: последнее слово у POST Hold. Изменившееся/занятое место не заменяется автоматически; пользователь видит, какое именно недоступно.

«Места рядом» показывать только по проверенным данным сервера. Для раздельных мест — предупреждение; при неизвестном соседстве не делать обещания. В подборе дать пожелание «Только места рядом», которое сохраняется при отправке.

### 2.7.2. Без схемы

Категории: название, описание, сидячие/стоячие, сектор при наличии, цена за билет, доступное количество, срок отправки, счётчик 1–10 и CTA. Конкретные номера могут не определяться — это написано до заказа. Изображение схемы без разметки разрешено как справочное с явной подписью «Для ориентира, выбор мест здесь недоступен».

REQUEST-предложение не имеет вымышленного остатка и нулевой цены. Его CTA открывает подбор с предзаполненными event/category. В одном оформлении MVP либо нумерованные места, либо количество одной категории; смешивание режимов не поддерживается. Больше 10 билетов — предложить подбор, а не обойти лимит.

## 2.8. Вход и регистрация

Единый экран/модальное окно: «Войти или зарегистрироваться» → email → «Получить код» → шесть цифр → «Продолжить». Подпись «Пришлём код на почту. Пароль не нужен». Поле кода поддерживает вставку целиком и `autocomplete=one-time-code`; email — подходящий input type/autocomplete. Код нельзя вводить только в шесть недоступных для вставки независимых полей.

Повторная отправка с реальным `resend_after` сервера; изменить email можно без потери выбранных мест. Состояния: sending, sent, wrong code, expired, rate limited, provider unavailable. Не показывать, был ли email зарегистрирован. Ошибка почты не выдаётся за успешный вход.

До запроса кода показать применимые документы по обработке email; необходимые отдельные согласия/подтверждения — без предустановленных галочек, в форме и объёме, утверждённых заказчиком. Аналитика/маркетинг не включаются скрыто. При выключенном PUBLIC_FORMS_ENABLED вход новых клиентов не предлагается как работающий, но существующие пользователи сохраняют доступ по безопасному предусмотренному каналу.

После успешного входа вернуть в прежний контекст. В выбранных местах ещё нет гарантии: сервер заново проверит наличие/цену перед Hold. Покупатель не теряет комментарий и настройки языка. Показывать полный телефон/контакт только в своём кабинете и нужной staff-карточке.

## 2.9. Оформление заказа и таймер

### 2.9.1. До резерва

Клиент выбирает билеты → нажимает «Оформить заказ» → при необходимости входит → сервер проверяет preview → создаёт Hold → открывается форма. При PRICE_CHANGED сначала показать старую/новую цену и запросить согласие. При SEAT_UNAVAILABLE вернуть к выбору с конкретным объяснением. Таймер до успешного Hold не показывать.

### 2.9.2. Форма на 10 минут

Вверху «Билеты временно закреплены на время оформления» и таймер. Поля: имя, телефон с выбором кода страны, подтверждённый email read-only с безопасным переходом смены, необязательный комментарий. Для REQUIRED Fan ID — один выбор «Есть карта / Нужна помощь / Не уверен» (для группы — «Есть у всех / Нужна помощь / Не уверен»), пояснение без запроса номера/паспорта.

Справа/ниже итог: событие, дата, площадка, все места или категория/количество, полная цена в RUB, срок отправки, возвратные условия, принятые версии документов. Главная кнопка **«Отправить заказ менеджеру»**. Подпись **«Сейчас деньги не списываются. Менеджер свяжется с вами для подтверждения деталей и оплаты»**. Нет кнопки «Оплатить», формы банковской карты, QR СБП и выбора предоплаты.

Таймер рассчитывается через разницу server_now/expires_at и монотонное локальное время; часы устройства не источник истины. Обновление страницы не запускает новые 10 минут. За 2 минуты — ненавязчивое предупреждение, без мигания и агрессивного звука. По истечении блокировать submit, показать «Время брони истекло» и «Проверить доступность заново». Контактные поля и комментарий не очищать.

Серверный 409 важнее локального таймера. Если ответ submit потерян, повторить с тем же Idempotency-Key и восстановить результат, не создать новый заказ. Кнопка disabled во время запроса, но это лишь UX-дополнение к серверной идемпотентности. При уходе с незавершённой формой предупредить о потере брони; не блокировать закрытие бесконечными диалогами.

### 2.9.3. После отправки

Экран успеха: «Заказ №… принят», «Менеджер свяжется с вами», контакты назначения, состав и итог, ссылка «Перейти к заказу». **Таймер исчезает:** это уже заказ с отдельным закреплением, не продолжающий истекать checkout. Не выводить «Покупка оплачена», «Билеты готовы» или гарантированный срок звонка, которого нет в настройках.

При уже существующем активном заказе на это событие показать ссылку на него и обращение менеджеру. Повторное нажатие Back/Submit не создаёт новую продажу. Успешный экран не является самостоятельным источником аналитического события order_created — этот факт приходит от сервера.

## 2.10. Подбор и персональное предложение

Свободная форма: «Какое событие ищете?», город, дата/период при знании, количество 1–100, предпочтения по местам/категории, «Места рядом», бюджет **на все билеты**, имя/телефон/email, комментарий. Для каталожного события event уже выбран. Бюджет необязателен, ноль не равен «не указан».

Подсказка: «Заявка не гарантирует наличие и не резервирует билеты. Менеджер проверит варианты». Перед отправкой — вход; после — номер заявки, статус, ссылка в кабинет. Вложения документов не предусмотрены. При включённой аналитике отправляется request_form_viewed, а request_created — только сервером.

Карточка Quote в кабинете: событие, состав/соседство, полная цена, условия, срок выдачи, действует до, «Наличие перепроверяется при подтверждении». Кнопка «Оформить по предложению» создаёт Hold и ведёт к обычному checkout. Просроченная/отозванная версия не нажимается, есть «Связаться с менеджером»/«Нужен другой вариант».

Принятие предложения не показывает моментальную покупку и не запускает оплату. При потере наличия показать конкретную ошибку, сохранить заявку и контекст, не заменить место более дорогим. В истории старые версии видимы как неактивные; CTA доступен только для текущей SENT-версии.

## 2.11. Личный кабинет

Разделы: активные заказы, вся история, заявки, профиль. На обзорном экране первыми — действия, требующие клиента: принятие предложения, информация о переносе, необходимость помощи Fan ID, ответ по обращению. Финансовые внутренние сведения отсутствуют.

Список заказов: номер, событие/дата, количество, итог, три статуса в компактном виде, срок отправки и кнопка деталей. Отдельно обозначать «Заявка», «Заказ», «Оплачен»; их нельзя смешивать в один список «Куплено» без фильтра. Отменённые события остаются в истории.

### 2.11.1. Карточка заказа

Карточка содержит состав по каждой позиции; исходные и актуальные сведения при переносе; контакты; «Обработка», «Оплата», «Отправка» отдельными блоками; публичный таймлайн; ожидаемый срок email-выдачи; инструкции Fan ID; обращение к менеджеру. Внутренние notes не выводятся.

| Состояние | Пример клиентского текста |
| --- | --- |
| NEW | «Заказ получен. Ожидает обработки» |
| IN_PROGRESS | «Менеджер работает с заказом» |
| CONFIRMED + UNPAID | «Заказ подтверждён. Условия оплаты согласуются с менеджером» |
| PAID + NOT_SENT | «Оплата получена. Отправим билеты до …» |
| PARTIALLY_SENT | «Отправлено 2 из 4 билетов на …» |
| SENT | «Билеты отправлены на email …, дата и время …» |
| REFUND_APPROVED, ещё не SETTLED | «Возврат согласован, ожидает выполнения» |
| REFUNDED | «Возврат выполнен: … ₽» |
| Есть инцидент | Конкретное публичное объяснение и способ связаться, без раскрытия внутренней причины/поставщика |

В MVP файл не скачивается на сайте. Пояснение: «Билеты отправляются письмом. Проверьте входящие и папку “Спам”». Действия «Не получил билет», «Связаться с менеджером», «Запросить отмену/возврат». Нельзя рисовать PDF-карточку или download-кнопку без доступного авторизованного файла.

Обращение: причина, необязательная сумма возврата, позиции при частичном запросе, текст; после отправки — номер, статус и история решения. Не обещать автоматическое одобрение или срок, не установленный утверждёнными условиями. Запрос не освобождает места и не меняет деньги самостоятельно.

### 2.11.2. Профиль

Имя, телефон, email, язык, настройки аналитики, выход, запрос по персональным данным. Email меняется по процессу подтверждения, а не свободным PATCH. Показать, что смена профиля не заменяет адрес доставки уже оформленного заказа; изменение для него согласуется отдельно. Не запрашивать дату рождения, пол, паспорт или аккаунты Госуслуг.

## 2.12. Рабочая панель администратора и менеджера

Одна рабочая панель для двух ролей с серверными разрешениями. Менеджер видит финансовые данные и поставщиков. Управление сотрудниками, интеграциями и публикацией юридических документов — только администратор. Скрытие пункта меню не единственная защита.

Левая навигация: «Дашборд», «Заказы», «Заявки», «Возвраты и обращения», «Мероприятия», «Площадки и схемы», «Предложения и билеты», «Поставщики», «Контент», «Уведомления». Для ADMIN дополнительно «Сотрудники», «Настройки», «Аудит». На мобильном сворачивается в меню, основные рабочие операции доступны без горизонтального скролла всей страницы.

### 2.12.1. Дашборд

Верх: период, тип периода «Продажи / Движение денег», timezone, фильтры события/менеджера/origin. Карточки: созданные/оплаченные заказы, билеты, оборот, средний чек, возвраты, себестоимость, прямые расходы, прибыль по заказам, неполные финансовые данные. Показать дату обновления; загружаемое/неизвестное значение не равно 0.

Ниже графики из 1.16 и две вкладки воронки. У каждой воронки видны база, окно 30 дней, as_of, уникальные journey/заказы, пошаговая/общая конверсия, число записей без веб-истории и доля атрибуции. Нельзя складывать просмотры и заявки без события в одну искусственную ступень.

Таблицы: просроченный первый контакт, сегодня к отправке, просроченная отправка, открытые возвраты, заказы с неизвестной себестоимостью. Числа кликабельны и открывают список с теми же фильтрами. CSV повторяет текущий фильтр и не скрыто выгружает всю базу клиентов.

### 2.12.2. Заказы

Список с номером, датой создания, событием, клиентом, суммой, статусами, менеджером, следующим действием, сроком выдачи и alert. Поиск по номеру, имени, телефону/email; контактные данные не отправляются в внешнюю аналитику/URL без необходимости. Фильтры «Новые», «Мои», «Без менеджера», «Просроченные», «Оплачены, не отправлены».

Карточка на desktop в 2–3 колонки: клиент/действия; позиции/статусы; история/финансы. Внутренние заметки визуально отделены и подписаны. Кнопки отражают allowed_actions. Действия с деньгами и отправкой имеют подтверждение с номером заказа и точной суммой/получателем.

«Зафиксировать поступление»: сумма, время, способ, reference; текст «Подтверждаю фактическое получение средств». «Отметить отправку»: позиции, email, время, message ID при наличии; текст «Файлы уже отправлены». Не объединять эти действия в одну кнопку «Завершить заказ».

Отмена/отклонение спрашивают причину и показывают последствия для денег и наличия. Возврат разделён на решение и исполнение. Устаревшая version даёт сообщение «Заказ изменил другой сотрудник — обновите данные», не молчаливое затирание. Двойное нажатие не удваивает операции.

### 2.12.3. Заявки и Quote

Очередь новых/в работе/предложенных, назначение менеджера, первый контакт, пожелания, бюджет на весь запрос и deadline. Предложение создаётся из подтверждённых units/категории, с полной ценой/условиями. Preview показывает ровно то, что увидит клиент. Отправленная версия блокируется для редактирования, есть «Создать новую версию» и «Отозвать».

При свободной заявке можно создать непубличное событие с полными данными; оно не должно неожиданно появиться на главной. Конверсия в заказ требует действия покупателя; менеджер не создаёт фиктивный заказ для улучшения воронки.

### 2.12.4. Редактор мероприятия и запасов

Вкладки: «Основное RU/EN», «Дата и площадка», «Контент», «Схема», «Предложения», «Условия», «Публикация». Подсвечивать обязательные переводы, Fan ID, срок выдачи, правила возврата, право на изображение. Preview RU/EN до публикации. Ошибки выводятся рядом с полем и в сводке.

У AVAILABLE-предложения — единичный/пакетный ввод билетов, поставщик, закупочная цена, основание наличия, срок закрепления; у REQUEST — пожелания и описание без фиктивного остатка. Замена режима не превращает автоматически неподтверждённый список в продаваемый запас. Состояния held/sold только для чтения, управляются заказами.

Менеджер вручную наполняет данные. Никаких кнопок «Импортировать все билеты конкурента», скрытого scraping и автоматического угадывания номера места по картинке.

### 2.12.5. Редактор схем

Последовательность: выбрать площадку → создать черновик плана → загрузить разрешённый фон → указать источник → расставить места/ряды → проверить список → preview → опубликовать. Инструменты: выделение, добавление точки, перетаскивание, сектор/ряд/номер, создание прямого ряда по началу/концу и явной нумерации, удаление в черновике, undo/redo в текущей сессии, zoom/fit.

Список мест синхронизирован с картой, позволяет массово проверить нумерацию и дубликаты. Показать предупреждения о совпадающих координатах/номерах и точках за пределами изображения. Undo не отменяет уже опубликованную версию. Автосохранение черновика с version и заметным статусом; при сетевой ошибке не писать «Сохранено».

Опубликованная схема read-only, для изменений — копия новой версии. Копирование геометрии не копирует продажи/покупателей/остатки. Замена фона не должна незаметно смещать места на опубликованном событии. На телефоне обязателен просмотр и базовые исправления; точная массовая разметка оптимизируется под desktop.

### 2.12.6. Справочники, контент и настройки

Поставщики — внутренние контакты/примечания; удаление используемого поставщика заменяется архивированием. Финансовые поля не появляются в публичном preview. Юридические документы имеют статус и версии; администратор публикует после утверждения, не одним заполнением произвольного textarea «для галочки».

На странице запуска — checklist домена, почты, контактов, документов, контента, тестов и backup. Переключатель приёма заказов показывает реальные серверные причины блокировки. Секреты SMTP/провайдера нельзя считать из API и подставить в browser input; управляются защищённой конфигурацией.

## 2.13. Библиотека компонентов и общие состояния

Минимальный набор: Button, Input, PhoneInput, Select, Checkbox, RadioGroup, Dialog/Drawer, Tabs, Toast, Alert, Badge, Skeleton, EmptyState, Pagination, DataTable, DateTimeField, Money, EventCard, EventFilters, FanIdNotice, SeatMap, SeatList, SelectionSummary, HoldTimer, OrderStatus, PublicTimeline, InternalNote, FinancialSummary, DeliveryChecklist, FunnelTable, UploadField, LanguageSwitcher, AnalyticsConsent.

Для каждого интерактивного компонента: default, hover, focus, disabled, loading, error; при необходимости empty/success. Видимый label обязателен, placeholder его не заменяет. Ошибки валидации рядом с полем, summary и focus на первой ошибке. Не сбрасывать значения после серверной ошибки. Toast не единственный способ сообщить важный результат оплаты/отмены.

Все суммы через единый formatter, без float-расчётов коммерческого итога. RU: «5 500 ₽», EN: «RUB 5,500»; копейки показывать при ненулевой дробной части. Даты через locale formatter с явным timezone. Отрицательная прибыль допустима и не маскируется нулём; NULL — «Нет данных».

Ошибки 401 возвращают к входу с безопасным контекстом, 403 — сообщение о правах, 409 — конкретный конфликт и повторная проверка, 429 — время ожидания, 5xx — повтор без потери формы. Не показывать traceback и SQL. Не разрешать browser retry опасной операции с новым ключом, когда результат старой неизвестен.

## 2.14. RU/EN, адаптивность и доступность

Все интерфейсные строки в словарях, включая ошибки, письма и состояния. Контент события RU/EN заполняется в CMS; машинный перевод не публикуется без проверки. Подписи с числом билетов используют корректные формы: 1 билет / 2 билета / 5 билетов, tickets в EN. Язык профиля задаёт язык сервисных писем.

Breakpoint-проверки: 360, 390, 768, 1024 и 1440 px. Устройство шириной 360 px должно позволять найти событие, выбрать место из списка, войти, отправить заказ, посмотреть статус и обращение. Горизонтальная прокрутка допустима только внутри подписанных таблиц/редактора, не всего сайта. Zoom браузера 200% не делает критические действия недоступными.

Проверить клавиатуру от шапки до отправки заказа, видимый focus, порядок заголовков, alt, aria для диалогов/статусов, focus trap и возврат focus после закрытия. Таймер не озвучивается скринридеру каждую секунду; доступны ключевые предупреждения. Учитывать prefers-reduced-motion. Графики имеют таблицу данных/доступное описание.

При ошибке схемы оставить работоспособный список мест; при отказе изображения событие остаётся читаемым. Основные действия не зависят от hover. Нельзя требовать точного попадания в двухпиксельную точку без альтернативного списка.

## 2.15. SEO, производительность и аналитика

Публичные страницы — уникальные title/description, H1, canonical, hreflang RU/EN, Open Graph, sitemap только опубликованных доступных страниц. Фильтры не создают бесконечный индекс дублей. Аккаунт, checkout, staff, заявки и непубличные Quote — noindex; robots.txt не заменяет авторизацию.

Разметка Event/Offer допустима только с достоверными датами, состоянием и ценой; при «По запросу» не подставлять 0 и не обозначать моментальную покупку, которой нет. Отмена/перенос обновляют публичные метаданные. На сервере не раскрывать себестоимость внутри JSON-LD.

Оптимизировать изображения, responsive sizes, lazy load нижних блоков; hero загружается приоритетно. Не отправлять весь редактор/графики в bundle главной. Целевые показатели для основного мобильного сценария: LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1 как проектные цели; полевой INP подтверждается реальным мониторингом после появления трафика, не выдуманным отчётом Lighthouse. Перед релизом выполнить воспроизводимые лабораторные замеры с описанием устройства/сети; не обещать постоянные 100 баллов.

Клиентская аналитика строго по словарю 1.17. Согласие с одинаково доступными «Разрешить»/«Отказаться», возможность изменить решение в footer/профиле. До разрешения нет сторонних трекеров и persistent journey. Бизнес-события заказа создаёт сервер, независимо от показа страницы успеха. Не включать session replay, запись текста форм и user fingerprint.

В SPA-переходах event_viewed отправляется на фактическое отображение, не на prefetch; повтор событий имеет event_uuid. UTM сохраняются только разрешённым механизмом, с очисткой. Ошибки аналитического endpoint не должны блокировать форму и заказ. E2E проверяет отсутствие контактов в event payload.

## 2.16. Тестовые данные и приёмка фронтенда

Пользователи: покупатель А, покупатель Б, менеджер, администратор. Цены/остатки включают последний билет, неизвестную себестоимость и частичную выдачу. Демоданные не переносятся в production.

## 2.17. Итоговый результат и передача проекта

Исполнитель передаёт исходники двух частей в одном репозитории, историю миграций, lock-файлы, Docker-конфигурацию, `.env.example` без секретов, актуальный OpenAPI, инструкции local/staging/production, backup/restore/rollback, руководство менеджера, таблицу тестов и известные ограничения. Проект считается готовым к технической приёмке, когда B01–B42 и F01–F30 пройдены либо для некритичного замечания есть письменное согласование переноса; отсутствуют критические дефекты доступа, денег, двойной продажи и потери заказов; обе локали работают; свежая среда поднимается по инструкции; backup восстановлен; заказчик может самостоятельно выполнить основной процесс через интерфейс.
