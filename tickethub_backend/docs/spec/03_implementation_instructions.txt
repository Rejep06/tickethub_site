========================================
ГЛАВНАЯ ЦЕЛЬ
========================================

Нужно получить РАБОТАЮЩИЙ backend Tickethub, а не демонстрационный skeleton.

Backend должен поддерживать полный основной сценарий:

Сотрудник создаёт мероприятие
→ создаёт площадку/схему при необходимости
→ создаёт билеты
→ публикует мероприятие
→ пользователь открывает каталог
→ выбирает мероприятие
→ выбирает билет/место
→ авторизуется
→ получает резерв на 10 минут
→ создаёт заказ
→ билет закрепляется за заказом
→ менеджер получает заказ
→ связывается с клиентом
→ подтверждает заказ
→ фиксирует получение оплаты
→ отправляет билет клиенту вручную по email
→ фиксирует факт отправки
→ завершает заказ.

Также должен полностью работать второй сценарий:

Клиент не нашёл билет
→ создаёт заявку
→ менеджер обрабатывает её
→ предлагает подходящий билет
→ клиент оформляет заказ
→ дальше используется обычная логика заказа.

Также должна работать заявка на мероприятие, которого ещё нет в каталоге.

========================================
РЕЗЕРВ
========================================

Резерв:

10 минут.

Сценарий:

AVAILABLE
→ CHECKOUT_HELD
→ ORDER_HELD
→ SOLD

Если клиент только начал оформление:

резерв действует 10 минут.

Если 10 минут закончились до отправки заказа:

места освобождаются.

НО:

после успешного POST /orders/

десятиминутный таймер больше НЕ действует.

Билеты должны закрепиться за созданным заказом.

Они освобождаются только через контролируемую бизнес-операцию.

========================================
ДВОЙНАЯ ПРОДАЖА
========================================

Это критично.

Используй:

transaction.atomic()
select_for_update()

и database constraints.

Два пользователя не должны иметь возможность получить последний один билет.

Обязательно реализуй и запусти конкурентный тест:

пользователь A
и
пользователь B

одновременно пытаются забронировать последний билет.

Успешным должен быть только один.

Второй получает:

409 CONFLICT.

========================================
ORDER
========================================

Не делай один универсальный status, который пытается описать всё.

Но payment_state и delivery_state предпочтительно вычислять из фактических записей, если это остаётся понятным.

Пример:

order_state = CONFIRMED
payment_state = PAID
delivery_state = NOT_SENT

Это нормальное состояние.

ОТПРАВКА БИЛЕТА
========================================

Например:

Повторная запись тех же двух билетов не должна давать:

4 из 4.

========================================
ЗАЯВКИ
========================================

TicketRequest:

- не нашёл подходящую категорию;
