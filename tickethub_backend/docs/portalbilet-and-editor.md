# PortalBilet и редактор схем — текущая реализация

## Статус

**Редактор: код реализован, автономные/UI-проверки выполнены, Django/PostgreSQL не проверены.**

**PortalBilet: частичная реализация. Полного автоматического импорта схемы и внешних билетов пока нет.**

Можно передать одну ссылку: код запрашивает page-data, подготавливает непубличные локальные события по распознанным датам, сохраняет ответы источника/диагностику. Неизвестные данные НЕ превращаются в выдуманные места и остатки.

В этой среде удалось прочитать публичную HTML-страницу примера, но JSON page-data, coordinates, tickets, standing_tickets и dates получить не удалось. Локальная попытка завершилась `PROVIDER_DNS`; инструмент веб-доступа также не предоставил JSON. Никаких реальных JSON fixtures не получено. Bootstrap-reader написан по справочнику пользователя и НЕ проверен на настоящем ответе. При несовпадении формата возвращается явная ошибка.

**Ключ связи tickets ↔ coordinates не установлен.** Это не считается завершённой интеграцией. Успешный HTTP-запрос к нашему import endpoint также не означает `COMPLETED`: проверяйте `status` и `warnings`.

## Почему архитектура осталась небольшой

- `Event` уже представляет одну дату: не меняем ссылки из билетов, заказов и заявок на новый Session.
- `ExternalEvent` группирует даты одного внешнего события по `provider + external_event_id`.
- `ExternalDate` связывает внешний ID даты с существующим `Event` один-к-одному.
- `ExternalSnapshot` хранит последний ограниченный и очищенный ответ ресурса, хеш и обзор структуры.
- У `Venue` добавлены служебные поля внешнего источника/ID и уникальность их пары. Пустые страна/город/адрес разрешены для неполного импортированного черновика: вместо отсутствующих данных ничего не придумывается.
- `SeatingPlan`, `Seat`, `TicketOffer`, `TicketUnit`, заказы и деньги не заменены.
- Отдельный Hall пока НЕ создан: фактическая структура зала и схемы ещё не подтверждена. Идентификатор layout не используется вместо hall ID.
- `PortalBiletProvider` — небольшой класс HTTP-запросов; `ExternalTicketProvider` — только typing.Protocol. Нет универсальных менеджеров/шлюзов/очередей.
- Никаких новых runtime-зависимостей. HTTP, URL, хеширование, CSV и расчёт геометрии используют стандартную библиотеку. Celery/Redis не добавлены.

## Что делает импорт

1. Проверяет URL `https://portalbilet.ru/{city}/{event}`. Tracking query/fragment удаляются; остальные URL строятся сервером.
2. Запрашивает page-data. Ищет ровно один однозначный объект event; использует его `id`, `event_source_id`, `place.id`, `hall_layout_id`. `selectedEventId` не используется.
3. Запрашивает `/dates`; при ошибке пробует `event.dates`. Fallback не позволяет помечать исчезнувшие даты неактивными.
4. Создаёт/находит площадку по внешнему ID. Ручные изменения существующей площадки не перезаписываются.
5. Для каждой распознанной даты создаёт непубличный Event. Повторный импорт не должен создавать новую копию. Неоднозначное время без часового пояса означает `date_tba=True`, а не выдуманную дату.
6. Категория пока «Импортировано — проверить категорию», EN-описание пустое, Fan ID не проверен, условия возврата не утверждены. Это намеренно черновик, а не готовый к продаже объект.
7. Повторная синхронизация обновляет только неотредактированные, неопубликованные события без билетов/резервов/заказов. Локальные изменения сохраняются и отмечаются предупреждением.
8. Получает JSON цен, координат, нумерованных/standing билетов и сохраняет ограниченные снимки. Координаты одинакового layout ID повторно не загружаются в течение 7 дней.
9. Возвращает `PARTIAL`: геометрия и inventory не декодированы, билеты не созданы. URL изображений/участники/категории остаются в диагностике, не заявляются как полностью импортированные сущности.

Нет жёстко зашитых ID примера. Единственные статические данные adapter — хосты, пути методов, RUB/source_code/source_id из справочника пользователя.

## Безопасность

Только `ADMIN` с действующей парольной staff-сессией может импортировать и читать снимки. Покупатель и MANAGER не получают этот доступ. Редактор схем доступен MANAGER/ADMIN по прежней политике каталога.

HTTP-клиент разрешает только три API/CDN-хоста PortalBilet из справочника; только HTTPS/443. Все DNS A-записи должны быть публичными IPv4. Соединение устанавливается с уже проверенным IP, TLS проверяет исходное DNS-имя. Это исключает повторное разрешение имени при подключении. IPv6-only источники в этой версии не поддерживаются.

Нет proxy из окружения, cookie/Authorization или передачи произвольных заголовков пользователя. Перенаправления проверяются заново. JSON Content-Type обязателен. Сжатые ответы отвергаются, чтобы избежать неограниченной распаковки. Есть лимит байтов и connect/read timeout; общий бюджет ограничивает HTTP-операции. DNS обслуживает системный resolver: его собственное ожидание не управляется socket timeout.

Транзакции создают локальные записи атомарно; сеть не вызывается внутри этих транзакций. Параллельный импорт одного URL/внешнего события блокирует PostgreSQL advisory lock, второй запрос получает `409 IMPORT_IN_PROGRESS`. Это отдельная блокировка процесса импорта, **не внешняя бронь билета**. Используется прямое соединение PostgreSQL, как в текущем Compose.

Снимки ограничены размером, известные чувствительные ключи удаляются. Это не универсальная гарантия отсутствия любых персональных данных: перед передачей диагностического архива его следует просмотреть. SVG не скачивается и не вставляется в HTML. Права на изображения не подтверждаются автоматически.

## Режим продаж

Доступен только `IMPORT_ONLY`. `MIRROR` и `LIVE_PROVIDER_SALE` отвергаются, а не притворяются работающими.

Не создаются TicketUnit по внешнему списку наличия. Источник не является подтверждением владения билетом. Собственные TicketUnit создаются прежними операциями проекта после подтверждения наличия. Локальные блокировки не резервируют что-либо у PortalBilet.

Не реализованы: нормализованная внешняя цена, внешний inventory, enabled_for_sale, массовое включение внешнего ряда в продажи, официальный reserve/order API. Поэтому синхронизация не может сбросить эти локальные настройки или цены: она вообще не пишет в текущие TicketOffer/TicketUnit/FinancialEntry.

## API импорта

Все маршруты — `/api/v1/`, с завершающим `/`. Staff login/CSRF остаются существующими.

| Method | URL | Назначение |
|---|---|---|
| POST | `/api/v1/staff/external-events/preview/` | Предпросмотр, без создания ORM-записей |
| POST | `/api/v1/staff/external-events/import/` | Импорт черновиков/снимков |
| GET | `/api/v1/staff/external-events/` | Список источников; стандартная пагинация |
| GET | `/api/v1/staff/external-events/{id}/` | Даты и диагностика источника |
| POST | `/api/v1/staff/external-events/{id}/sync/` | Повторная синхронизация, тело `{}` |

Запрос (пример синтаксиса, не запись о состоявшемся live-прогоне):

```json
{
  "provider": "portalbilet",
  "url": "https://portalbilet.ru/sochi/match-khk-sochi-spartak-kontinentalnaia-khokkeinaia-liga-2",
  "mode": "IMPORT_ONLY"
}
```

`preview: true` у import использует тот же непишущий preview. API не требует вводить source/date/layout ID.

Схематический ответ текущей версии (UUID и количества — иллюстрация, не фактические данные PortalBilet):

```json
{
  "status": "PARTIAL",
  "source_id": "UUID-источника",
  "mode": "IMPORT_ONLY",
  "created": {"events": ["UUID-черновика"], "venues": 1, "seats": 0, "ticket_units": 0},
  "updated": {"events": []},
  "resources": {},
  "warnings": [
    {"code": "LAYOUT_MAPPING_UNVERIFIED", "message": "Автоматическое создание мест не включено."}
  ]
}
```

Фактические counts/ID вычисляются в коде, не подставляются из этого примера. Возможны `FAILED`, `400 INVALID_PORTALBILET_URL`, `409 IMPORT_IN_PROGRESS`, `502 PROVIDER_DNS/PROVIDER_TIMEOUT/PAGE_DATA_SCHEMA` и стандартные ошибки доступа. Ошибка одной стадии сохраняется в diagnostics; неизвестные поля не интерпретируются как успешный импорт.

## Визуальный редактор

Открытие: `/ops/` → «Seating plans» → «Открыть редактор». Кнопка есть также в карточке схемы. Импорт PortalBilet: раздел «Импорт мероприятий» → список External events → «Импорт по ссылке PortalBilet».

Редактор содержит:

- создание сразу нескольких рядов; начало нумерации и шаг 1/2/-1/-2;
- прямые/изогнутые блоки, угол, ширина, расстояние между рядами;
- границы проходов для разделения групп соседства (сами визуальные интервалы увеличиваются перемещением блоков);
- масштаб колесом, перемещение холста Alt+drag, выделение рамкой/Shift;
- фильтр по сектору/ряду, перемещение, поворот, отражение, переименование, удаление;
- локальная отмена последних 20 операций;
- предварительный импорт CSV и безопасный экспорт CSV;
- пустой холст без фоновой картинки; изображение загружается через существующую карточку схемы;
- сохранение одной version-checked операцией; опубликованная схема только читается, для изменений есть копирование.

**Выделение в редакторе — не включение билетов в продажу.** Это выбор геометрических мест для редактирования.

До 50 000 мест в схеме, до 2 000 изменений/создаваемых мест за одно сохранение. Сохраняйте крупные схемы блоками. Для удобства нейтральный холст имеет пропорции 1600×1000; при загрузке изображения берутся его пропорции. В БД остаются нормализованные x/y 0…1.

Публикация без картинки теперь разрешена. При наличии картинки прежние проверки прав сохраняются. Изменение геометрии/нумерации очищает затронутые группы соседства: переставленные места не должны автоматически сохранять обещание «рядом».

Пакетная операция блокирует SeatingPlan через `select_for_update`, проверяет версию и весь итоговый набор мест, затем сохраняет транзакционно. Повторные номера, чужие ID, координаты вне 0…1 и удаление используемых мест запрещены. Смена номеров мест местами работает в одной транзакции. При конфликте версии локальная правка не перезаписывает чужую — нужно обновить данные и повторить редактирование.

Новые endpoints редактора (MANAGER/ADMIN):

| Method | URL | Вход / выход |
|---|---|---|
| POST | `/api/v1/staff/plans/{id}/block-preview/` | Параметры блока → `{seats, count, saved:false}` |
| POST | `/api/v1/staff/plans/{id}/csv-preview/` | `{text: "CSV"}` → `{seats, count, saved:false}` |
| POST | `/api/v1/staff/plans/{id}/bulk-edit/` | `{expected_version, create:[], update:[], delete:[]}` → `{version, created_ids, created, updated, deleted}` |

Block input: `sector`, `rows`, `seats_per_row`, `row_start`, `seat_start`, `seat_step`, `x`, `y`, `width`, `row_spacing`, `angle`, `curve`, `reverse_alternate`, `aisles_after`. В API геометрия в долях 0…1 (угол в градусах), в форме проценты. Все поля кроме sector имеют defaults. CSV заголовок: `sector,row,number,x,y`; UTF-8; comma/semicolon; до 512 КБ и 2 000 мест.

Bulk create — поля Seat без ID/plan. Bulk update — `{id, ...изменяемые поля Seat}`. Delete — массив UUID. `plan`, цены и внутренние поля билетов здесь не принимаются. Ошибки: `400 INVALID_GEOMETRY/BATCH_LIMIT`, `404 SEAT_NOT_FOUND`, `409 VERSION_CONFLICT/DUPLICATE_SEAT/PLAN_IMMUTABLE/PLAN_IN_USE`.

## Проверка на компьютере разработчика

Изменения Compose/.env не требуются. Внешние зависимости не добавлены.

```powershell
docker compose run --rm api python manage.py showmigrations core venues external_events
docker compose run --rm api python manage.py makemigrations --check --dry-run
docker compose run --rm api python manage.py migrate --plan
```

Если обнаружены несозданные изменения миграций или ошибки, сначала исправить их; не использовать `--fake`, `down -v` или удаление существующих migrations.

После проверки плана:

```powershell
docker compose run --rm api python manage.py migrate
docker compose run --rm api python manage.py check
docker compose run --rm api python manage.py test venues external_events --verbosity=2
docker compose up -d api
```

Две новые миграции: `venues.0003_external_place`, `external_events.0001_initial`. Добавлен отсутствующий `core/migrations/__init__.py`; поэтому ранее невидимые миграции core также могут впервые попасть в план. В существующей БД это требует проверки, не удаления таблиц.

Ручная проверка редактора: создать план → блок 5×12 → сохранить → перезагрузить → убедиться в 60 местах → повторить нумерацию (получить конфликт, не дубли) → открыть вторую вкладку (проверить version conflict) → опубликовать → убедиться, что изменения запрещены, копия редактируется.

## Получение недостающих реальных ответов

После установки файлов даже без выполненных миграций:

```powershell
docker compose run --rm --no-deps api python -m external_events.capture --url "https://portalbilet.ru/sochi/match-khk-sochi-spartak-kontinentalnaia-khokkeinaia-liga-2"
```

Команда не использует Django/БД и не передаёт cookies/пароли. Она получает page-data, сама определяет IDs, затем получает dates/prices/coordinates/tickets/standing для первых двух дат. Результат в `backend/portalbilet_capture.zip` благодаря существующему bind mount. При частичных ошибках архив содержит manifest с причинами; exit code 2 не означает, что JSON удалось получить. Для повторного запуска задайте новую папку `--output portalbilet_capture_2`.

Нужно проверить настоящий формат coordinates, устойчивый join key tickets↔coordinates, standing-количество/ценовые единицы, а затем добавить декодер и тесты на реальных очищенных fixtures. До этого приложение НЕ заявляет, что автоматический импорт схемы завершён.

## Плановая синхронизация

```text
python manage.py sync_external_events --limit 5
```

Команда пригодна для cron; отдельного worker/Redis нет. Синхронизация по умолчанию не чаще 360 минут на источник, ручной sync — отдельное действие. Это синхронизация метаданных/снимков, а не торговля внешним остатком.

Настройки: `PORTALBILET_HTTP_TIMEOUT=8`, `PORTALBILET_IMPORT_BUDGET=35`, `PORTALBILET_MAX_RESPONSE_BYTES=8388608`, `PORTALBILET_SNAPSHOT_BYTES=524288`, `PORTALBILET_MAX_DATES=20`, `PORTALBILET_SYNC_MINUTES=360`. Большие значения бюджета для HTTP-импорта требуют согласования с Gunicorn/Nginx timeout; для больших захватов предусмотрена CLI-команда, не долго живущий веб-запрос.
