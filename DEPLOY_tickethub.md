# Tickethub: запуск на сервере с доменом и HTTPS

Версия инструкции: 21 октября 2026 года. Релиз: **manager-checkout-promocodes**. Основа — последняя версия `tickethub_launch_update.zip`; включает оба приложения, заказ менеджеру, промокоды, предыдущие исправления каталога, изображений и схем.

**Сначала важное.** Здесь подготовлены исходники, миграции и конфигурация развёртывания. Это не отчёт об уже запущенном production-сервере. В среде подготовки нет Docker/PostgreSQL и не удалось установить зависимости Next/Django; полная сборка и сквозные проверки не подтверждены. Не открывайте продажи до прохождения проверок из разделов 5 и 11. Сводка фактически выполненных проверок находится в `VERIFICATION_tickethub_checkout.md`.

Текущая модель работы — **оформление заказа из доступных билетов с обработкой менеджером**, отдельно — заявка на подбор при отсутствии билетов. Онлайн-платёж не нужен для создания заказа. После выбора мест покупатель переходит к оформлению, а отправленный заказ попадает в `/ru/staff/orders` со статусом `NEW`. Приём карты/СБП и автоматическая выдача файлов билетов этим обновлением не добавляются. Не называйте ручное подтверждение оплаты подключённой платёжной системой.

## Быстрый ориентир

Это полный путь для нового VPS. Не пропускайте перенос базы, если у вас уже есть мероприятия и заказы.

1. Домен/DNS и сервер — разделы 1–3.
2. Настройки SMTP/секреты — раздел 4.
3. Проверка исходников, зависимости и сборка — раздел 5.
4. Пустая база **или** перенос текущих данных — разделы 6–7.
5. Домен и сертификат — раздел 8.
6. Каталог, реальные остатки, документы и включение заказов — разделы 9–10.
7. Проверка заказа, уведомления менеджера и промокода — раздел 11.
8. Резервные копии и обновления — разделы 12–13.

Для уже установленного локального проекта сначала прочитайте `UPDATE_tickethub_checkout.md`. Для правил скидок и API — `MANAGER_CHECKOUT_PROMOS.md`.

## 1. Что и где будет работать

Пример ниже — один VPS с Ubuntu 24.04 LTS и одним основным доменом. Везде заменяйте `tickets.example.com` своим доменом. Это пример, не адрес вашего сайта.

```text
Посетитель → HTTPS / Nginx
                   ├ /api/v1/     → Django / Gunicorn
                   ├ /ops/        → Django Admin
                   ├ /media/      → публичные изображения
                   ├ /static/     → статика Django
                   └ остальные URL → Next.js production
                         PostgreSQL доступен только внутри Docker
```

Снаружи открываются только 80/443 и SSH. Порты 3000, 8000 и 5432 в production-файле **не публикуются**. Сайт и API имеют один origin: отдельный API-поддомен и CORS для этой конфигурации не нужны. Изменяющие запросы сохраняют session cookies и CSRF-проверку.

Рабочие файлы в корне проекта:

```text
compose.production.yml      полный стек: БД, backend, frontend, Nginx, scheduler
compose.check.yml           отдельная временная БД для тестов
.env.production.example     пример настроек без настоящих секретов
deploy/                     Nginx, создание env, сертификаты, резервные копии
 tickethub_backend/         ваш backend
 tickethub_frontend/        ваш frontend
```

Не смешивайте этот compose с прежним `tickethub_backend/compose.prod.yaml`: тот рассчитан на другую, backend-only схему. В этой инструкции все production-команды вызываются из **корня**, через `sh deploy/prod.sh`.

Для первой оценки ресурсов можно рассмотреть 4 vCPU и 8 ГБ RAM, но это не измеренный минимум и не гарантия нагрузки. Лимит в 300 МП означает очень большие операции декодирования; сначала проверьте свой набор файлов и одновременные загрузки. Два worker-процесса выбраны как начальная настройка, а не как подтверждённая ёмкость. Для обложек афиши обычно разумнее подготовить отдельное изображение нормального веб-размера: сервер не создаёт миниатюры автоматически.

## 2. Домен, DNS и доступ

В DNS-панели домена создайте A-запись выбранного имени на публичный IPv4 сервера. AAAA нужна только при реально работающем IPv6; неверная AAAA мешает открытию сайта и получению сертификата. На первом запуске пример предполагает DNS-only, без дополнительного внешнего reverse proxy.

Проверка с вашего компьютера:

```powershell
nslookup tickets.example.com
ssh root@SERVER_IP
```

Создайте обычного пользователя, настройте SSH-ключ и **проверьте вход в новом окне, не закрывая исходную сессию**:

```bash
adduser deploy
usermod -aG sudo deploy
```

Скопируйте свой публичный SSH-ключ в `/home/deploy/.ssh/authorized_keys` с владельцем deploy, правами 700 на `.ssh` и 600 на файл. После проверки доступа настройте запрет парольного SSH-входа согласно политике вашего сервера.

В firewall провайдера разрешите SSH только со своего адреса, 80/443 — для посетителей. Нельзя полагаться только на UFW для опубликованных Docker-портов: Docker использует свои правила перенаправления. Поэтому база и приложения в compose вообще не имеют `ports` [1].

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status
```

## 3. Docker и подготовка каталога

Команды установки основаны на официальной инструкции Docker для Ubuntu [1]. На сервере, где уже есть Docker и другие проекты, сначала проверьте версию и конфликты пакетов; не удаляйте используемую установку без плана переноса.

```bash
sudo apt update
sudo apt install -y ca-certificates curl unzip python3
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker run --rm hello-world
sudo usermod -aG docker deploy
```

Членство в группе docker фактически даёт высокие права на сервере; не добавляйте туда посторонних. Выйдите и войдите под deploy снова, затем:

```bash
docker version
docker compose version
sudo mkdir -p /opt/tickethub
sudo chown deploy:deploy /opt/tickethub
```

С компьютера Windows, из каталога с архивом:

```powershell
scp .\tickethub_checkout_promocodes.zip deploy@SERVER_IP:/home/deploy/
```

На сервере:

```bash
cd /opt/tickethub
unzip /home/deploy/tickethub_checkout_promocodes.zip
ls
```

В `/opt/tickethub` должны появиться `compose.production.yml`, `deploy`, `tickethub_backend`, `tickethub_frontend`. Не загружайте на сервер старые `node_modules` и `.next` с Windows.

## 4. Секреты и настройки

```bash
cd /opt/tickethub
python3 deploy/create_production_env.py tickets.example.com
nano .env.production
```

Скрипт создаёт случайный Django secret и **два разных** пароля PostgreSQL. При существующем `.env.production` он останавливается, ничего не заменяя. Файл создаётся с правами 600. Не публикуйте его, не отправляйте в чат и не добавляйте в Git.

Заполните SMTP и реальные контакты. Значения ниже — шаблон полей, а не рабочие credentials:

```env
EMAIL_HOST=smtp.your-mail-provider.example
EMAIL_PORT=587
EMAIL_HOST_USER=your-smtp-login
EMAIL_HOST_PASSWORD='your-smtp-password'
EMAIL_USE_TLS=true
EMAIL_USE_SSL=false
DEFAULT_FROM_EMAIL='Tickethub <hello@tickets.example.com>'
CONTACT_EMAIL=hello@tickets.example.com
CONTACT_PHONE=+XXXXXXXXXXX
CONTACT_HOURS='Ежедневно, 10:00–20:00, время Москвы'
STAFF_NOTIFICATION_EMAILS=manager@your-domain.example

PUBLIC_FORMS_ENABLED=false
ORDER_INTAKE_ENABLED=false
CLIENT_ANALYTICS_ENABLED=false
```

Для SMTP с implicit TLS на 465 задайте порт 465, `EMAIL_USE_TLS=false`, `EMAIL_USE_SSL=true`. Не включайте оба режима одновременно. У конкретного почтового провайдера возьмите разрешённого отправителя и настройки SPF/DKIM/DMARC; не придумывайте их значения. У VPS-провайдера исходящий SMTP может быть ограничен.

Пароли с `$`, `#` и пробелами заключайте в одинарные кавычки по правилам `.env` Compose. Не используйте `source .env.production`: это не shell-скрипт.

`PUBLIC_HOST` автоматически задаёт HTTPS origin, Django allowed hosts, CSRF trusted origin, публичный URL Next и **приватный SSR Host**. Значение `API_INTERNAL_HOST` не попадает в браузер; оно нужно серверному Next, который обращается к Django по внутреннему имени `backend`. Не меняйте это на `NEXT_PUBLIC_*` и не подставляйте туда клиентский заголовок.

На сервере остаётся `NODE_ENV=production`; запускать `npm run dev` для посетителей нельзя [2].

## 5. Зависимости, проверка и сборка — обязательный этап

В архиве сохранён настоящий `package-lock.json` из вашего проекта. Версии Next/React не обновлялись автоматически. Python-зависимости исходного backend заданы диапазонами; в среде подготовки lock не удалось разрешить. Скрипт ниже создаёт **настоящий** lock через pip в той же версии Python, что будет в контейнере:

```bash
cd /opt/tickethub
sh deploy/lock-python.sh
cat tickethub_backend/backend/requirements.lock
```

При ошибке сети/версии скрипт не подменяет старый lock пустым файлом. Разберитесь с ошибкой registry; не заменяйте результаты выдуманным списком версий. Сохраните полученный lock в репозитории релиза. Сам `pip freeze` не заменяет проверку уязвимостей и лицензий.

Запустите backend-тесты **на отдельной временной базе**:

```bash
docker compose --env-file .env.production -f compose.check.yml build tests
docker compose --env-file .env.production -f compose.check.yml up --abort-on-container-exit --exit-code-from tests
docker compose --env-file .env.production -f compose.check.yml down
```

Это проект `tickethub-check`, не `tickethub-live`. Он не подключает production-volume. В командах нет `down -v` для рабочей БД. Проверка `makemigrations --check` должна подтвердить, что модель и миграции согласованы; затем должны пройти тесты. Ошибку нельзя пропускать ради запуска.

Сборка приложений:

```bash
sh deploy/prod.sh build backend frontend
```

Dockerfile фронтенда запускает `npm ci`, typecheck, lint, автономные тесты, сверку переводов и `next build`. Если какой-либо этап падает, сборка останавливается. **Не удаляйте проверки и не добавляйте `--force` для сокрытия ошибки.**

Дополнительно в каталоге frontend на машине с установленным Node x64:

```bash
npm ci
npm run test:components
npx playwright install chromium
# E2E запускаются отдельно с настроенным тестовым Django, не с реальными заказами.
```

Проверяйте security advisories используемых зависимостей перед релизом; не применяйте `npm audit fix --force` без проверки совместимости. Контейнерные теги в env — начальные удобные значения, не неизменяемые версии. После успешных тестов сохраните разрешённые digest'ы базовых образов:

```bash
docker pull nginx:stable-alpine
docker image inspect nginx:stable-alpine --format '{{index .RepoDigests 0}}'
```

Аналогично для Node, Python, PostgreSQL и Certbot. Запишите проверенные значения `name@sha256:...` в `.env.production`; сохраните их с записью о релизе и пересоберите. Не меняйте major PostgreSQL поверх существующего volume.

## 6. База, миграции и первый администратор

Для нового пустого сервера:

```bash
sh deploy/prod.sh up -d --wait db
sh deploy/prod.sh run --rm --no-deps backend python manage.py migrate --noinput
sh deploy/prod.sh run --rm --no-deps backend python manage.py collectstatic --noinput
sh deploy/prod.sh run --rm --no-deps backend python manage.py createsuperuser
sh deploy/prod.sh run --rm --no-deps backend python manage.py seed_categories
```

`createsuperuser` создаёт владельца с ролью ADMIN. Используйте длинный уникальный пароль, а не пароль из тестов. Обычному покупателю доступ к staff не выдаётся.

`seed_categories` создаёт недостающие реальные категории: футбол, хоккей, баскетбол, теннис, концерты, шоу, театр. Он не изменяет существующие категории, не создаёт мероприятия, билеты, отзывы или пользователей. **`seed_demo` для рабочего сайта не запускайте.**

Если вы ещё не ставили прошлое обновление, будет применена и миграция `events.0004_category_images_publication`. Она добавляет фото категорий и снимает с публикации уже опубликованные события со служебной категорией импорта, шаблонными `{name}` / `{city-in}` / `{phone}` или остатками инструкции покупки в PortalBilet. Данные не удаляются: такие события остаются черновиками, version увеличивается. Автоматической повторной публикации нет.

Новые миграции этого релиза:

- `orders.0003_manager_checkout_discounts`: добавляет исходную сумму, скидку и код в заказ, распределение скидки по билетам; сохраняет суммы всех прежних заказов. Для старых заказов скидка равна нулю. Разрешает менеджеру уточнить срок выдачи позже, вместо уже просроченного автоматического срока.
- `promotions.0001_initial`: создаёт промокоды и журнал применений. **Никаких активных скидок автоматически не создаётся.**

При откате нельзя просто удалить эти таблицы или вернуть старую логику расчётов: новые заказы могут содержать скидки. Сначала проверяйте совместимость на копии базы.

При переносе существующей базы сначала выполняйте раздел 7, затем миграции; не создавайте поверх неё демонстрационные данные.

## 7. Перенос вашей локальной базы и media из Windows

Это необязательный раздел: нужен, если необходимо сохранить уже введённые мероприятия, схемы и пользователей. На время экспорта остановите изменения на локальном сайте. Сначала сохраните резервную копию; не удаляйте локальный Docker-volume.

В PowerShell из `tickethub_backend`:

```powershell
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc --no-owner --no-acl -f /tmp/tickethub.dump'
docker compose cp db:/tmp/tickethub.dump .\tickethub.dump

docker compose exec -T api sh -c 'tar -C /app/media -czf /tmp/tickethub-media.tar.gz .'
docker compose cp api:/tmp/tickethub-media.tar.gz .\tickethub-media.tar.gz

scp .\tickethub.dump deploy@SERVER_IP:/home/deploy/
scp .\tickethub-media.tar.gz deploy@SERVER_IP:/home/deploy/
```

Дамп сначала создаётся **файлом внутри контейнера**, затем копируется. Это избегает повреждения бинарного потока при перенаправлении в старых версиях PowerShell. Если локальная папка media ещё не создана и файлов нет, пропустите экспорт media, но убедитесь, что на диске действительно нечего переносить.

На сервере, **до миграций и только в пустую новую базу**:

```bash
cd /opt/tickethub
sh deploy/prod.sh up -d --wait db
sh deploy/prod.sh cp /home/deploy/tickethub.dump db:/tmp/tickethub.dump
sh deploy/prod.sh exec -T db sh -c 'pg_restore -U "$POSTGRES_APP_USER" -d "$POSTGRES_DB" --no-owner --no-privileges --exit-on-error /tmp/tickethub.dump'

sh deploy/prod.sh run --rm --no-deps -v /home/deploy/tickethub-media.tar.gz:/tmp/media.tar.gz:ro backend tar -C /app/media -xzf /tmp/media.tar.gz
sh deploy/prod.sh run --rm --no-deps backend python manage.py migrate --noinput
sh deploy/prod.sh run --rm --no-deps backend python manage.py collectstatic --noinput
sh deploy/prod.sh run --rm --no-deps backend python manage.py seed_categories
```

Импорт media производится из **вашего доверенного архива**. Не выполняйте tar над неизвестным присланным файлом. Проверяйте права владельца media; приложение работает от UID 10001, Next — от UID 1001.

Если pg_restore сообщает, что таблицы уже существуют, **не добавляйте наугад `--clean`**. Это означает, что база не пустая; создайте отдельную пустую целевую базу либо восстановите копию на отдельном тестовом сервере и проверьте план замены. Восстановление нельзя делать поверх принимающей заказы базы.

После переноса адрес сайта и secret меняются: старые локальные сессии не должны использоваться. Войдите заново. Если владелец уже перенесён, повторный createsuperuser с тем же email не нужен. Дампы содержат персональные данные — храните их приватно, удалите временные копии после подтверждённого восстановления.

## 8. Первый сертификат HTTPS

Certbot использует HTTP-01/webroot: домен должен уже вести на этот сервер, порт 80 должен быть доступен [3]. Сначала запускается временный Nginx, который отдаёт только challenge и 503 для остального сайта:

```bash
cd /opt/tickethub
sh deploy/prod.sh --profile bootstrap up -d nginx-bootstrap
DOMAIN=$(python3 deploy/env_value.py PUBLIC_HOST)
sh deploy/prod.sh run --rm --no-deps certbot certonly \
  --webroot -w /var/www/acme \
  --cert-name "$DOMAIN" -d "$DOMAIN" \
  --email YOUR_REAL_EMAIL --agree-tos --non-interactive
```

Замените `YOUR_REAL_EMAIL` вашим действующим адресом. Не продолжайте при неуспешной проверке. Проверьте A/AAAA, firewall и занятость 80 порта. Этот пример выдаёт сертификат только одному основному домену; `www` не добавляйте, пока не настроены его DNS, сертификат и отдельное правило перенаправления.

После успешной выдачи:

```bash
sh deploy/prod.sh --profile bootstrap stop nginx-bootstrap
sh deploy/prod.sh --profile bootstrap rm -f nginx-bootstrap
sh deploy/prod.sh up -d backend frontend scheduler nginx
sh deploy/prod.sh ps
sh deploy/prod.sh exec -T nginx nginx -t
```

Bootstrap и рабочий Nginx не должны работать одновременно: оба используют 80 порт.

```bash
curl -I "http://$DOMAIN/ru"
curl -I "https://$DOMAIN/ru"
curl -fsS "https://$DOMAIN/api/v1/public/config/?lang=ru"
curl -fsS "https://$DOMAIN/health/ready/"
```

HTTP должен перенаправляться на HTTPS. Health не означает проверку всего бизнеса — он проверяет доступность backend по своему контракту. Затем откройте сайт настоящим браузером.

Сертификаты сохраняются в Docker-volume `certificates`, а не в образе. Для продления:

```bash
sh deploy/renew-cert.sh --dry-run
crontab -e
```

Добавьте, например:

```cron
17 3,15 * * * cd /opt/tickethub && /usr/bin/flock -n /tmp/tickethub-cert-renew.lock sh deploy/renew-cert.sh >> /home/deploy/tickethub-cert-renew.log 2>&1
```

Скрипт проверяет конфигурацию и перезагружает Nginx после Certbot. Настройте контроль срока сертификата извне и ротацию этого cron-лога: наличие расписания само по себе не доказывает успешное продление [3].

```text
https://ваш-домен/ops/                 технический Django Admin
```

В категории выберите тип SPORT/CONCERT/OTHER, названия RU/EN, родителя при необходимости и порядок. Фото можно загрузить файлом либо HTTPS-ссылкой. Подтверждение прав не убрано. Новая фотография хранится у вас на сервере. Для хорошей скорости карточек подготавливайте отдельную горизонтальную обложку; не используйте многомегапиксельную схему арены в качестве фотографии футбола.

У импортированного события смените «Без категории (черновики импорта)» на реальную категорию, например «Хоккей». Проверьте дату и timezone площадки, названия, описания RU/EN, Fan ID, условия возврата, фон/геометрию и наличие билетов. Не оставляйте телефонные/городские шаблоны и инструкции «купить на Portalbilet». При недостатке информации сохраните черновик, а не выдумывайте данные.

Сохраните форму и нажмите «Опубликовать». Блок «Перед публикацией» перечисляет проблемы; проверка есть и на сервере, обход кнопки не разрешает публикацию. Опубликованная схема остаётся неизменяемой; корректировка через её копию.

Снимите с публикации демонстрационные события. Прежний seed оставляет в базе записи с «Демо:» в названии — обновление не удаляет их за вас. Нельзя выдавать демонстрационные продажи/остатки за реальные.

Главная показывает до шести записей из того же публичного каталога, что афиша, без скрытого фильтра «начиная с текущей секунды». Вкладки обращаются к backend с `kind`. Дата, статус переноса и «по запросу» не подменяются. Если после миграции не осталось проверенных опубликованных событий, пустая главная корректна: сначала завершите модерацию.

Проверьте афишу командой, которая ничего не меняет:

```bash
sh deploy/prod.sh exec -T backend python manage.py catalog_audit --strict
```

`BLOCK` нужно исправить до запуска. `WARN` — например, отсутствующая обложка или событие с прошедшей датой — требует просмотра. Команда не является юридическим аудитом, антивирусом или полной проверкой stock.

### Реальные билеты, а не только точки на схеме

У мероприятия должны быть активное предложение с положительной ценой и реальные `TicketUnit` со статусом `AVAILABLE`. Для нумерованного билета нужны подтверждённые сектор, ряд и номер. Статусы `ORDER_HELD`, `SOLD`, `BLOCKED` и чужой активный резерв не становятся доступными от включения оформления.

В этом релизе **старое значение `REQUEST` у предложения не скрывает реальный доступный остаток**. Остатки с ценой можно оформить при любом значении этого устаревшего признака. Если билетов нет, остаётся подбор, а не выдуманный резерв. Чтобы снять билет с продажи, заблокируйте `TicketUnit` или отключите предложение. Изображение/точка схемы сама по себе не создаёт билет.

Проверьте диагностикой (замените slug):

```bash
sh deploy/prod.sh exec -T backend python manage.py checkout_status --event YOUR_EVENT_SLUG
```

Команда ничего не меняет: покажет флаги, готовность документов, причину закрытия конкретного события и количество пригодных билетов. `online_payments_enabled: False` — нормально, это не препятствие заказу менеджеру.

## 10. Почта, документы и включение приёма заказов

В административном интерфейсе подготовьте и утвердите ваши реальные документы с кодами `privacy`, `offer`, `refund-policy`, RU/EN и данными оператора. В версии проекта уже есть управление версионированными документами; опубликованная версия не должна тихо переписываться. Шаблонные тексты в архиве не являются готовыми юридическими документами для вашего бизнеса.

SMTP проверяется реальной доставкой, а не только наличием env:

```bash
sh deploy/prod.sh exec -T backend python manage.py shell -c "from django.core.mail import send_mail; from django.conf import settings; print(send_mail('Tickethub: проверка доставки', 'Проверка почты сервера Tickethub.', settings.DEFAULT_FROM_EMAIL, [settings.CONTACT_EMAIL], fail_silently=False))"
```

Проверьте входящее письмо, папку «Спам» и журналы backend. Не публикуйте логи с паролями/OTP.

После настройки документов, контактов, реальных билетов и успешного теста почты:

```env
PUBLIC_FORMS_ENABLED=true
ORDER_INTAKE_ENABLED=true
CLIENT_ANALYTICS_ENABLED=false
STAFF_NOTIFICATION_EMAILS=manager@your-domain.example
```

Вставьте настоящий email менеджера. Можно несколько адресов через запятую. Это не покупательский email и не настройка платёжного провайдера.

Затем пересоздайте сервисы, чтобы env перечитался:

```bash
sh deploy/prod.sh up -d --force-recreate backend frontend scheduler nginx
sh deploy/prod.sh exec -T backend python manage.py check --deploy
```

Проверьте результат:

```bash
sh deploy/prod.sh exec -T backend python manage.py checkout_status
DOMAIN=$(python3 deploy/env_value.py PUBLIC_HOST)
curl -fsS "https://$DOMAIN/api/v1/public/config/?lang=ru"
```

Нужно увидеть `public_forms_enabled: true`, `order_intake_enabled: true`, `legal_ready: true`, `checkout_mode: "MANAGER"`. Значение `online_payments_enabled: false` должно остаться: сайт не принимает карту, но принимает заказ. Если `legal_ready` false, опубликуйте и утвердите реальные документы, а не отключайте CSRF или проверку согласий.

`restart` не перечитывает env контейнера. Аналитику можно оставить выключенной. Если позже её осознанно включить, настройка посетителя доступна в подвале; отсутствие явного согласия означает отсутствие необязательных клиентских событий. Учёт реальных заказов в панели сотрудников — отдельная бизнес-функция.

## 11. Проверка в браузере до реальных клиентов

Проверьте русский и английский интерфейсы, обе темы и телефон. Особенно: обложки категорий, главную/афишу/спорт, схему (кнопки, колесо, сектор, перемещение, pinch), удобство выбора места через список и возврат к странице.

На отдельном staging-наборе пройдите вход покупателя по OTP, заявку с сохранением формы, резерв и его истечение, повторное обновление страницы, заказ, появление заказа у менеджера, запись **тестовой** оплаты и отметку выдачи. Не используйте реальные платёжные записи для тренировки. Отдельно проверьте, что покупатель не открывает staff, чужой заказ и внутренние данные поставщика.

В DevTools → Network запросы должны иметь `/` перед `?`: `/api/v1/me/?lang=ru`, `/api/v1/public/config/?lang=ru`, `/api/v1/auth/csrf/`. Не должно быть циклических 301/308, CORS, 413 или CSRF-ошибок. На сервере нет dev-кнопки Next и overlay; используется production server из standalone build [2].

Загрузка категории: файл → сохранение → появление фото на `/sports`; отдельно URL → локальный media URL. Проверьте отказ без прав, конфликт `expected_version` из двух вкладок и запрещённый приватный URL. Для огромных схем измерьте время и RAM на ваших файлах.

Только после этой приёмки включайте рекламу и выдавайте сайт реальным клиентам. Файл `VERIFICATION_tickethub_checkout.md` описывает, какие проверки уже выполнены здесь, а какие остаются на вашем стенде.

### 11.1. Пройти заказ покупателя → менеджер

На staging или на выделенном собственном тестовом событии:

1. Откройте событие, выберите доступные места или количество в категории и нажмите **«Перейти к оформлению»**. Гость сначала подтверждает email кодом; выбор не должен потеряться.
2. Заполните имя/телефон и согласия, подтвердите серверную стоимость и резерв. Резерв длится до 10 минут; перед началом события или явным сроком продаж он может быть короче.
3. На этапе резерва введите промокод, нажмите **«Применить»**, проверьте скидку и итог. Код необязателен. Введённый, но не применённый код нужно применить либо явно убрать.
4. Нажмите **«Оформить заказ»**. Откроется заказ со статусом `NEW` / ожидание менеджера, оплатой `UNPAID`. Не должно быть перенаправления к эквайрингу.
5. В отдельном окне сотрудника откройте `/ru/staff/orders`. Список обновляется каждые 15 секунд в активной вкладке. Откройте тот же номер, проверьте контакты, билеты, исходную цену, скидку и сумму к оплате.
6. На email из `STAFF_NOTIFICATION_EMAILS` должно прийти уведомление с прямой ссылкой на заказ. При отсутствии письма смотрите `EmailLog` / `/ru/staff/notifications`: сам заказ не должен пропасть или отмениться из-за SMTP-сбоя.
7. Нажмите **«Взять в работу»**, свяжитесь с клиентом, уточните детали, затем подтвердите. После фактической оплаты зафиксируйте именно сумму **после скидки**, затем отметьте реально отправленные билеты.
8. Обновите страницу покупателя и повторите один и тот же сетевой запрос в тесте: не должно появляться второго заказа и второго применения скидки. После создания заказа исходный checkout-таймер больше не освобождает билеты — они `ORDER_HELD` до решения менеджера.

Для неоплаченного отменённого заказа используйте штатную операцию отмены с подтверждением отсутствия незавершённых расчётов. Не редактируйте статусы билетов напрямую в БД.

### 11.2. Создать и проверить промокод

Войдите **администратором** в `/ru/staff/promo-codes`. Менеджер видит коды и их условия, но менять скидки может только администратор.

Пример для теста (не создаётся автоматически): `MATCH10`, тип «Процент», значение `10`, минимальный заказ `1000` ₽, максимум скидки `2000` ₽, общий лимит `100`, на клиента `1`. Можно задать период или выбрать одно мероприятие; пустое мероприятие означает все.

Проверьте на тестовом заказе 10 000 ₽: скидка 1 000 ₽, итог 9 000 ₽. Затем проверьте неверный/просроченный код, лимит одного клиента, изменение условий в другой вкладке. Для финального заказа backend проверяет всё повторно; успешный предпросмотр не обещает последнее применение, пока заказ не создан.

Коды фиксированной скидки вводятся в рублях в интерфейсе, API хранит копейки. Процент — целое число от 1 до 99. Скидка не может полностью обнулить заказ. Один код на заказ; с индивидуальным Quote скидка не суммируется. Применение считается при создании заказа, а не при предпросмотре и не при оплате. Отмена/возврат не возвращают лимит — это защита от бесконечного повторного использования; при необходимости администратор создаёт отдельный код.

Дополнительно уже включён настоящий E2E-сценарий `tests/e2e/live.spec.ts`. Для отдельного staging-Django задайте `E2E_ALLOW_WRITES=1`, `E2E_CUSTOMER_EMAIL`, `E2E_OTP_FILE` (свежий код из тестовой почты), `E2E_EVENT_SLUG`; для проверки скидки — `E2E_PROMO_CODE`. Затем `npm run test:e2e`. При отсутствии разрешения на запись/учётных данных сценарий **пропускается**, это не успешная проверка покупки. Не направляйте его на базу реальных клиентов.

Параллельные заказы на последнее применение проверяются в новых PostgreSQL-тестах. Их исходники включены; выполнить нужно в отдельной базе из раздела 5, они **не были выполнены в среде подготовки**.

## 12. Резервные копии, обновления и восстановление

Резервная копия:

```bash
cd /opt/tickethub
sh deploy/backup.sh
```

Сохраняются дамп БД, media, приватный env, compose и lock-файлы. Дамп консистентен на момент pg_dump; для точного соответствия БД и media приостановите загрузку/замену изображений на время копирования. Для общего обновления безопаснее закрыть приём новых действий и выбрать окно обслуживания.

Расположите копии **вне сервера**, зашифруйте и ограничьте доступ. Одна копия на том же VPS не защищает от потери VPS. Проверяйте восстановление на отдельной базе. Скрипт не удаляет старые копии автоматически; задайте срок хранения и контролируйте диск.

Пример ежедневного задания:

```cron
42 2 * * * cd /opt/tickethub && /usr/bin/flock -n /tmp/tickethub-backup.lock sh deploy/backup.sh >> /home/deploy/tickethub-backup.log 2>&1
```

Доставка в удалённое хранилище и мониторинг результата настраиваются отдельно. В копиях есть персональные данные и секреты.

Порядок обновления:

1. Сохраните текущий код, lock, digest'ы и резервную копию БД/media. Закройте новые действия на окно обслуживания.
2. Обновите исходники, **не заменяя** `.env.production` и не удаляя volumes. Применяйте patch только к указанной базовой версии.
3. Выполните изолированные тесты и сборку новых образов. До этого старое приложение может продолжать работать, если схема ещё не менялась.
4. Для миграций остановите приложения, не базу. Выполните миграции/collectstatic из нового образа, затем пересоздайте сервисы, включая Nginx (обновятся адреса upstream).

```bash
sh deploy/backup.sh
# Здесь обновление исходников и проверки из раздела 5.
sh deploy/prod.sh build backend frontend
sh deploy/prod.sh stop nginx frontend scheduler backend
sh deploy/prod.sh run --rm --no-deps backend python manage.py migrate --noinput
sh deploy/prod.sh run --rm --no-deps backend python manage.py collectstatic --noinput
sh deploy/prod.sh up -d --force-recreate backend frontend scheduler nginx
sh deploy/prod.sh exec -T backend python manage.py check --deploy
sh deploy/prod.sh exec -T backend python manage.py catalog_audit --strict
```

При неудаче сохраняйте логи и не запускайте второй независимый приём заказов. Откат кода после миграции не всегда совместим с новой схемой: проверяйте обратимость миграций на копии либо восстанавливайте согласованные БД/media/код из резервной копии. Новые заказы, поступившие после копии, нельзя просто потерять — нужен отдельный план переноса/сверки.

**Никогда не выполняйте для работающего проекта `docker compose down -v`, `docker volume prune` или удаление каталогов media как способ «починить запуск».**

## 13. Где смотреть ошибки

```bash
sh deploy/prod.sh ps
sh deploy/prod.sh logs --tail=150 backend
sh deploy/prod.sh logs --tail=150 frontend
sh deploy/prod.sh logs --tail=150 nginx
sh deploy/prod.sh logs --tail=150 scheduler
```

| Симптом | Что проверить |
|---|---|
| Оформление недоступно | `checkout_status --event SLUG`: флаги, документы, явный срок продаж/статус события, активное предложение и фактический остаток. Онлайн-оплата не нужна |
| Промокод не применился | Код активен, период и мероприятие подходят, минимальная сумма/лимиты соблюдены; в браузере нажата «Применить»; не используется Quote |
| Заказ есть, письма менеджеру нет | `STAFF_NOTIFICATION_EMAILS`, SMTP и `EmailLog`; заказ ищите в панели, не создавайте повторный |
| 502 после обновления | Здоровье backend/frontend, завершение сборки, пересоздание/reload Nginx после смены контейнеров |
| CSRF 403 | Вы действительно на HTTPS основного домена; PUBLIC_HOST правильный; Nginx передаёт Host и X-Forwarded-Proto; cookie не блокируются |
| DisallowedHost / SSR redirect | У Next `API_INTERNAL_HOST` совпадает с PUBLIC_HOST; запросы к backend идут внутри сети, Django настроен на этот домен |
| 413 | Используется новый Nginx с `client_max_body_size 110m`; внешний прокси не вводит меньший лимит |
| Падает очень большая картинка | RAM, число одновременных загрузок, worker timeout; лимиты площади и сторон проверяются одновременно |
| На главной нет события | Публикация, настоящая активная категория, видимость PUBLIC; посмотрите catalog_audit и последствия модерационной миграции |
| Не меняется категория | Отправлена актуальная expected_version; конфликт требует перечитать запись, не убрать проверку |
| Не приходит OTP | SMTP, почтовый провайдер, запрет исходящего порта, EmailLog, реальные опубликованные документы и флаги форм |
| Ошибка получения сертификата | A/AAAA, доступность порта 80 снаружи, challenge, временный Nginx, отсутствие второго слушателя 80 |
| env изменён, а поведение старое | Пересоздайте нужные сервисы через `up -d --force-recreate`; простой restart не обновляет env |

Не отключайте CSRF, проверку сертификатов, права сотрудников или `expected_version` ради обхода ошибки. ID технического запроса можно раскрыть в «Данных для поддержки», а не показывать посетителю вместо понятного текста.

### Сохранённый срок продаж

Поле `sale_deadline` продолжает закрывать приём заказов, даже при наличии билетов. В прежних версиях оно могло заполняться автоматически за два часа до начала — это не признак онлайн-оплаты. Если срок оказался не тем, который нужен, измените его в карточке мероприятия на допустимый будущий момент до начала. Обновление не сдвигает существующие сроки и не открывает закрытые продажи молча.
